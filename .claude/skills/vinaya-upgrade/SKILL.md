# Vinaya Upgrade — bumping `@attalabs/vinaya` and its family in this monorepo

## Context — one version pin, four places it actually lives

`@attalabs/vinaya`'s version is not one fact in this repo, it is four, and they can silently disagree:

1. Root `package.json` devDependencies — the version `bun install` resolves for the CLI and `aeg-core`.
2. `apps/vinaya-portal/web/package.json` and `apps/vinaya-studio/web/package.json` — each pins `@attalabs/aeg-core`/`@attalabs/aeg-forge-state` (and Portal only, `@attalabs/vinaya-sources`) **independently** of the root file.
3. `.github/workflows/vinaya-checks.yml`, `vinaya-review.yml`, `vinaya-review-verdict.yml`, `vinaya-archivist.yml` — each runs a literal `npx --yes @attalabs/vinaya@<version>` string, generated by `vinaya init` and regenerated by `vinaya upgrade`. This is Ring 1 (CI).
4. `.husky/pre-commit` and `.husky/pre-push` — the same literal pinned-version `npx` string, inside a `>>> vinaya:managed:... >>>` block. This is Ring 0 (local hooks).

A plain `bun add @attalabs/vinaya@latest` (or a hand-edit of the root `package.json` alone) only ever touches (1). (2) then resolves to whatever range it already declared — often a stale one nobody remembers to update, so `node_modules` silently hoists a newer version than the file admits to. (3) and (4) don't move at all: Ring 0 and Ring 1 keep running the OLD version's checks while `package.json` claims the new one — the exact "three rings must agree" failure mode this harness exists to prevent, self-inflicted by the upgrade process itself.

Found and fixed by hand upgrading `0.17.1` → `0.18.0` → `0.19.0` (`#970`, `#971`) before this skill and its script existed.

## The script — `scripts/upgrade-vinaya.ts`

```
bun scripts/upgrade-vinaya.ts [version]
```

Omit `version` to resolve the latest published `@attalabs/vinaya` from npm. It does, in order:

1. Walks every `package.json` in the repo (skipping `node_modules`, `.git`, `.worktrees`) and bumps any `@attalabs/vinaya`/`aeg-core`/`aeg-forge-state`/`aeg-types`/`vinaya-sources` pin to the target version — preserving whichever range style (`^x.y.z` vs. an exact pin) that file already used, since this repo mixes both conventions and picking one is not this script's call.
2. `bun install`.
3. `npx --yes @attalabs/vinaya@<version> upgrade --yes` — regenerates the four managed CI workflows and both husky hooks' managed blocks to the new pinned version. This is the step a plain dependency bump has no equivalent for.
4. A full clean reinstall (`rm -rf node_modules` at the root and under every `apps/*/web`, then `bun install` again) — defends against a stale nested `node_modules/@attalabs/<pkg>/node_modules/@attalabs/aeg-types` copy at the OLD version surviving alongside the newly-hoisted one. Found live: it doesn't show up as a `bun.lock` diff, doesn't show up in a `find -maxdepth` shallower than five, and its only symptom is TypeScript reporting two structurally-incompatible copies of the same exported type (e.g. `Lifecycle`) with no hint that a stale duplicate is the cause.
5. `bunx turbo typecheck --force` and `vinaya doctor`, both printed in full, plus a short report at the end.

**The script does not commit, push, or open anything.** It leaves the tree dirty and the report on stdout — finishing the task is a normal task from there.

## After the script — what's actually left to do

**Read `vinaya doctor`'s output for anything beyond the two always-present, deliberately-out-of-scope findings:**

- `.github/workflows/vinaya-body-checks.yml is not installed` — expected and NOT something `vinaya upgrade` will ever fix; only `vinaya init` installs a workflow that doesn't already exist. Adding it (so CI can run `body-bare-digits`) is a separate, deliberate task, not something to fold into a version bump.
- The handful of `[doc-owners]` warnings about globs matching no tracked file — pre-existing repo hygiene, unrelated to the version bump, not this task's job to fix.

**A real `doc-coverage` finding is the one thing that usually needs action** — most often because the new version's changelog describes a behavior this repo's own doc pointer (`.claude/skills/vinaya-architecture/SKILL.md`, bound to `apps/vinaya-portal/**`/`apps/vinaya-studio/**` in `.vinaya/doc-owners`) no longer accurately describes. If so:

**Commit the doc fix BEFORE the dependency-bump commit, in its own commit — never after, never combined.** `doc-coverage`'s local pre-commit check (`vinaya check --all --local`, run by the `.husky/pre-commit` hook `upgrade` just regenerated) diffs only `main...HEAD` — committed history — and has no visibility into what is merely staged. Committing the code/dependency change first and the doc fix second means the doc-coverage check, running pre-commit on that second commit, still sees only the first commit's trigger with no doc pointer in `main...HEAD` yet — and fails, because the fix is sitting in the staging area it cannot see. Reordering so the doc commit lands first means: the doc-only commit trivially passes (nothing in `main...HEAD` yet needs it), and the dependency-bump commit's own pre-commit run sees a `main...HEAD` that already includes the doc fix — satisfied. Both commits pass individually; the final pushed branch's cumulative diff satisfies `doc-coverage` for real, the same way CI will read it.

**Then:** `bun run check` for the full sweep (typecheck + biome + affected tests + the forbidden-colors scan), fix anything real it surfaces, commit, push, open the PR the normal way (`npx --yes @attalabs/vinaya pr create --title "..." --body-file <path>` — never raw `gh pr create`, blocked by this repo's forge gate).

## What NOT to do

- Don't hand-edit any of the four version-pin locations directly — always go through the script, or if you must do it by hand, still run `vinaya upgrade --yes` afterward for the CI/hook half; a `package.json`-only edit leaves Ring 0/Ring 1 stale.
- Don't skip the clean reinstall step to save time. The stale-nested-duplicate failure mode is silent until `tsc` reports an opaque structural-incompatibility error with no mention of a duplicate; the clean reinstall is cheap insurance against a confusing debugging session.
- Don't fold `vinaya init`'s missing-workflow installation into an upgrade PR. `doctor` will flag it every time; that is a correct, stable finding, not a regression this task introduced.
- Don't combine the doc-coverage fix and the dependency bump into one commit, and don't commit the bump first — see above.
