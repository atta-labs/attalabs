# Vinaya — Product Architecture (`apps/vinaya-portal/`, `apps/vinaya-studio/`)

## Context

Vinaya is AEG packaged as a distributable product: `npx @attalabs/vinaya init` turns any GitHub repo into a governed one. Everything under `apps/vinaya-portal/` and `apps/vinaya-studio/` exists to ship that packaging — it does not reimplement governance logic. The single rule that disambiguates almost every design question in this tree: **Vinaya renders and spawns; the published `@attalabs/aeg-core` and `@attalabs/aeg-forge-state` decide.** If a change under either of these apps starts computing a governance verdict instead of consuming one, it is very likely in the wrong package.

## The contract chain the Portal renders

The `/start` pipeline (`apps/vinaya-portal/web/src/app/(site)/start/_lib/stages.ts`) mirrors the contract files bundled in the pinned `@attalabs/vinaya`'s `aeg-root/contracts/`: Plan → Develop → Review, with Security alongside Review, then Archive → Wrap up. The Planner renders each task's brief itself (`planner-developer.md`); there is no separate Brief stage or `brief-author` role. `architect-planner.md`, `security-archivist.md`, `planner-operator.md` and `principal-operator.md` sit outside that linear chain and are listed in `stages.test.ts`'s `CONTRACTS_MODELED_ELSEWHERE`; the test fails when a contract file on disk is neither in `STAGES` nor in that set.

Studio consumes `@attalabs/aeg-core`'s `checkDispatchReadiness`, which returns `blockerDetails` (one structured entry per blocker) alongside `blockers` and `ready`.

## Architecture — one web surface split into two apps; cli and sources extracted

The product used to be a single `web` workspace that served both the public marketing/docs site and the local-only Studio dashboard behind a runtime `isVercelDeploy()` gate — one deployment, two products, one gate that had to be correct on every route. The Portal/Studio split replaces that runtime answer with a structural one: the public surface and the local-only surface are now two separate apps that never share a deployment. Its vendored `cli/` and pre-extraction `sources/` workspace members are gone too — the CLI's canonical home is now the standalone `atta-labs/vinaya` repo (`apps/cli`), installed here as the published `@attalabs/vinaya` from npm; everything an app renders comes from the published `@attalabs/vinaya-sources` (registry) instead. Neither app carries a `specs/` directory of its own yet — each gets one when someone needs it, a separate, later decision.

```
apps/vinaya-portal/
└── web/        @atta/vinaya-portal-web — the public site: every `(site)` route (landing, /start,
                 /docs, /the-harness, /state-machine, /cli, /config, /compare, /roadmap). Deployed. Contains
                 no Studio route, no api/coherence, and no forge-connection code — that absence is
                 the design, not an oversight (task 1/#917). `/roadmap` is CMS-backed: its
                 items are `roadmapMilestone` Sanity documents (`getRoadmapMilestones()` in
                 `@atta/cms`), not a hardcoded array — content-editable from Studio without a
                 code change, and still no forge dependency (CMS is not forge). A milestone's
                 `version` is optional and holds only a record of what already shipped, never
                 a predicted/target number — see `.claude/skills/ui-cms-theme/SKILL.md`'s
                 "Non-theme content document types" section for the full rule and how status
                 derivation behaves while it's empty. Render ORDER is derived from that
                 `version` too, not taken from the CMS: `_lib/sort-milestones.ts` puts every
                 versioned milestone first, ascending, then the unversioned ones in the
                 editor's manual `order` — so a rung that ships stops sitting below the
                 unshipped ones without an editor renumbering anything.

apps/vinaya-studio/
└── web/        @atta/vinaya-studio-web — the local governance dashboard: `/studio`,
                 `/studio/projects`, `/studio/tranches`, `/studio/backlog`, and the
                 `api/coherence` route they read from. Never deployed — no ProductSwitch, no
                 `isVercelDeploy()` gate, because there is structurally nothing to gate against
                 (task 3/#885). Depends on neither spelling of the sources package — zero imports across
                 its moved surface, verified before the move; do not add it back for symmetry
                 with the other two apps.
```

The split apps also have independent CMS identities inside Vinaya's shared Sanity
project. Portal uses `vinayaPortal` for every runtime config and branding read and
generates its build-time UI aliases under `packages/ui/generated/vinayaPortal/`.
Studio symmetrically uses `vinayaStudio` and
`packages/ui/generated/vinayaStudio/`. Neither app reads the legacy `vinaya`
document or aliases the legacy `generated/vinaya/` directory; display copy that says
"Vinaya" remains a product label and is not a CMS key.

The vendored-copy deletion is load-bearing, not housekeeping: `init` detects a workspace
member declaring the published package's name and, when one exists, generates every
artifact — workflows, hook blocks, `VINAYA.md` — invoking that member's `dist` build
instead of the published package. A repo that means to *adopt* the published CLI must not
also vendor it.

### Both web apps consume the engine from the registry, not the workspace

`apps/vinaya-portal/web` and `apps/vinaya-studio/web` both declare `@attalabs/aeg-core` and
`@attalabs/aeg-forge-state` (Portal also `@attalabs/vinaya-sources`) as ordinary registry
dependencies at a real semver range — never `workspace:*`. attalabs is an adopter of the
engine here, not its host. Three consequences, each of which has to hold or the swap is
cosmetic:

- **`package.json` alone does not move resolution.** Bun resolves workspace members by
  package *name*, so as long as a local `packages/aeg-core` workspace member existed, a
  source file importing `@atta/aeg-core` kept resolving to it whatever the manifest
  declared — every import specifier had to move with the package.json swap, or the swap
  was cosmetic. The attalabs-adoption tranche closed this structurally by deleting
  `packages/aeg-core`/`packages/aeg-forge-state`/`packages/aeg-types` and the stale
  pre-extraction `@atta/vinaya-sources` workspace member outright: there is no local
  `@atta/*`-named workspace member left for a stray `@atta/aeg-core` import to shadow
  against.
- **The published packages ship raw `.ts`** via their `exports` field with no build step,
  so each app's `next.config.ts` must list them in `transpilePackages`; Next refuses to
  compile `.ts` under `node_modules` otherwise. Studio lists the two engine packages only —
  `@attalabs/vinaya-sources` stays out, since it has no consumer in this tree.
- **The lockfile is the evidence, not a green build.** Confirm each package resolves to a
  registry tarball with a `sha512` integrity hash rather than a workspace symlink.

Both apps declare the **same** range, so one engine tree resolves for the whole product —
two ranges would put two copies of the derivation logic behind two surfaces of one product.
Note that caret pins the *minor* on a `0.x` version (`^0.9.0` means `>=0.9.0 <0.10.0`), so
picking up a new minor is an explicit edit, and one that belongs to both apps together
rather than to whichever app is being touched.

### The one-way import boundary (mechanically enforced)

No web-shaped app may import `cli` internals; `cli` must never import a web app's internals. Each side carries its own vitest/bun-test file walking its own source tree and failing on any specifier reaching across — `apps/vinaya-portal/web/src/lib/import-boundary.test.ts`, `apps/vinaya-studio/web/src/lib/import-boundary.test.ts`, and `cli/tests/import-boundary.test.ts` — deliberately **not** sharing a helper between them, since importing one would itself cross the boundary they exist to defend. Crossing either direction would let one surface reach around the other's derivation and compute governance facts on its own — the renderer-never-derives rule, made structural.

### `@attalabs/vinaya-sources` — the shared registry + the two `StateSource` adapters

The seam the CLI and the Portal both sit on top of without crossing each other. **Read this section as describing the published package**, canonically developed in `atta-labs/vinaya` and consumed here from the registry. None of the three workspaces this seam originally joined still exist in this tree: `cli` was extracted, the original combined web app was deleted in the Portal/Studio split, and the local `@atta/vinaya-sources` workspace member — a stale pre-extraction copy with zero consumers — was deleted in the attalabs-adoption tranche.

- **`commands.ts`'s `COMMANDS` registry** — every command's name, description, flags, and `shipped`/`planned` status, in one place. The CLI's `printHelp()` and Portal's `/docs/cli` page are two renderers over this one registry — never a hand-transcribed second list. They do not read the same artifact, though: Portal declares the package and resolves it from `node_modules` when it builds, while the CLI inlines it at publish time (its shipped bundle carries a literal `COMMANDS` array and never names the package), so an edit reaches Portal on the next install and `printHelp()` only on the next CLI publish.
- **`forge-adapter.ts`'s `createForgeSource`** (primary) — wires `@attalabs/aeg-forge-state`'s `deriveTrancheFromForge` behind aeg-core's `StateSource` contract.
- **`file-adapter.ts`'s `createFileSource`** (transitional, deliberately deleted once every consumer is forge-backed) — wraps `parseTranche` over a configurable governance root.
- **`select-source.ts`** — config-driven choice between the two.
- **`doctrine-file-adapter.ts`'s `createFileDoctrineSource`** — implements aeg-core's `DoctrineSource` contract, reading `<root>/enforcement.md` + `roles/*.md` + `contracts/*.md` for `DiagramModel` derivation.

Both adapters are proven equivalent by a golden comparison test (`golden-forge-vs-file.test.ts`) — the forge and file paths must derive the identical `Tranche` shape on every field the pure evaluators read.

### `cli` — the shipped package

**Router:** `vinaya help`/`version`, `check <name>|--all`, `new check`, `pr|issue create|edit`, `pr report`, `init|init product|eject`, `doctor|upgrade`, `archive|archive tranche|audit`, `demo break|waiver`, `studio`, `quickstart`. The per-command source of truth is `COMMANDS`, above — this list drifts; the registry does not. `archive tranche <slug>` (`cli/src/commands/archive.ts`) is the tranche-level bookend to `init product`: it closes the GitHub Milestone, refusing outright if any task Issue attached to it is still open — the same refuse-by-default posture as every other forge-write here, so a tranche can never be closed with unresolved work by accident.

**Check engine (`cli/src/checks/`)** — the mechanism every gate reaches an adopter through:

```
CheckSpec { name, run, args?, scope: 'diff'|'full', include?, timeoutMs?, env? }
   │
   ├─ scope:'diff'  → runner may skip under --diff-only when no `include` glob matches a changed file
   ├─ scope:'full'  → always runs (coherence, dispatch-readiness — both read live forge state)
   └─ env           → declared allowlist; child spawns with ONLY the fixed baseline
                       (PATH/LANG/HOME/HTTPS_PROXY/HTTP_PROXY/NO_PROXY/TMPDIR) plus
                       whatever the check explicitly forwards — never the full parent env.
                       Any core check whose bin spawns `gh` (any call shape) or reaches
                       the forge via token resolution must forward GITHUB_TOKEN/GH_TOKEN
                       `{ optional: true }` — on CI runners those vars are `gh`'s only
                       auth path; coupling-tested in tests/checks/registry-env.test.ts
   ▼
runner.ts:  spawn → race timeoutMs → parse stderr as CheckError JSON lines → CheckOutcome
   ▼
CheckError { schema: 1, check, severity: 'error'|'warning', message, agent_recovery_prompt, file?, line? }
```

`agent_recovery_prompt` is a corrective **instruction**, never a restatement of `message` — this is the ring-0 self-correction loop's entire mechanism (a hook that only diagnoses, never tells the agent what to run next, is half-built). The exit code IS the verdict (`0`=pass, `1`=findings); anything else, or unparseable stderr, is `status: 'error'` — a check that emits garbage must be loud, never a silent pass. A `timeoutMs` is runner-enforced (the runner kills the child; a check is never trusted to self-enforce its own deadline).

`coreCheckRegistry()` ships every core check through this exact same `CheckSpec` interface as any adopter-authored custom check — the set grows with releases, so the current list is read from the registry itself (`cli/src/checks/registry.ts` in `atta-labs/vinaya`), never from a doc — `tests/checks/no-privileged-api.test.ts` mechanically proves neither side carries a field the other cannot. `vinaya new check <name>` scaffolds a self-contained custom check into the *adopter's* repo (`./scripts/vinaya-checks/<name>.ts`), never into this package.

**`vinaya pr report --write <body-file>` and `evidence-fresh` (0.12.0).** `pr report` emits an `AEG:EVIDENCE` block between `<!-- AEG:EVIDENCE:START -->`/`<!-- AEG:EVIDENCE:END -->` markers, replacing any prior block at those anchors in place (or appending a fresh pair when the body carries none yet). Two groups, deliberately unequal in what can be re-verified: **Group A** is the head sha and a width-invariant `git diff --numstat` against the resolved merge-base (`--numstat`, never `--stat`, which scales column widths to output width and would differ byte-for-byte between a terminal and CI for identical content). **Group B** is the result of `vinaya check --all --diff-only` — this repo's own portable gate suite, not the host toolchain's own `typecheck`/`lint`/`test` commands, so Group B stays meaningful in an adopter not on this repo's exact stack. `evidence-fresh`, the CI-side check, recomputes and byte-compares Group A against the PR's real diff; it can only check Group B for **staleness** (the recorded head sha still matches the PR's real head), never re-run the suite, so a fabricated Group B pass cannot be caught by re-execution — only by the head-sha binding. Nothing outside the anchors is covered at all: prose claims elsewhere in the PR body are the author's to get right by hand. The anchor pair is opt-in — a PR body carrying none is not broken by the absence — so when the emitter genuinely cannot run (an environment defect, an unresolvable merge-base), the correct response is to say so plainly in the body, never to hand-type a block that imitates the emitted shape.

**A core check adapter that drops an optional argument silently disables the evaluator behind it.** `check-coherence.ts` called `checkR1(issues, grandfathered)` while aeg-core's `checkR1` had grown an optional third `registeredNames` — defaulting to `[]`, which is that evaluator's own dormant-when-absent state. The result was a control that `enforcement.md` and `state-machine.md` both described as enforced, silently inert in the shipped CLI: the adopter-facing surface. The adapter now reads `.vinaya/projects.md` from `git rev-parse --show-toplevel` and passes the names. Note precisely what that does and does not buy: `--show-toplevel` resolves **relative to cwd**, so it is not itself immune to the `chdir` class above — it is correct here only because this bin deliberately performs no `chdir` and the runner spawns it with the caller's cwd. What it adds over a bare `cwd` is subdirectory-tolerance, plus a safe failure: outside any repo git exits 128, the helper yields `''`, and the check goes dormant rather than resolving some unrelated repo's registry. The dormancy is announced — but through `emitCheckError` with `severity: 'warning'`, never a raw `process.stderr.write`. Two general rules fall out. When an aeg-core evaluator gains an optional parameter whose default is "dormant", every `checks/bin/*` adapter is a call site that must be re-examined — a defaulted argument is not a safe no-op here, it is a disabled gate. And **every** byte a check bin writes to stderr must be a `CheckError` JSON line: `runner.ts` parses stderr line-by-line and one unparseable line forces `status: 'error'` regardless of exit code, so a friendly plain-text warning is indistinguishable from a crashed check.

One core check, `review-gate` (`cli/src/checks/bin/check-review-gate.ts`), wraps `@atta/aeg-core`'s `checkReviewGate` and carries **verdict-author verification** (2026-08-09): only PR comments whose author is on the principal allowlist participate in `APPROVE`/`PASS` verdict extraction — forged, bot, and unresolvable-author comments are ignored, never fatal. The allowlist defaults to the hardcoded `PRINCIPAL_ALLOWLIST` (this monorepo's own principal) the waiver actor-check also trusts, but is now overridable via `vinaya.config.json`'s `principals` field (`config.ts`'s `resolvePrincipalAllowlist`) — a full replacement, not additive, repo-local only (a global `~/.vinaya/config.json`'s `principals` is stripped the same way its `checks` already is). Fixes what was previously a structural gap: with no override, this check — and the `vinaya/waiver:docs`/`vinaya/waiver:review` actor-verified waivers, same trust anchor, same three check bins — was unpassable in any adopter repo whose own principal wasn't this monorepo's maintainer; found live the same night, on a real adopter repo's first dispatched task, when two independently-dispatched reviewer verdicts sat on a PR counting for nothing. `checkReviewGate`'s own `principalAllowlist` field stays optional and defaults to `PRINCIPAL_ALLOWLIST` when omitted — every existing caller (this repo's own use of `@attalabs/aeg-core`'s `verify-review-gate.ts` included) is unaffected.

**A trust-anchor read may not take its CONTENT from the job's own filesystem — three rounds of the same bug proved it.** `principals` decides who may approve a merge, so where it is READ from is itself security-critical. All three bins call `loadTrustAnchorConfig()` (`config.ts`) with no argument: a `gh api repos/<owner>/<repo>/contents/vinaya.config.json` read of the repository's **default branch**, decoded from base64 — no local git, no working tree, and no ref parameter selecting a commit. State the scope precisely, since overclaiming is what undid the previous two rounds: the CONTENT is server-side, but the repo IDENTITY addressing that call still comes from `trustAnchorRepo()` (`GITHUB_REPOSITORY`, else the `origin` remote). That is deliberate, not an oversight — where a PR controls the workflow YAML it already holds a strictly stronger primitive (delete the step), and where the YAML is trusted the runner sets `GITHUB_REPOSITORY` correctly so the remote fallback never runs. The precedence order is load-bearing; do not reorder it. The three rounds it took to get there, all caught pre-merge by the two dispatched reviewers, are worth knowing because each fix looked correct: (1) `loadConfig()` read the PR's own working tree — a PR added its author to `principals` and self-approved; (2) `git show ${BASE_SHA}:…` — but a `pull_request`-triggered workflow runs the PR's OWN copy of the workflow YAML, so the PR set `BASE_SHA` to its own head; (3) `git show origin/main:…` hardcoded — but `origin/main` is a LOCAL remote-tracking ref, and the PR's workflow can `git update-ref refs/remotes/origin/main HEAD` before the gate runs (reproduced live). Every round's fix removed one lever while leaving the class open. `check-doc-coverage.ts`/`check-doc-coverage-push.ts` keep their own separate, still-overridable `BASE_SHA` for diff-scoping — not a trust decision, never reused for principals. Any future trust-anchor field belongs on this same API path.

**Say plainly what the gate is and is not.** Because a `pull_request`-triggered workflow's definition comes from the PR, a PR can always delete the gate's step or `exit 0` — no in-workflow cleverness changes that. **Branch protection with the Vinaya check required is still worth enabling** — `init` prints the command and `doctor` reports its absence — but say precisely what it buys, because the obvious sentence is wrong. A required status check is satisfied by a conclusion reported under its name; it does not certify that the conclusion came from running the real check. Deleting the gate's *step* does not stop the *job* reporting green — only removing the job or workflow outright gives the never-reports case that blocks a merge — and a step edited to `exit 0` reports success having run nothing. **The trust boundary is who controls the workflow definition producing the required check, and under `pull_request` that is the PR author, whatever the check is packaged as.** Packaging decides blast radius, not the boundary: against a published artifact the PR can rewrite only the invocation; in a repo vendoring the CLI it also controls the check sources, the build script, and the dependency lifecycle scripts the install step runs. The same widening needs no packaging question at all — any required workflow that checks out the PR head and runs a gate from that tree is already in the wider class, which is where this monorepo's own hand-written review gate sits. Do **not** write "unbypassable" for the published case either; branch protection closes merge-without-a-report and nothing more, and the reviewer closes the rest. Note also that no generator emits the vendored shape yet (as of 2026-08-14 `init` writes only the published `npx` line, which in a vendoring repo misresolves and kills the job) — so describe it as the shape such a repo needs, never as current behavior. Documentation must never describe `principals` as a security control without the branch-protection prerequisite attached.

**Install lifecycle (`init`/`init product`/`eject`, `doctor`/`upgrade`):** `init` is a diff-and-confirm install of a fixed manifest (`cli/src/lib/artifacts.ts` — the ONE place that decides what ships to an adopter repo), recorded in a `managed` ownership block `eject` reverses exactly. `init product <name> [--path <path>]` (`cli/src/lib/registry-write.ts`) writes/appends a row to `.vinaya/projects.md` — the registry Studio's tranche board resolves a project's board link against (`web/src/lib/repo-state/read-root.ts`'s `readRegistry()`) — plus a `project:<name>` label (informational only, no shipped check or Studio reads it). The registry row is deliberately NOT tracked in the `managed` manifest and NOT reversed by `eject`: it is the adopter's own declared data ("Identity = the registry row" — `.vinaya/projects.md`'s own doctrine), not vinaya-owned scaffolding, the same way a hand-written `.vinaya/doc-owners` binding survives `eject` too. The generated git hooks invoke `npx --yes @attalabs/vinaya@<exact-installed-version>` — never a bare/`--no-install` spec, whose npx cache-key mismatch broke the first post-init commit on fresh machines (regression-tested in `cli/tests/init.test.ts`). The manifest's four workflows include a split review gate: `vinaya-review.yml` (required, `pull_request`-only) plus `vinaya-review-verdict.yml`, whose comment-triggered evaluation re-runs the required workflow on a clean verdict — cross-workflow check-run writes are platform-forbidden, so re-running is the propagation channel (2026-08-09). `doctor` diagnoses everything (hooks, workflows, manifest coherence, `gh` auth, custom-check registration) and mutates nothing; `upgrade` regenerates vinaya-owned artifacts through the same diff-and-confirm engine, leaving adopter-owned config content untouched.

**Adopting an already-governed repo — what `init` measurably does (verified against published 0.6.0 in attalabs, itself a non-greenfield adopter).** For a pre-existing file at a path `init` generates, foreign content — anything without a `managed` manifest claiming it — is REFUSED, printed as `✖ REFUSE <path> — foreign content exists at this path; not overwritten`, and the rest of the install proceeds around it. Both a hand-authored `vinaya.config.json` (no `managed` key) and a hand-authored `.vinaya/doc-owners` take this path: content is never replaced. The config is not left untouched byte-for-byte, though — `init` *appends* a `managed` block to it (recording only the artifacts init itself wrote: the four workflows, `VINAYA.md`, the two hook blocks) and reserializes the JSON; every adopter-authored key (`checks`, `briefSchema`) survives verbatim. And `init` writes no `aeg-root/` into the repo at all: the doctrine reaches an adopter only inside the installed package (`node_modules/@attalabs/vinaya/aeg-root/`), resolved at read time via `vinaya doctrine` — an in-repo doctrine copy is never part of the install, so a repo carrying its own hand-authored `aeg-root/` keeps it, unclobbered, alongside the package's.

**Guided install (`quickstart`):** a pure external orchestrator (`cli/src/commands/quickstart.ts`) over `init`/`init product`/`demo break`/`doctor`'s existing, unmodified entry points — it calls them in sequence with Y/n prompts between steps, never reimplements their internals. The install commit itself is never prompt-gated (it always runs, no-opping when there is genuinely nothing to commit); `demo break` defaults to yes, since the whole point is proving the install actually works before an adopter walks away. One hazard this surfaced that no single-prompt command had ever hit: `lib/prompt.ts`'s `closeStdin()` destroys the stdin stream permanently, so a command chaining multiple prompts (quickstart is the first) must close it exactly once, at the very end of the whole flow — not per-prompt the way every other command's own realDeps() does, which would hang the second prompt.

**Config loader (`cli/src/lib/config.ts`):** hierarchical — repo-local `vinaya.config.json` (walked up from `cwd`) over global `~/.vinaya/config.json`, `null` if neither exists; a global config's `checks` key is stripped at load time (loud stderr warning naming the file), never resolved. The **configurability architecture** (design frozen v11, implementation landing incrementally — the design chapter and its Correction history now live in `atta-labs/vinaya`, not this repo's spec) layers two things on top of this loader: an `env` allowlist per check (above), and a `default`/`overridden`/`additive` resolution model shared between checks and roles — a config key exactly matching a core ID is an override attempt (contract-validated, fail-closed if it doesn't satisfy the contract); any other key must be namespaced (`<name>/<id>`). This is a live, in-progress design — check that repo's own history for what has actually shipped versus what is still design-only before assuming a piece of it is built. The checks-side half of the resolution model has landed as a pure function (`cli/src/checks/resolver.ts`, `resolveChecks`/`isValidNamespacedKey`), feeding `vinaya check --plan` / `--plan --json` only — `vinaya check`'s real execution still runs the unvalidated flat concat until a later task wires the resolver into it (Correction 11). Every `vinaya.config.json` key, and the `--plan --json` envelope's own shape, is documented adopter-facing at `/config` (`@attalabs/vinaya-sources`' `CONFIG_REFERENCE`/`PLAN_JSON_SCHEMA`, Correction 12) — an authored registry, not a schema introspection, coupling-tested against `VinayaConfigSchema`.

**Distribution:** published as `@attalabs/vinaya` (bare `vinaya` is unobtainable — npm's typosquat filter, not a taken name), a single Node-executable ESM bundle inlining the whole workspace graph it is built from — in `atta-labs/vinaya` those are `@attalabs/aeg-core`, `@attalabs/aeg-forge-state`, `@attalabs/aeg-types` and `@attalabs/vinaya-sources` (only `@atta/typescript-config` keeps the `@atta` scope). The `files` allowlist (`dist/`, `templates/`, `aeg-root/`, `studio-standalone/`, `README.md`) is the tarball's actual contents — a file that isn't an `artifacts.ts` op AND isn't in this list never reaches an adopter, whatever else it may be (`specs/vinaya-spec.md`'s "Vinaya's own vs. attalabs' own" classification table is the authoritative three-way split when this is ambiguous).

**`studio-standalone/` — Studio ships runnable outside the workspace, split across both repos.** THIS repo is the producer: `.github/workflows/vinaya-studio-artifact.yml` builds `apps/vinaya-studio/web` (`next build`, `output: 'standalone'` — the only place workspace resolution of `@atta/*` and the `@atta/ui` codegen step work) on every push to `main` touching Studio's build inputs, plus on manual dispatch, and publishes the raw build (`standalone/`, `static/`, `public/` if present) as a GitHub Release asset on a rolling `studio-standalone-latest` tag. This repo is PUBLIC, so that asset is fetchable over plain HTTPS with no token. The standalone `atta-labs/vinaya` repo (`cli/scripts/bundle-studio.ts`, `studio.ts`'s `resolveStudioTarget()`) is the consumer: it fetches that release artifact at `prepack` time and assembles it into `studio-standalone/` — copying `static/`/`public/` into the standalone tree, renaming `node_modules` to `_node_modules` (npm/bun's packer unconditionally strips any directory literally named `node_modules`; `studio.ts` renames it back lazily on first run). That consumer repo's own generators are the authority on the exact path at any given time; treat any path cited here as illustrative, not current. Next's generated `server.js` also calls `process.chdir(__dirname)` as its own first line, so `AEG_REPO` is resolved from the caller's cwd *before* spawning and forced into the child's env — the one thing that makes the guest repo's identity survive that chdir. That chdir hazard is also why `VINAYA_REPO_ROOT` exists at all — see the FILE-based repo-root walk paragraph below.

**`verify-published-lifecycle.ts`'s coverage self-check has no grace period.** Every `status: 'shipped'` entry in `COMMANDS` must have a matching `EXERCISES` or `EXEMPTIONS` key before the script will run at all — a newly shipped command with neither is a coverage gap, not a silent skip. `archive tranche` and `quickstart` are both exempt: the former for the same live-forge/no-dry-run reason as `archive`/`audit`; the latter because it's a pure orchestrator over four already-exercised commands, with its own prompt-sequencing logic proven separately by `tests/quickstart.test.ts`.

**Published version tracks landed source, not a fixed cadence.** `package.json`'s `"version"` and `scripts/verify-published-lifecycle.ts`'s `PACKAGE_SPEC` are bumped together whenever fixes already merged to source need to actually reach `npx @attalabs/vinaya@latest` — source ahead of publish means an adopter installing today gets none of it. Most recently bumped to carry the standalone-Studio repo-root fix, the `.vinaya/doc-owners` drift exemption, `quickstart`'s validate/retry/multi-bind loop, and the `closes-n` token-forwarding fix — all described above, all landed in source before this bump made them installable. `0.4.4` carries the `requiresOpenPr`/`--local` bootstrap-deadlock fix, the `brief-shape` anchor-scoping fix, the `doctor` worktree-hooks fix, and the generated-CI `PR_BODY` wiring fix immediately below — all found live on a real adopter repo's first dispatched task, the day the requiring fix was authored. `0.4.5` carries the four fixes described in the next paragraph, found live on a real adopter repo running `0.4.4` and independently re-verified against this repo's own source before shipping. `0.4.6` carries the authoring-time half of the branch grammar — `validateForgeWrite` took no branch, so `pr create`/`pr edit` refused a standalone `fix/*` PR for a `Closes #N` its branch cannot carry while CI passed the identical body — plus the `noConsole` cleanup in `archive.ts`/`audit.ts`, which had been sitting in source unpublished. **Four more adopter-facing gaps, all found live against a real adopter repo running `0.4.4`, all re-verified against this repo's own source before fixing.** (1) `reviewWorkflow()`'s generated job ran `check --all` (the full registry, including `PR_BODY`-dependent checks like `test-plan`/`closes-n`) instead of just `review-gate` — the one check that job actually needs — and carried a stale `PR_BODY` wiring comment describing the exact bug the 0.4.4 fix above had already closed for the *checks* workflow but never applied to the *review* workflow; `reviewWorkflow()` now runs `check review-gate` only, with no `PR_BODY` env at all (`review-gate` never reads it). (2) `checksWorkflow()`'s `pull_request.types` omitted `edited`, so a PR author fixing a Test Plan/`Closes #N` gap by editing the body alone never re-triggered CI — the stale `✗ fail` sat on the PR until an unrelated push forced a re-run; `edited` is now in the trigger list. (3) `vinaya audit`'s direct-main-push check read `commits/{sha}/pulls` once — the same merge-association-lag class already fixed elsewhere in this codebase for a different endpoint — so a merge whose association hadn't propagated yet (confirmed live: read `[]` 15s post-merge) was misclassified as a direct push and opened a false incident; `runDirectMainPushCheck` now polls (6 attempts, ~20s apart, ~100s ceiling), breaking early the instant an association appears, falling through to today's behavior unchanged after the ceiling. (4) `check-brief-shape.ts` never read `BRANCH` and always ran `checkBriefSections` with `requireClosesN` defaulted to `true` — so a genuinely brief-shaped PR on a non-task branch (a standalone `fix/*` brief, which by design has no Issue to close) failed the merge gate on a `Closes #N` requirement it should never have carried; `check-brief-shape.ts` now ports `verify-brief.ts`'s existing non-task-branch bypass logic verbatim (`isTaskBranch`, newly exported from `brief-validation.ts` alongside `isBriefShaped`, feeding `requireClosesN: isTaskBranch(branch)`), and `registry.ts` forwards `BRANCH` to the check (previously silently stripped by the runner's env allowlist — the same failure class the `closes-n`/`test-plan` entries' own inline comments already warn about).

**The branch grammar reached the CI check but not the authoring wrapper.** The gap above fixed `check-brief-shape.ts`, which runs at merge time; `validateForgeWrite` — the runner behind `pr create`/`pr edit`, which runs at authoring time — took no branch at all and graded every body as a task branch's. Since `starterConfig()` seeds `{ builtin: 'closesN' }` unconditionally and `BriefSectionSchema` has no conditional form, an adopter opening a standalone `fix/*` PR was refused by the very wrapper the model mandates, for a `Closes #N` their branch structurally cannot carry — while CI would pass the identical body. One grammar, two enforcement points, disagreeing: the exact failure `enforcement.md` names. Confirmed live on an adopter repo, whose only lever was deleting the builtin from their own config — which silently drops the check for their task branches too. `ForgeValidationInput` now carries an optional `branch`, and `validateForgeWrite` applies the same predicates the check uses (`isTaskBranch`/`isBriefShaped`, imported from `@atta/aeg-core` rather than re-derived, so a fourth copy of `TASK_BRANCH_PATTERN` never appears): a non-task branch whose body is not brief-shaped bypasses every section, a brief-shaped one is graded on all of them except `closesN`, and the title grammar stays outside the bypass. An unresolvable branch stays fail-closed and enforces everything, so the relaxation is confined to the one axis it was built for.

**`archive.ts`/`audit.ts` carried 14 `lint/suspicious/noConsole` warnings** — every progress line used bare `console.log` instead of `process.stdout.write`, the convention every other command in this package already follows (`runAudit`'s own main output, for one). Quick standalone fix, no tranche: both files now write exclusively through `process.stdout.write`/`process.stderr.write`; `console.error` calls were never flagged by this repo's Biome config and stay as-is.

**The generated adopter CI never actually enforced `test-plan`/`closes-n` — it only looked like it did.** `checksWorkflow()`/`reviewWorkflow()` (`cli/src/lib/artifacts.ts`) wire `PR_NUMBER` into the generated workflow's env (the fix `PR #813` review already forced), but never `PR_BODY` — and `test-plan`/`closes-n` both read `process.env.PR_BODY` directly, never fetch it themselves. An unwired job sees an empty body, and both checks' documented "nothing to check yet" bypass reads that identically to a real PR with a genuinely empty Test Plan — so they printed `✓ pass` on every adopter CI run regardless of the PR's actual content. Confirmed live against a real adopter repo's real CI run: `test-plan: pass` on a PR whose test plan was never validated by anything. Both generators now also set `PR_BODY: ${{ github.event.pull_request.body }}` — the same safe env-injection idiom `PR_NUMBER` already uses (untrusted PR content lands in an environment variable, never interpolated into a `run:` script body). `tests/quickstart.test.ts`'s hook-swap-to-local-fixture must happen on quickstart's own first `confirm()` call, not gated on the demo-break question text — `commitInstall()` runs earlier in the flow and triggers the same real `.git/hooks/pre-commit` `vinaya init` just installed, so swapping any later lets that first commit hit the real (network-dependent) hook in a network-free test sandbox.

**Standalone Studio's `process.chdir` hazard was only half-fixed the first time.** The `AEG_REPO` fix above covers `resolveRepo()`'s git-remote/GitHub-API reads, but two separate FILE-based repo-root walks — `.vinaya/projects.md` (`src/lib/repo-state/read-root.ts`, in `apps/vinaya-studio/web` post-split) and `vinaya.config.json` (`src/lib/github-links.ts`'s `findRepoRoot()`, in `apps/vinaya-portal/web` post-split) — still defaulted to a bare `process.cwd()` with no override, so they silently resolved the installed package's own directory post-chdir instead of the guest repo (found live: Studio's Projects card read "No projects registered" against a repo with a real registry). `VINAYA_REPO_ROOT`, set in `spawnStandalone()` (`cli/src/commands/studio.ts`, the standalone repo) the same way `AEG_REPO` already is, closes the gap for both. This override matters only for that bundled-and-repointed-cwd case: the ordinary `next dev` case in either app resolves its walker from the real `process.cwd()` with no override needed, since neither app's own depth from the repo root changed when it split out of the original combined web app. (A third reader, `aeg-root/` itself, used to be a parallel cwd walk in `docs/load-aeg-docs.ts` — since attalabs deleted its local `aeg-root/` copy, that call site now imports `github-links.ts`'s `findAegRoot()`, which composes on `findRepoRoot()`'s own walk above rather than walking independently: `<repo root>/node_modules/@attalabs/vinaya/aeg-root`, the installed package's bundled doctrine. It inherits the same `VINAYA_REPO_ROOT` fix through that composition, with no override of its own needed.)

**`.vinaya/doc-owners` needed the same adopter-owned-content exemption `vinaya.config.json` already has.** `doctor`'s drift check and `upgrade`'s regeneration plan both diffed it byte-for-byte against the pristine empty starter — any real binding added after install read as drift, and `doctor`'s own warning recommended `vinaya upgrade`, which would have silently regenerated the file back to empty. Fixed in both `doctor.ts` and `upgrade.ts` with the identical `op.path === DOC_OWNERS_PATH` exemption `CONFIG_PATH` already carries.

**`quickstart`'s doc-owner/project prompts loop and validate now, not just once.** Bad input (an unparseable glob, or a doc pointer that doesn't exist on disk — a new check, since a typo like a bare number used to be written straight into `.vinaya/doc-owners` unchecked) offers a "Try again?" instead of silently skipping, and a successful bind/registration offers "Bind/Register another?" so a guest isn't limited to exactly one of each per run.

**The generated `pre-commit`/`pre-push` hooks could not pass their own first commit.** Both ran `check --all` unconditionally, and two registered checks — `closes-n`, `test-plan` — read the real PR body/number, which cannot exist yet at commit or push time on a fresh task branch: a bootstrap deadlock found live during a real dispatched task (`closes-n` failing with no PR to read a body from; `test-plan` failing on a `[principal]` box `roles/developer.md` forbids the Developer from ticking). `CheckSpec` gained `requiresOpenPr?: boolean` (`checks/contract.ts`, mirrored in `vinaya.config.json`'s `CheckEntrySchema` — same no-privileged-field discipline as `env`) and a new `--local` flag on `vinaya check` skips every check declaring it (`runner.ts`'s `RunOptions.localOnly`). The generated hooks pass `--local`; `vinaya-checks.yml` (CI, `pull_request`-triggered) does not, so both checks still run for real once a PR exists. The same live task also surfaced two smaller bugs, fixed alongside: `brief-shape`'s Test Plan checks (`checkTestPlanExclusivity`/`checkPrincipalPlaceholder`/`checkTestPlan`, `packages/aeg-core/src/brief-validation.ts`) scanned the whole PR body instead of the `AEG:TEST-PLAN` anchor `test-plan.ts` already honors, so a pasted reference-brief copy's checkboxes (the template's own instruction) could trip a false failure the real merge-gate check didn't share; and `doctor`'s hook-presence probe used a literal `join(repoRoot, '.git/hooks/…')`, which never resolves inside a linked worktree (`.git` there is a gitdir-pointer file, not a directory) even though the hooks fire correctly — `resolveManagedBlockPath` now resolves through `git rev-parse --git-common-dir`.

### `apps/vinaya-portal/web` and `apps/vinaya-studio/web` — the split web surface

**The renderer contract, stated as a rule:** *"Studio renders, it never re-derives."* The rule predates the split and binds both apps equally. Governance state enters either app through exactly two permitted paths — `@attalabs/aeg-core`'s public API, or a `StateSource`/`DoctrineSource` adapter from `@attalabs/vinaya-sources` (Portal only — Studio has no dependency on that package at all, see below) — an OR, not a hierarchy; do not "fix" an aeg-core-direct call site into a `StateSource` one on this rule's strength alone. Fetching facts (an HTTP call, a `gh` shell-out inside a `StateSource` adapter, inside `lib/forge`/`lib/repo-state`) is fine; **computing** a derived status, a dispatch verdict, or a diagram layout inside either app is the violation — the derivation must happen inside `aeg-core`, even if the I/O that feeds it happens in the app.

**`DiagramModel` is the one derivation, N consumers principle made concrete:** `deriveDiagramModel` (in `aeg-core`) turns doctrine + config + a live tranche into one renderer-agnostic model; Portal's `/docs/harness` and `/docs/reference`, and Studio's own dashboard, all draw from it, so none re-implements which gate guards which action. The same discipline extends to a gate/check node's `/docs` URL fragment: `nodeDocRoute`'s anchor is the node's display form (an internal doctrine code stripped, an over-length name cut at its first clause), computed once in `aeg-core`, never re-derived per renderer — and when that cleanup changes what a node's anchor used to be, `legacyAnchorSlugs` (also `aeg-core`) is the one place that knows its retired slugs, rendered by Portal as empty alias anchors so no `/docs` deep-link ever goes dead.

**`/docs` IA lives entirely in Portal now.** `/docs` itself is a bare `permanentRedirect` to `/docs/reference`, not a page — the 4-card hub that briefly lived there was removed (Principal decision 2026-08-09): the site TopBar's `Docs` entry is a `TopBarLinkGroup` (a `NavigationMenu` dropdown, not a link) whose five items — Harness, State Machine, CLI, Reference, Config — each carry a lucide icon and a one-line description, so the dropdown is now the only Docs entry point in the nav; the group's own trigger carries `ElectricLabel`'s active-state treatment via a `/docs` prefix match (every item lives under `/docs/*`), the panel items do not. The top-level nav itself (`(site)/layout.tsx`'s `links` array) reads Home, Lifecycle, Start, Docs, Compare, Studio, Roadmap — `Config` no longer sits as a flat top-level item, absorbed into the Docs dropdown instead. `/compare` is the evidence-first comparison page against the open-source market at or above a 25,000-star inclusion threshold (Superpowers, Spec Kit, OpenSpec, BMAD), sitting between the Docs dropdown and Studio in the nav. Its children split across two route groups under `apps/vinaya-portal/web/src/app/(site)/docs/`: `(with-sidebar)/` — `layout.tsx` (the `DocSidebarHost` shell), `[...slug]/` (the doctrine catch-all: roles/contracts/rings/actions/glossary), and `reference/` (the generated harness-map, formerly `/docs` itself) — versus `(standalone)/` — `harness/`, `state-machine/`, `cli/`, and `config/`. Config keeps its public `/docs/config` URL but owns a section rail of its own rather than inheriting `DocSidebarHost`'s doctrine tree — belonging under `/docs` is a navigation fact, not a layout one. That rail is `/docs/cli`'s shape with one deliberate divergence: `CliSidebar` drives active state from an `IntersectionObserver`, which reports only when a section's intersection *changes* and so sticks on the previous entry for the whole time a reader is inside a section taller than the viewport — true of `checks` here, not of any one command block there. Config's rail scans section positions on scroll instead, sharing one offset constant with `StickyDocHeader` so the rail and the sticky context line can never name different sections. The rail lists page sections only — the top-level `CONFIG_REFERENCE` keys plus the `check --plan --json` envelope section — while every key including nested fields keeps a stable `#config-<key>` anchor, resolved on arrival to the top-level section that owns it so a nested deep link highlights its parent rather than nothing. Static route directories take precedence over the `[...slug]` catch-all, so `harness`/`state-machine`/`cli`/`reference`/`config` can never collide with a doctrine slug (checked at dispatch time against `loadAegDocs()`'s `nav.flat`, which only ever emits `roles/*`, `contracts/*`, `actions`, `rings`, `rings/ring-*`, `glossary`). The pre-move paths (`/the-harness`, `/state-machine`, `/cli`, `/install`, and now `/config`) are permanent-redirect stubs pointing at their `/docs/*` equivalents — `/install` points straight at `/docs/cli`, never through an intermediate redirect.

**The `STAGES` chain (`apps/vinaya-portal/web/src/app/(site)/start/_lib/stages.ts`) models one tranche's linear task lifecycle, not every role — and is no longer rendered anywhere in the app.** It declares a single ordered Plan → Brief → Develop → Review → Archive → Wrap up chain, and `stages.test.ts` asserts it declares exactly the contract files on disk in the installed package's `aeg-root/contracts/`, modulo an explicit `CONTRACTS_MODELED_ELSEWHERE` set — a role whose contract describes a real edge the linear chain has no slot for. Two entries as of `@attalabs/vinaya` 0.19.0: `security-archivist.md` (Security is a parallel fan-in alongside Review → Archivist, not a sequential stage) and `architect-planner.md` (Architect is manually-invoked, above the tranche — it turns a goal into ordered tranche intents that Planner consumes, but Planner still starts the chain itself; Architect never cuts task Issues and isn't part of any one tranche's lifecycle). The seven per-stage `/start/*` routes (and their sidebar — `StartSidebar`/`StartSidebarHost`/`StagePage`/`start-nav.ts`) are deleted; `/start` itself is reduced to a bare redirect to `/start/quick`. `/life-cycle` was briefly built to absorb `STAGES` verbatim — `StageGlyph.tsx`'s diagrams and `LoopComposition.tsx`'s whole-harness loop were moved from `start/_components/` into `life-cycle/_components/` — but a later rework replaced that whole seven-stage/swimlane design with a three-altitude (Milestone/Tranche/Task) tab-switcher UI built on its own hand-authored content model (`lifecycle-content.ts`), and both moved files were then deleted outright rather than kept unreferenced. `STAGES`/`stages.ts` has had zero UI consumers since — a real open question for a future pass (retarget the drift test at `lifecycle-content.ts`, or decide `STAGES` is no longer canonical), not resolved by this note. The `start/layout.tsx` shell those deletions left behind is not a bare pass-through: it owns the section's content container (the sidebar deletion briefly shipped it as a pass-through, which rendered `/start/quick` with no page container at all — every other `(site)` page carries its own), pending a planned rebuild of the quickstart shell. `/start/quick` itself documents the full ownership arc rather than a four-step install: `quickstart` (the one command a reader types — the package-manager tabs run it, not bare `init`), `upgrade`, `doctrine` plus the three bundled skills, and `eject` — every command name, flag, and behavioral claim sourced from the installed `@attalabs/vinaya-sources` `COMMANDS` registry, each step deep-linking to `/docs/cli`'s `command-<name>` anchors.

**Studio's Docs link is now cross-app.** Every top-level item on both apps' TopBars carries an icon — Studio's via `src/lib/nav-icons.ts`'s `getAegNavIcon(slug)`, unchanged from before the split — but Studio's own "Docs" nav item, which used to be an in-app route to the same `web` process, is now an `external: true` `TopBarLink` pointing at Portal's production `/docs/reference` URL: same-origin routing stopped being available the moment the two surfaces became two apps.

**Portal's non-scroll-pinned landing sections share one shell.** `LandingSection` (`apps/vinaya-portal/web/src/app/(site)/_components/landing/LandingSection.tsx`) is the `<section><div mx-auto max-w-[73.75rem] px-6 sm:px-10 py-*></div></section>` wrapper every plain landing section renders through — a new section reaches for it rather than re-deriving the container by hand. `LifecycleSection` and `OwnershipSection` (scroll-pinned, sticky + `h-[300dvh]`) and the hero (full-bleed, no container) are the deliberate exceptions, not gaps to close. The site-wide footer is the real shared `@atta/ui/footer` `Footer` — not a Portal-local component — and `(site)/layout.tsx` constructs exactly one branded instance. `FooterGate` distributes that instance: ordinary and State Machine pages render it after the page at site level; sidebar docs, CLI, and Config consume it through `FooterContentSlot` inside their own content scroll pane; Harness stays footerless because its diagram fills the viewport. Nested layouts must consume that slot rather than construct a second footer or issue another CMS branding read. The docs-family shells (sidebar docs, CLI, Config, the Harness diagram) are `h-full` two-pane shells whose sidebar and content pane each scroll on their own; `h-full` only resolves because `SiteContentPad` — the `h-dvh overflow-y-auto` scroll container — wraps the route's children directly (`FooterGate` renders no DOM node of its own). Any wrapper element inserted between the two, or a second scroll container around `SiteContentPad`, turns that percentage height back into `auto` and collapses every docs shell into one page-level scroll.

**Home sells the lifecycle; each section makes one claim, and no two make the same one.** `LandingPage.tsx` composes, in order: hero, `LifecycleSection` (the tagline plus plan/solve/archive, i.e. how the loop works), `OwnershipSection` (what you get: readable issues, small PRs, your CI), `HarnessDiagramSection` (the "Your GitHub, perfectly structured" harness drawing, title and canvas only, a brand pause rather than an explanation), Three rings (the governance story, with a pointer to `/compare`), Who it's for (three personas), and the install end: One file, In/out with one command, Start. Arguments that already have a page stay on that page: the rules-file study and the enforcement-ratio number belong to `/compare`, and a tool catalog (tracker, method and agent badges) belongs to the docs. On Home that becomes one line under One file. A new or reworked section is judged against the one-claim criterion before anything else, and a section whose overline or core claim repeats another's is cut or trimmed rather than restyled. Adjacent sections also alternate backgrounds that visibly differ in both colour schemes, not merely different token names: in dark mode `--secondary` sits within a hair of `--card`, and in light mode `--card` sits within a hair of `--background`, so neither pair counts as a change. Home therefore alternates `bg-background` with `bg-secondary` (or `bg-secondary/70`), a step that reads in both schemes, and keeps `bg-card` off section backgrounds. Removing, adding or reordering a section means re-checking both of its new neighbours. **The landing never scrolls sideways, and a too-wide element is bounded where it is defined.** `SiteContentPad` sets only `overflow-y-auto`, so its `overflow-x` computes to `auto` and a row wider than the viewport makes the whole page pan sideways on a phone. While the hero builds, `hero-scene.js` briefly adds `overflow-hidden` to that same container as a scroll lock, so a check taken in that window sees the row clipped instead of scrollable. Either way, this is checked by measuring `main`'s `scrollWidth` against the viewport at `375px` and `768px`, not by looking for a scrollbar. A fix goes on the overflowing element itself — a `whitespace-nowrap` command given room to wrap inside its own card, a flex row allowed to wrap, a font size stepped down where a two-column grid halves the row — never an `overflow-x-hidden` on `main` or a section wrapper, which only hides the overflow.

**`LifecycleSection`'s tagline is pinned with the stage block, not above it.** The "A harness for your software engineering process" tagline is not a separate landing section. It is the top of the one `sticky top-14` block (pinned under the fixed TopBar, which would otherwise cover it) inside `LifecycleSection`'s own `<section ref={sectionRef} id='what-it-is'>`, rendered as a full-bleed `bg-secondary` banner that carries `id='tagline'`, the hero's scroll target. The "Plan, solve, archive" row, the tabs and the stage track sit below it in the same block, so the tagline stays fixed at the top of the viewport for the whole tab scroll-through. The `min-[700px]:h-[300dvh]` runway is on the section itself. Nothing unpinned comes before the block, so `progress` starts at the moment the pin engages, and `travel` is the section height less one viewport, with nothing to subtract. The tagline is not a `LandingSection`, because that shell is for non-pinned sections. The pinned block is a fixed `100dvh-3.5rem` tall (the viewport below the bar) with `overflow-hidden`, so any height added to the tagline banner comes out of the stage track's room. Re-check that the stage cards still fit at a short desktop viewport before growing it. Don't give the tagline its own separate `sticky`: two sibling pins need a hardcoded offset between them, and one block needs none.

**`/life-cycle`'s altitude switcher is a sticky sub-bar, and an altitude change scrolls to a measured target.** `LifeCycleSwitcher` is a full-width `ChromeFrame variant='bar'` inside a `sticky top-0` wrapper at the top of the panels section. It pins directly under the fixed TopBar with no TopBar slot, because `SiteContentPad` carries the bar-height `pt-14` and sticky insets resolve inside that padding. `sticky` sits on the wrapper, not on `ChromeFrame`, because retro's bar puts its `className` on an inner card. Every altitude change (a tab, or a panel's handoff button) goes through `LifeCycleExperience.handleChange`. After the new panel commits, `_lib/scroll-to-panel-start.ts` scrolls the scroll container (smoothly, or instantly under `prefers-reduced-motion: reduce`) so the panel's first `LandingSection` (reached through its `ref`) lands flush under the bar. It measures the container padding, the switcher's `top` and the switcher's height at scroll time, and hardcodes no pixel offset. A scroll to the switcher itself is a no-op while it is stuck, which is why the target is the section. The panel's enter animation is fade-only: a `translate` would move the measured section box away from its layout position while the animation runs.

**`/life-cycle`'s hero is the repo's first WebGL surface, and sets the mount/dispose precedent for the next one.** The scene is a plain three.js module (`apps/vinaya-portal/web/src/app/(site)/life-cycle/_lib/lifecycle-scene.js`) exporting one factory that takes its DOM as arguments and returns a `dispose()`; a client component mounts it from a `useEffect` and tears it down on cleanup. `three` is a dependency of Portal alone, core module only — no addons — and is reached by a dynamic `import()` inside that effect, so it stays out of the SSR module graph and out of the route's initial chunk. The landing hero (`(site)/_components/hero-canvas/hero-scene.js`, mounted by `VinayaHeroEmblem.tsx`) is the second, built from the identical factory shape — one exported `mountHeroScene({ canvas, root, labelClass, onReady })` returning `{ dispose, applyTheme }`. A second three.js surface has five constraints to satisfy, each of which is a real failure mode rather than a preference:

- **Every `document`/`window`/`getComputedStyle` read lives inside the factory.** One surviving module-scope DOM read compiles green and runs fine under `next dev`, then throws only in the production build, under SSR — the dev server gives no signal at all.
- **`dispose()` is mandatory, not defensive.** App Router remounts on client navigation and React 18 StrictMode double-invokes effects in dev; without teardown a visit leaves behind a second renderer, a second rAF loop, and a duplicated label layer. Teardown must cancel the frame, disconnect every observer, remove every listener, dispose the renderer plus every geometry/material/texture, and empty any DOM layer the scene created.
- **The window is not the viewport in this app.** `(site)/layout.tsx` renders the TopBar `fixed` (out of flow, inside `TopBarChromeHost`) over one `h-dvh overflow-y-auto` scroll container, `SiteContentPad` — which also carries the `pt-14` clearing the bar on every route except landing, so a `sticky top-0` pins just under the bar there and at the true page top on landing — so `window.scrollY` is permanently `0` here and any document-scroll progress value never moves. Scroll progress comes from the pinned section's own `getBoundingClientRect()`, and the renderer size, camera aspect and label projection come from the canvas box, not `innerWidth`/`innerHeight` — a canvas that does not fill the window otherwise projects its overlay text off by the TopBar's height. The sticky pane matching that scroll region is `h-[calc(100dvh-4.5rem)]`, the same constant `LifecycleSection`/`OwnershipSection` already pin against.
- **The hero's scroll-progress camera value is damped, not read raw.** `progress()` (`hero-scene.js`) returns `-track.top / (track.height - hero.clientHeight)` — a fraction whose denominator is viewport-height-relative (`320vh` track over an `h-dvh` hero) while its numerator, the scrolled distance in pixels, is not. At any nonzero scroll offset into the hero's pin range, a window resize changes that denominator (and so the fraction) the instant layout recomputes. The per-frame loop chases this raw value with an exponentially-damped `pSmooth` (`0.2` per frame) before deriving the camera's tilt/elevation/distance from it, so a step in the input becomes a few frames of motion instead of a same-frame snap. The scroll-locked build phase and `prefers-reduced-motion` both bypass the damping and snap straight to their exact target (`0`/`1`): the build lock must hold exactly `0`, and reduced-motion must not gain new motion from the smoothing itself. This is a real smoothness improvement, not the fix for the resize flicker below — it has nothing to smooth at scroll position zero, where that flicker reproduced too.
- **The hero's actual `renderer.setSize()` call is deferred to the render loop, never run straight from the `ResizeObserver`.** A live window drag delivers far more resize notifications than the hero renders frames — every intermediate size the browser lays out, not one per vsync. `renderer.setSize()` reallocates the WebGL drawing buffer (and, at this canvas's `antialias`+`devicePixelRatio`, its multisample renderbuffers) — not free — and a canvas's backing buffer is spec-cleared to transparent the moment its `width`/`height` changes, staying that way until the next draw lands. Calling `setSize()` synchronously from the observer let a burst of notifications run several reallocations back to back with no `render()` call landing in between, holding the canvas on that cleared frame for the whole burst — the harness and fabric visibly vanishing, then snapping back once the drag paused and a render finally reached the screen. The observer callback only sets a `resizePending` flag; `frame()` consumes it (and calls the real `resize()`) as the very first thing it does, before anything else in the frame and always immediately followed later in the same tick by `renderer.render()` — so `setSize()` runs at most once per rendered frame and a cleared-but-unpainted frame can never reach the screen. Reproduces (and was fixed against) purely from resize timing, independent of scroll position — confirmed by resizing at scroll `0`, where the scroll-progress-damping bullet above has nothing to do.
- **Tailwind cannot see a `.js` scene module.** `packages/ui/styles/globals.css`'s `@source` globs cover `.ts`/`.tsx` only, so a utility class string written inside the scene generates no CSS and the element renders unstyled with no error. Class strings for DOM the scene creates itself are authored in the `.tsx` component and passed into the factory.
- **No colour, and no font family, is written into the scene.** Both resolve from CSS custom properties at runtime. Token resolution needs a hidden-`<span>` fallback as well as canvas `fillStyle`, because a custom property comes back as authored and `fillStyle` silently ignores `oklch()` — leaving the previous colour with nothing thrown. A `MutationObserver` on `documentElement` re-reads the tokens and repaints on a theme switch; a reload is not an acceptable substitute.
- **A token that can't be read yet is a state to wait out, never a throw.** Inside the admin preview frame (`/?preview=true`) the theme arrives by `postMessage` after mount, and the CMS writes every achromatic colour with a `none` hue (`oklch(1 0 none)`), which the parser must read as 0. The landing hero's `mountHeroScene` holds off starting until its whole palette reads, and its retheme keeps the current palette when a read fails mid-swap. The no-literal-colour rule stands, so the fallback is waiting, never a hardcoded colour.

**`/life-cycle`'s hero reads from one reading-focus partition, and never blanks what is being read.** Three rules in `lifecycle-scene.js` hold it legible in both scroll directions:

- **One partition drives every "which altitude" signal.** Labels, the caption card, the rail, the readout and the morphing word all come from `HANDOFF` (the midpoints of the camera's two eased legs). The camera bands (`band()`, `wM`/`wT`/`wK`) still drive scene *contrast* only. Gating labels off those bands left two scroll ranges where no altitude's labels or card could be read.
- **Labels hand off with an overlap, and every weight is a pure function of scroll progress.** The arriving altitude's labels reach full opacity before the leaving altitude's begin to fade, so reversing the scroll replays the same frames. The caption cards share one spot, so they cannot overlap-fade. Instead the outgoing card fades out before the incoming one starts (its `data-on` transition in `LifeCycleHero3D.tsx`), and a small hysteresis band stops a reader who rests on a boundary from seeing the card flicker.
- **The task's run is driven by scroll, not a clock.** The branch draws itself stage by stage across a scroll window (`TASK_P`) through to the Merged chip, and undraws on the way back up, so a fast scroller lands on the same frame as a slow one. Stage labels hold a floor opacity, so the words are there to read before their stage is drawn.
- **Each altitude arrives early and holds, and the task view zooms in on the branch.** Scroll progress is remapped onto the camera (`CAM_LEGS`): each leg runs over a window and the view parks between them. The last leg blends into a frame fitted to the branch itself, from the first stage to the chip, in the free region beside or above the caption card. A narrow window starts that frame at develop instead, trading the lane's start for size, never the merged end. The page title stays in the DOM header for the whole descent; the zoomed task view has no room for an in-drawing copy.

Under `prefers-reduced-motion` the hero is one composed frame, not a scroll runway. The section collapses to the pane. The camera is fitted once per resize to the whole graph from a direction between the tranche and task altitudes. All labels and all three captions show at once: a row overlaying the pane's foot on `lg`+, which the fit stops above, and in flow below the pane under `lg`. A one-shot pass then pushes apart any labels the smaller frame made collide. Nothing in that frame reads scroll, time or the pointer.

**The landing hero's fabric is one even layer of hairlines.** `hero-canvas/field-3d.js` draws its own grid; it doesn't use `packages/ui/canvas/bg/fabric.ts`. The double grid (coarse mesh on every second vertex row/column, fine mesh in between) is one `LineSegments` with one material at one opacity (`--hero-fabric-alpha` in `hero-core.css`), so every line and square looks the same. A fainter fine material made two kinds of lines. The material stencil-tests (`NotEqual`/`Replace`, with the renderer created with `stencil: true` in `hero-scene.js`), so each pixel takes the fabric ink at most once per frame. `LineSegments` blends every segment on its own, which doubled the ink at every vertex and row×column crossing into bright dots that crawled with the shimmer. Keep the lines 1 device px and the density as they are; don't split the grid back into separately blended meshes. The lines lie exactly on the opaque `fabric-surface` sheet (same vertices), and `polygonOffset(1, 1)` on the sheet is only one depth step. Real GPUs rasterise line depth differently from triangle depth, so the sheet hid the lines in blotchy patches that crept with the shimmer. The line material's vertex shader therefore pulls each line's depth, not its screen position, toward the eye by `LINE_DEPTH_PULL` (0.2% of its distance). SwiftShader has exact depth and never shows the fight, so test it adversarially: pull the sheet forward (`polygonOffsetUnits: -4`) and every line must survive.

**The landing hero drives the persisted topbar's lockup; its lifecycle is a layout effect.** There is one wordmark in the DOM, the topbar's `HeroLockup` inside the persisted `(site)/layout.tsx`, and the landing hero only writes inline styles onto it (`hero-canvas/lockup-flip.js`'s `attachLockupFlip`, wired through `hero-lockup-context.tsx`). `VinayaHeroEmblem.tsx` attaches that loop from a `useLayoutEffect`, and `attachLockupFlip` writes its first frame synchronously before returning, so the hero-scale transform exists before the browser paints and the lockup is revealed in that same pre-paint pass. A passive `useEffect` or a reveal deferred to a `requestAnimationFrame` paints one frame of the small, un-transformed wordmark first. The SSR'd HTML of a hard reload is painted before any JS runs, and that window is covered by CSS: `data-bare="true"` on landing hides the lockup via `[[data-bare=true]_&]:opacity-0`. Because the lockup outlives the hero, the effect's cleanup must undo as well as stop. Cancelling the rAF loop leaves the last frame's inline `transform`/`opacity`/`marginTop`/`width` (and `data-bare`) on the shared nodes, which shows up as a frozen fragment on the next route. So cleanup calls `resetLockup`, which clears every inline write back to the CSS rest state. Don't move the lockup into the page to escape this: it's in the layout so it persists across routes.

**`/roadmap`'s card artwork is each milestone's own CMS SVG, sanitized on the server and inlined.** `page.tsx` (a Server Component) resolves every card's artwork through `_lib/resolve-artwork.ts` — fetch the CMS `image` asset, detect SVG by `content-type`, sanitize with `_lib/sanitize-svg.ts` — and hands the client `DeploymentTrack` only the resulting markup, so the sanitizer never ships to the browser and the client never fetches. The markup is inlined, never an `<img>`, because only inline SVG reads the theme tokens and runs `marks-motion.css`'s `mm-*` keyframes. There is no repo-local copy of any mark, no version-keyed lookup and no SVGR build rule: which artwork a card shows is its own CMS document's decision (the full content rule is in `.claude/skills/ui-cms-theme/SKILL.md`'s roadmap section). The sanitizer is `isomorphic-dompurify` under its SVG profile plus a hook that closes what DOMPurify leaves open inside CSS: `<style>` is forbidden (an inlined SVG `<style>` would style the whole page); `class` is reduced to `mm`/`mm-*` tokens and every `id` is dropped (a site utility class such as `fixed inset-0` would pull a mark out of its card); inline `style` keeps only the marks' motion declarations (`animation*`, `transform-box`, `transform-origin`, `opacity`, `--mm-*`) with plain values, so no `url()`/`image-set()`/escape and no layout property survives; and every `href`/`xlink:href`/presentation-attribute `url(...)` must be a same-document `#fragment`. A new mark that relies on any other class, id or style declaration loses it silently — theme through presentation attributes (`fill="var(--primary, currentColor)"`), never `style`. The fetch itself only ever goes to `https://cdn.sanity.io/images/…` on the default port, with redirects refused, a timeout and a size cap; `sanitize-svg.test.ts` pins both halves — a hostile SVG neutralized, a real mark keeping its root `class="mm"` (the reduced-motion rule's selector), inline `animation`/`--mm-d` styles, `viewBox`, `pathLength` and `stroke-dasharray`. Loosening the sanitizer config is a security change, not a styling one.

**Public docs link to public docs, not the private implementation repository.** Role, contract, ring, action, and Harness leaf surfaces retain their model-derived in-app routes and anchors, but expose no `atta-labs/vinaya` blob link or source-code affordance. The installed package remains the server-side doctrine input; repository visibility is not part of the reader contract.

**Route inventory and status** are not centrally tracked in a spec today — neither Portal nor Studio has its own `specs/` directory yet (each gets one when someone needs it, a separate, later decision). Read the route source directly (`apps/vinaya-portal/web/src/app/(site)/`, `apps/vinaya-studio/web/src/app/studio/`) for what's live.

**Studio's own nav is a persistent `Sidebar*` shell, not a TopBar-plus-per-route-sub-bar stack.** `studio/layout.tsx` (an async Server Component) fetches CMS branding, the project list (`listProjectViews`), and a small `StudioRepoFooter` fact bundle (resolved repo via `resolveRepo`, the current git branch, the installed `@attalabs/vinaya` version), then renders `StudioShell`, which composes `StudioSidebarHost` (`_components/StudioSidebar.tsx`, `'use client'`) next to the one scrollable content pane — the same client/server split `apps/vinaya-portal/web`'s `DocSidebar`/`DocSidebarHost` established, cited here as the precedent it followed. A fixed rail renders at `lg`+; below that, a `ChromeFrame variant='bar'` strip opens the same nav body in a `Sheet` drawer. `StudioSidebarHost`'s `SidebarFooter` block — repo, branch, version — sits outside `SidebarContent`'s own scroll region, so it stays visible without scrolling regardless of how many projects/nav items overflow the rail; a `null` `resolveRepo()` renders "no repository resolved" there instead of throwing. The `ProjectsSubBar` sticky in-page tab strip this replaced is gone outright — the "Projects" nav item now expands to per-project children directly in the sidebar — and the padding-counterweight trio it required across `StudioShell`/`ProjectsSubBar`/`projects/layout.tsx` goes with it. One divergence worth knowing before extending this: Studio is pinned to the `retro` library (`ui-library-pins.ts`), whose native `SidebarMenuSubButton` has no `render`-prop shim (only `SidebarMenuButton` got one, in `interactive/sidebar-menu-button.tsx`) — a per-project child link uses `asChild` instead, not `render`.

**No production/preview gate in Studio.** Before the split, `web/src/lib/env.ts`'s `isVercelDeploy()` (gated on `VERCEL_ENV` presence, not equality to `'production'`, so preview deploys were covered too) sent a deployed visitor from every `/studio/*` route to a Portal marketing page, and `ProductSwitch.tsx` gated a Portal↔Studio toggle on the same check plus forge-reachability. `apps/vinaya-studio/web` carries neither: it is never deployed, so there is nothing to gate against and no second product to switch to from inside it. The original combined web app, which carried both, was deleted once this split proved out (task 4, #886).

**`LabelBadge.tsx` is the one place Studio styles an Issue's label vocabulary.** `apps/vinaya-studio/web/src/app/studio/_components/LabelBadge.tsx` derives a `LabelKind` (`project | tier | type | state | needs | flag | other`) from the code-owned `@attalabs/aeg-forge-state/labels` vocabulary — never from a hand-written prefix check, so the component stays correct across a namespace rename. Colour is keyed to a label's CATEGORY, never its value: one flat semantic-token variant per family (`tier` → `text-foreground border-border`, `type` → `text-muted-foreground border-border`, `needs` → `warning`, `flag` → `destructive`, `project`/`state` → `primary`) — the doctrine forbids a per-value palette, and there is no `info`/blue token (`.claude/skills/ui-theme-tokens/SKILL.md`). `project` is not a label kind despite appearing in `LabelKind`: a project name comes from the Issue body's `**Project:**` field, not a label — `KIND_CLASS.project` exists only for `ProjectBadge`, a visually-matched sibling component, never reached through `labelKind()`. `splitLabels()` partitions an Issue's labels into the families `BacklogTable.tsx` renders (`{ tier, type, flags }`) — `type`, the commit-type shape of the work (`vinaya/type:feat`, `vinaya/type:fix`, …), shares the Tier column (labelled "Tier / Type") rather than getting a new one, since the two are both classification facts about what the Issue IS, distinct from the state/flag/needs "needs attention" family, and the table's `table-fixed` column-width budget is already fully allocated. The module is reached from a `'use client'` module (`BacklogTable.tsx`), which is why it imports `@attalabs/aeg-forge-state/labels` by SUBPATH and never the package barrel: the barrel re-exports `gh.ts`'s `node:child_process`, which Turbopack cannot bundle for the browser.

**`fetch-token-ledger.ts` carries the same verdict-author verification `review-gate` does.** `apps/vinaya-studio/web/src/lib/forge/fetch-token-ledger.ts` maps each merged PR's comments into `@attalabs/aeg-core`'s `TokenSourcePr` shape and calls `aggregateTaskTokenRows`. Since `@attalabs/aeg-core` 0.23.0, a `TokenSourcePr` comment carries `{ body, author }` rather than a bare string, and `aggregateTaskTokenRows` takes a required `principalAllowlist: string[]` — a `Tokens: …` line in a PR comment counts toward the ledger only when an allowlisted principal posted it, mirroring `review-gate`'s own verdict-author check (above). The GraphQL query fetches each comment's `author { login }` alongside its body, and the caller passes `@attalabs/aeg-core`'s exported `PRINCIPAL_ALLOWLIST`, not this repo's `vinaya.config.json` `"principals"` override. That override (`["daniboomerang"]`) is read by the `review-gate` and waiver-label check bins through `loadTrustAnchorConfig()` (above), never by this Studio caller. It names the same single login `PRINCIPAL_ALLOWLIST` hardcodes, so the ledger and `review-gate` trust the same principal today, but an edit to `principals` does not reach the ledger until this caller reads the config itself. As a merge control, `principals` still depends on branch protection requiring the Vinaya check (see "Say plainly what the gate is and is not", above).

**The tranche page's forge-heavy load path is a local, stale-while-revalidate store — the page's own `dynamic = 'force-dynamic'` still means what it always meant.** `apps/vinaya-studio/web/src/lib/forge/tranche-page-snapshot.ts`'s `loadTranchePageData` is the single entry point `studio/projects/[name]/tranches/[slug]/page.tsx` now calls instead of invoking `readTranche`/`loadTrancheSnapshot`/`loadDispatchReadiness`/`fetchTrancheTokenLedger` directly on every request — those four are still called, just from inside this module, and only when the store has nothing fresh to serve. `disk-cache.ts` is the storage primitive: a JSON file per `owner/repo/slug` under the OS cache dir (`$XDG_CACHE_HOME` or `~/.cache/vinaya-studio`) — outside the repo tree, so it is never committed and never read by the CLI — with a `Map`-aware replacer/reviver, since `ForgeFacts`/`LedgerRow[]`/`DispatchResult` all live in `Map`s a bare `JSON.stringify` would silently flatten. A request within the (one-minute) TTL reads the file and returns with zero forge calls; a request past TTL still returns the stale entry immediately but kicks an unawaited background refresh that overwrites the file once it finishes — the *next* load sees the update, not the request that triggered it. `refresh-snapshot-action.ts`'s `refreshTrancheSnapshotAction` is a `'use server'` function bound directly into a `<form action={...}>` in the page itself (a Server Component, so no client component is needed for this one button) — it forces the same background refresh regardless of TTL and returns immediately, never blocking the click on the tens of seconds a full derivation can take. The refresh is scheduled via `after()` (`next/server`), not a bare `void`-called promise: a `void forceRefresh(slug)` sitting next to `revalidatePath` in the same action body was empirically still tying the detached promise to the action's own response lifecycle (found live — the button blocked for the full ~13.7s derivation), so `after()` is what actually gets the work outside that lifecycle. This is why `force-dynamic`'s own comment ("never serve from cache") still holds: the Next-level route cache stays fully disabled, and the correctness guard against a silently-stale answer is the page's visible "snapshot from HH:MM" line plus the refresh button, not a cache Next itself would ever know about. `timing.ts`'s `timeCall` wraps each of the five reads (including `resolveProjectView`) and prints `[timing] <label>: <ms>ms` in dev only. `resolveProjectView` is deliberately outside the cached bundle, but "no forge call" for it is true only in a registry-present repo (a `.vinaya/projects.md` file resolves): in a registry-absent repo it falls through to `forgeDerivedProjectNames()`, which lists and derives every tranche from the forge on every call, memoized only per-request (React's `cache()`) — so a registry-absent repo still takes a real forge hit on every tranche-page load, warm or not. This PR's O2 guarantee ("no forge call on warm load") is scoped to registry-present repos; closing the registry-absent gap is a follow-up, not yet done.

**A missing `.vinaya/projects.md` is a normal state, not an error.** `src/lib/repo-state/read-root.ts`'s `findAegRoot()` (present in both `apps/vinaya-portal/web` — as `github-links.ts`'s sibling walk — and `apps/vinaya-studio/web`) walks up from `process.env.VINAYA_REPO_ROOT ?? process.cwd()` for the file and returns `null` (never throws) when it isn't found — a single-project repo legitimately has no registry at all. Every caller (`readRegistry`, the legacy `completed/*.md` archived-tranche supplement, Studio's `api/coherence/route.ts`) treats `null` the same way this file already treats `resolveRepo() === null` everywhere else: a safe empty default, not a crash. That same route's spawned subprocess (the coherence oracle bin) resolves from the registry `node_modules/@attalabs/aeg-core/bin/verify-coherence.ts` — the attalabs-adoption tranche deletes the local `packages/aeg-core` copy it used to shell out to.

**Board routing is registry-optional, not registry-gated (#811).** `boardHref`/`trancheHref` (`apps/vinaya-studio/web/src/app/studio/_lib/tranche-href.ts`) take a third argument, `registered: ReadonlySet<string> | null` — a real `Set` (registry present) keeps the original rule byte-for-byte: link the first project name that has a `.vinaya/projects.md` row, `null` (no such row for any declared name, or none declared at all) when it doesn't — `NO_BOARD_REASON` is that null case's honest, still-deliberate non-clickable render, unchanged. `null` for the whole argument means no registry exists at all: there is nothing to gate against, so every name a tranche declares gets a board, and a projectless tranche gets the one reserved `DEFAULT_BOARD_SLUG` (`_default`) board instead of `NO_BOARD_REASON` — a view over every projectless tranche, not a real project (no `project:default` label minted, nothing written to the forge). `read-root.ts`'s `resolveProjectView`/`listProjectViews` are the registry-optional counterparts to `readProject`/`readRegistry`, switching mode on `findAegRoot() !== null` exactly like this section's own null-tolerance already does — and, per renderer-never-derives, resolving a forge-derived name only from `task.projects` the tranches already carry, never re-deriving one. A forge-derived name becomes a URL segment via `forgeProjectSegment` (percent-encoding), so a name that isn't slug-safe still renders instead of 500ing.

**Studio's own app sits three hops up from the repo root** (`apps/<name>/web`), so the ordinary `next dev` case resolves the repo root with no `VINAYA_REPO_ROOT` override — that override exists for the standalone-bundled-CLI case described below, where `process.chdir` runs before any request does. Studio still carries no `tracing-markers.test.ts` guard (that mechanism watches computed-path reads specifically, and Studio's `read-root.ts` walk needs no tracing help — it always runs against the real filesystem, `next dev` or a local `next build && next start`), but it does now declare one `outputFileTracingIncludes` entry: `output: 'standalone'` runs Next's static-import file tracer regardless of Vercel deploy status, and `vinaya-studio-artifact.yml` builds exactly that standalone output and ships it inside the published `@attalabs/vinaya` npm package (`studio-standalone/`) for every adopter's `vinaya studio`. `api/coherence/route.ts` spawns its oracle bin (`node_modules/@attalabs/aeg-core/bin/verify-coherence.ts`) via a raw `execFile` path, never a static `import` — invisible to the tracer, so the shipped bundle silently dropped the file even with `@attalabs/aeg-core` declared as a real `dependencies` entry. Found live: a fresh adopter install's `vinaya studio` threw "Module not found" on that exact path, never reproduced locally because dev/build-from-source always has the real `node_modules` tree. `outputFileTracingIncludes: { '/api/coherence': ['../../../node_modules/@attalabs/aeg-core/bin/verify-coherence.ts'] }` closes the gap; the route also `existsSync`-guards the spawn so a genuinely missing oracle returns a clear `oracleError` instead of bun's raw crash text.

**`VINAYA.md`'s pointer names the doctrine's own front door, not just its categories.** `doctrinePointer()` (`cli/src/lib/artifacts.ts`) previously described the doctrine only in prose ("roles, contracts, the state machine, the ring gates") without naming a specific first file to open — a cold agent had to discover `aeg-root/skills/aeg/SKILL.md` exists on its own. The generated text now names it directly, resolved relative to `doctrineRoot` (the installed package's own bundled `aeg-root`) the same way the function's existing "read the doctrine text" path already is — a pointer, not a restatement of what that file says.

## Rules

### Every command's identity lives in ONE registry

Never hand-write a second command list (in `printHelp()`, in a web page, in a doc) — read from or extend the published `@attalabs/vinaya-sources`' `COMMANDS`, in `atta-labs/vinaya`.

### `CheckSpec` carries no privileged field

A core check and a config-registered custom check are indistinguishable to the runner. A new core check must be addable by an adopter through the public grammar — if it needs a field a custom check couldn't also declare, that is a design gap to escalate, not a quiet exception.

### Repo-root resolution is a deployment input, not just a lookup — for a deployed app

Any route or check **in a deployed app** (`apps/vinaya-portal/web`) that locates the repo by walking up for a marker file (`vinaya.config.json`, `.vinaya/projects.md`) must have that marker declared in the serverless host's file-tracing config, or the walk fails silently at runtime with a green build. Introducing a new marker-walking reader is a two-place change (the walk itself + the tracing declaration) — this exact gap has left doctrine routes returning production-only 500s twice, both times traced to a marker that built green locally and was simply never declared. `apps/vinaya-studio/web` is the deliberate exception: it is never deployed, so it declares no tracing config for its one marker-walking reader (`read-root.ts`'s `findAegRoot()`) at all — there is no serverless bundle for the walk to fail inside.

Portal's doctrine routes render static/ISR, not `force-dynamic`, as of task 3 (`#916`) — the walk still happens on the deployed lambda, just at build/ISR-regeneration time rather than on every request, so an undeclared marker still builds green and fails only there. See `apps/vinaya-portal/web/README.md`'s "Rendering mode" section for what unlocked that (removing `@atta/ui`'s `NextWebShell` cookie read, not an experimental Next feature).

### The `files` allowlist is the real ship boundary — not what exists in the CLI's own repo

Something existing on disk in the standalone `atta-labs/vinaya` repo's `cli/` source tree does not mean it reaches an adopter. Before assuming a bin/script/asset is available post-install, check that repo's `package.json` `files` field and `cli/src/lib/artifacts.ts`, not just the source tree.

## Anti-patterns

- ❌ Portal or Studio importing anything from `cli/src` (or vice versa) — mechanically caught by each app's own import-boundary test, but know the rule before writing the import.
- ❌ Computing a derived status, a dispatch verdict, or graph layout logic inside Portal or Studio — that is `aeg-core`'s job; both apps only fetch and render.
- ❌ Adding `@attalabs/vinaya-sources` to Studio's `package.json` or its `transpilePackages` "for symmetry with Portal" — Studio has zero imports of it, so this buys nothing and couples Studio to the package's release cadence.
- ❌ Adding a second command-list literal instead of extending `COMMANDS`.
- ❌ A `CheckSpec` field or behavior only a core check can use — breaks the no-privileged-API invariant `tests/checks/no-privileged-api.test.ts` exists to prove.
- ❌ A check reading `process.env` directly with no `env` declared on its `CheckSpec` — the allowlist is enforced, so such a read is invisible to the child process, and `vinaya doctor`'s permanent missing-declaration diagnostic flags the missing declaration.
- ❌ Hardcoding this monorepo's own paths/product names into anything meant to ship in the `@attalabs/vinaya` tarball — the same portability discipline `aeg-core`/`aeg-forge-state` follow applies here, since this workspace is what actually ships.
- ❌ Assuming a design chapter in `atta-labs/vinaya` (e.g. the configurability architecture) is fully built because it's documented there — check its own Correction/Status notes; several land in stages across multiple minors.
