# Atta Coordination — How to Work With This System

**This file lives in Claude.ai project knowledge.**
**Every Claude agent reads this at session start.**

Dani works with multiple Claude agents simultaneously across Desktop, Web, and Claude Code. This file is the coordination contract that keeps them in sync.

---

## The two-layer model

**Repo** = code, technical specs, skills, design docs. Git-tracked. Long-lived. Changes are commits.

**Project knowledge** = operational coordination state. Updated dynamically as work progresses. Synced across all of Dani's Claude sessions.

These are NOT mirror copies of each other. They serve different purposes.

### What lives in project knowledge (4 files only)

| File | Purpose | Update cadence |
|------|---------|----------------|
| `atta-coordination.md` | This file. Names, rules, how to work. | Rare (when system changes) |
| `atta-current-state.md` | What's true right now across the ecosystem. | Whenever state changes |
| `atta-plan.md` | What's being worked on, what's next, what's blocked. | Frequently (any session can update) |
| `docs-index.md` | Discovery map of repo content. Auto-generated by `bun docs:index`. | When repo files added/removed/renamed |

### What lives in the repo

Everything else. All skills (`.claude/skills/*/SKILL.md`), all specs (`apps/*/specs/*.md`), root docs, `docs-index.md` source. The index lists where things are; ask Dani to paste content by path when needed.

## Session start protocol

Every session, every Claude agent:

1. **Read all 4 project-knowledge files** (this file, current-state, plan, index)
2. **Ask Dani which product is in scope:**
   *"Which product are we working on today? Vāda, Vitakka, Sati, Cetana, Herald, or general Atta ecosystem work?"*
3. **Once scope is named, BEFORE answering anything substantive, scan `docs-index.md` for every spec under that product and list them back to Dani:**
   *"For Vitakka, the index shows: `apps/vitakka-ai/specs/vitakka-spec.md`, `apps/vitakka-ai/specs/vitakka-human.md`. I haven't read these. Paste them, or confirm they're not relevant to today's question, before I respond."*
4. **Do not generate strategy, briefs, or recommendations until either (a) the relevant specs have been pasted, or (b) Dani has explicitly confirmed they're not needed for this session's question.**
5. **Wait** for Dani's question.

When Claude needs content from a repo file mid-session, Claude asks Dani by exact path:
> *"I need to read `apps/vada-ai/specs/vada-decisions.md` — can you paste the content?"*

**Tooling note (May 7-8, 2026):** GitHub's hosted MCP server is connected to Claude.ai via OAuth (`api.githubcopilot.com/mcp/`). In **fresh** Claude.ai conversations, Claude may have direct read access to `daniboomerang/atta.ai` via tools like `Get file or directory contents`, `List branches`, `List commits`, `Search code`, `Search repositories`. MCP connectors only surface in the tool registry at conversation start, so connections made mid-conversation are not available until the next session begins. When repo access is available, prefer it over paste-back loops; when it's not, fall back to asking Dani by exact path. Self-hosted MCP servers with bearer-token auth (e.g., Vāda's own hosted MCP) currently fail through Claude.ai's connector broker — workaround is Claude Code CLI which works today.

Claude does not pretend to have read content it doesn't have. The index is for discovery, not for content.

### Hard rule — the spec-check gate

If Dani asks a strategic, architectural, or product-shape question about a named product, and Claude has not read the specs for that product, Claude STOPS and asks for them. No "thinking out loud first." No "let me draft something we can react to." No reviewer briefs. The specs come first.

Violations of this rule waste hours. The cost of asking is 30 seconds. The cost of skipping is a session of misaligned reasoning.

## Coordination rules — how to keep sessions in sync

### When state changes, update `atta-current-state.md`

State changes include:
- A Vāda phase advances (e.g., 7.3 → 7.4)
- Auth migration starts or completes
- DNS gets configured
- A new app is scaffolded
- Stale-doc list changes (something got updated, something else got created)
- Domain configuration shifts
- Any "what's true right now" fact changes

Claude updates `atta-current-state.md` in project knowledge before the session ends. Dani re-uploads if needed.

### When the plan changes, update `atta-plan.md`

Plan changes include:
- A new sub-feature surfaces during work
- Priorities shift between phases
- A blocker is discovered
- A phase is split or merged
- Sequencing changes
- Something completes (move from "next" to "done")

Any Claude agent can update the plan during a working session. Update before session ends.

### When repo structure changes, regenerate `docs-index.md`

Run `bun docs:index` in the repo. Re-upload `docs-index.md` to project knowledge.

This happens when files are added, removed, or renamed. Content changes within existing files do NOT require regeneration.

### When this file or system rules change, update `atta-coordination.md`

Rare. Only when the coordination model itself shifts.

## Anti-patterns

- ❌ Putting tactical day-to-day plans in repo specs (creates commit churn)
- ❌ Putting technical architecture docs in project knowledge (loses version history)
- ❌ Updating one without the other when both should change (e.g., advancing Vāda phase in `atta-current-state.md` but not reflecting it in `atta-plan.md`)
- ❌ Pretending to have read a repo doc that's not in project knowledge — always ask Dani by path (or use GitHub MCP if available in this session)
- ❌ Renaming `@atta/*` packages to `@attalabs/*` — code namespace is Atta, AttaLabs is only the public URL
- ❌ Treating Atta as a product — it's the ecosystem only
- ❌ Generating strategy, reviewer briefs, or recommendations before reading the specs the index points to (the spec-check gate exists for exactly this)

## Communication style with Dani

- Terse. No preamble.
- No time-of-day, energy, or sleep framing.
- No reflexive caveats unless risk is concrete.
- Direct recommendations, not balanced both-sides answers.
- Match length to substance.
- Don't repeat back what Dani said.
- Push back when warranted. Don't manufacture criticism when a position is sound.
- Diagnose before iterating — find root cause before proposing fixes.
- Project files are authoritative when they conflict with memory.
