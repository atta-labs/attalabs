# Atta Coordination — How to Work With This System

**This file lives in the repo at `project-management/coordination.md`.**
**Every Claude agent reads this at session start.**

Dani works with multiple Claude agents simultaneously across Desktop, Web, and Claude Code. This file is the coordination contract that keeps them in sync.

---

## The model

The four operational files (this one, `state.md`, `plan.md`, and the repo's root `docs-index.md`) are project-management state for Atta. They live in the repo so:

- They are git-tracked (audit trail, blame, history)
- Any Claude session can read them via GitHub MCP without a manual upload step
- Cetana (when V0 ships) can read and write them programmatically as part of normal task execution

The repo is the source of truth. Claude.ai project knowledge is not used for these files anymore.

### What lives where

| File | Purpose | Update cadence |
|------|---------|----------------|
| `project-management/coordination.md` | This file. Names, rules, how to work. | Rare (when system changes) |
| `project-management/state.md` | What's true right now across the ecosystem. | Whenever state changes |
| `project-management/plan.md` | What's being worked on, what's next, what's blocked. | Frequently (any session can update) |
| `docs-index.md` (repo root) | Discovery map of repo content. Auto-generated by `bun docs:index`. | When repo files added/removed/renamed |

Everything else lives in the repo as code, specs, skills, etc. The index lists where things are.

## Session start protocol

Every session, every Claude agent:

1. **Read all 4 operational files via GitHub MCP** — `project-management/coordination.md` (this), `project-management/state.md`, `project-management/plan.md`, `docs-index.md`. The repo is the source of truth.
2. **Ask Dani which product is in scope:**
   *"Which product are we working on today? Vāda, Vitakka, Sati, Cetana, Herald, or general Atta ecosystem work?"*
3. **Once scope is named, BEFORE answering anything substantive, scan `docs-index.md` for every spec under that product and list them back to Dani:**
   *"For Vitakka, the index shows: `apps/vitakka-ai/specs/vitakka-spec.md`, `apps/vitakka-ai/specs/vitakka-human.md`. I haven't read these. Paste them, or confirm they're not relevant to today's question, before I respond."*
4. **Do not generate strategy, briefs, or recommendations until either (a) the relevant specs have been read (via GitHub MCP) or pasted, or (b) Dani has explicitly confirmed they're not needed for this session's question.**
5. **Wait** for Dani's question.

When Claude needs content from a repo file mid-session, Claude reads it via GitHub MCP. If GitHub MCP isn't available in the session, Claude asks Dani by exact path:
> *"I need to read `apps/vada-ai/specs/vada-decisions.md` — can you paste the content?"*

**Tooling note (May 7-8, 2026):** GitHub's hosted MCP server is connected to Claude.ai via OAuth (`api.githubcopilot.com/mcp/`). In **fresh** Claude.ai conversations, Claude has direct read AND write access to `daniboomerang/atta.ai` via tools like `Get file or directory contents`, `List branches`, `List commits`, `Search code`, `Search repositories`, `Create or update file`, `Push files`, `Create branch`. MCP connectors only surface in the tool registry at conversation start, so connections made mid-conversation are not available until the next session begins. When repo access is available, prefer it over paste-back loops; when it's not, fall back to asking Dani by exact path. Self-hosted MCP servers with bearer-token auth (e.g., Vāda's own hosted MCP) currently fail through Claude.ai's connector broker — workaround is Claude Code CLI which works today.

Claude does not pretend to have read content it doesn't have. The index is for discovery, not for content.

### Hard rule — the spec-check gate

If Dani asks a strategic, architectural, or product-shape question about a named product, and Claude has not read the specs for that product, Claude STOPS and reads them (via GitHub MCP) or asks for them. No "thinking out loud first." No "let me draft something we can react to." No reviewer briefs. The specs come first.

Violations of this rule waste hours. The cost of asking is 30 seconds. The cost of skipping is a session of misaligned reasoning.

## Coordination rules — how to keep sessions in sync

### When state changes, update `project-management/state.md`

State changes include:
- A Vāda phase advances (e.g., 7.3 → 7.4)
- Auth migration starts or completes
- DNS gets configured
- A new app is scaffolded
- Stale-doc list changes (something got updated, something else got created)
- Domain configuration shifts
- Any "what's true right now" fact changes

Claude commits the update via GitHub MCP. The commit goes either to a feature branch (if in flight) or directly to a `chore/update-pm` branch with a PR for review.

### When the plan changes, update `project-management/plan.md`

Plan changes include:
- A new sub-feature surfaces during work
- Priorities shift between phases
- A blocker is discovered
- A phase is split or merged
- Sequencing changes
- Something completes (move from "next" to "done")

Any Claude agent can update the plan during a working session. Commit via GitHub MCP.

### When repo structure changes, regenerate `docs-index.md`

Run `bun docs:index` in the repo. Commit the regenerated `docs-index.md`.

This happens when files are added, removed, or renamed. Content changes within existing files do NOT require regeneration.

### When this file or system rules change, update `project-management/coordination.md`

Rare. Only when the coordination model itself shifts.

## Anti-patterns

- ❌ Putting tactical day-to-day plans in repo specs (use `project-management/plan.md` instead)
- ❌ Putting technical architecture docs in `project-management/` (those are repo specs, not operational state)
- ❌ Updating one without the other when both should change (e.g., advancing Vāda phase in `state.md` but not reflecting it in `plan.md`)
- ❌ Pretending to have read a repo doc that wasn't read — always read via GitHub MCP or ask Dani by path
- ❌ Renaming `@atta/*` packages to `@attalabs/*` — code namespace is Atta, AttaLabs is only the public URL
- ❌ Treating Atta as a product — it's the ecosystem only
- ❌ Generating strategy, reviewer briefs, or recommendations before reading the specs the index points to (the spec-check gate exists for exactly this)

## Communication style with Dani

- Terse. No preamble.
- No time-of-day, energy, or sleep framing.
- No reflexive caveats unless risk is concrete.
- Direct recommendations, not balanced both-sides answers.
- Match length to substance.
- Don't repeat back what Dani said.
- Push back when warranted. Don't manufacture criticism when a position is sound.
- Diagnose before iterating — find root cause before proposing fixes.
- Repo files are authoritative when they conflict with memory or stale context.
