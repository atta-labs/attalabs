[vinaya-adopter-ci-hotfix-v1] 1 — Fix adopter CI generator/check bugs + version bump

## Planner's rationale

**Boundary** — Four confirmed bugs in `@attalabs/vinaya`'s adopter-facing surface, all found live on a real adopter repo (identifier redacted — a third-party adopter repo) and independently re-confirmed here against source + a fresh local `vinaya init`/`vinaya check` run, land as ONE task + ONE version bump:

1. `reviewWorkflow()` (`apps/vinaya/cli/src/lib/artifacts.ts`) generates a "review gate" job that runs `vinaya check --all` — every registered check, not just `review-gate` — so an unrelated failing check (e.g. `test-plan`) fails a job whose only stated purpose is the review verdict. Fix: change the generated `run:` line to `vinaya check review-gate` and drop the now-unneeded `PR_BODY` env wiring from that workflow (the `review-gate` check's `CheckSpec.env` already declares `BRANCH`/`PR_NUMBER`/`GITHUB_REPOSITORY`/tokens as optional — confirmed in `checks/registry.ts` — no registry change needed for this half).
2. `checksWorkflow()`'s `pull_request` trigger (`types: [opened, synchronize, reopened]`) omits `edited` — a Test Plan checkbox tick is a PR-body edit, so `test-plan`/`closes-n` (both PR_BODY-driven) never re-evaluate on a checkbox-only push. Fix: add `edited` to `checksWorkflow()`'s trigger types only. (`reviewWorkflow()` does not need this: after fix 1 it no longer runs any PR_BODY-dependent check.)
3. `fetchAssociatedMergedPrs()` (`apps/vinaya/cli/src/commands/audit.ts`) calls `gh api repos/.../commits/<sha>/pulls` exactly once and treats an empty result as a genuine direct push — but that endpoint has a live eventual-consistency lag right after a merge (reproduced: a real 2-parent merge commit read `[]` 15s post-merge, false-flagged, auto-filed an incident Issue). Fix: bound the check with a poll (~120s ceiling, breaking early the moment an association appears) before declaring `direct-push`; a genuine direct push (no PR ever) still fails, just after the ceiling instead of racing the index.
4. `check-brief-shape.ts` calls `checkBriefSections` unconditionally — including `Closes #N` — with no branch-type bypass, so a standalone `fix/*` PR with no task Issue can never structurally pass it. The exact bypass this needs (`isTaskBranch` + `isBriefShaped`, `requireClosesN: isTaskBranch`) already exists and is proven in this repo's own `packages/aeg-core/bin/verify-brief.ts` (lines ~131–160) — it was never ported to the published CLI's bundled check. Fix: export a small `isTaskBranch(branch): boolean` helper from `packages/aeg-core/src/brief-validation.ts` (dedupes the `TASK_BRANCH_PATTERN` regex already triplicated across `verify-brief.ts`/`test-plan-gate.ts`/`archive-task.ts` — reuse, don't add a 4th copy) re-exported via `index.ts`, then give `check-brief-shape.ts` the same branch-aware bypass `verify-brief.ts` already runs, reading `BRANCH` from env. Requires adding `BRANCH: { optional: true }` to `brief-shape`'s `CheckSpec.env` in `checks/registry.ts` (currently only `PR_BODY` is forwarded — an unforwarded env var is invisible to the spawned check, the same class of gap `closes-n`/`registry-gates` already document inline).

Then: bump `apps/vinaya/cli/package.json` version `0.4.4` → `0.4.5` AND `apps/vinaya/cli/scripts/verify-published-lifecycle.ts`'s `PACKAGE_SPEC` to match (the two are bumped together, per this repo's own convention — a source fix that isn't published isn't live for any adopter running `npx @attalabs/vinaya@latest`).

**Explicitly NOT in scope**: the configurability/resolver wiring (Correction 11, separate in-flight design); re-architecting the review-gate/verdict-comment split; the deliberately-unpinned `npx --yes @attalabs/vinaya` (no exact version) inside generated CI workflows — that's an intentional design choice (only the git hooks pin exact version) and out of this task's boundary; any change to `vinaya.config.json`/`doc-owners` adopter-owned-content handling (already correct).

**Sizing** — Passes all four tests. **One verification story**: re-run this same audit's method end-to-end post-fix — build locally, `vinaya init` into a scratch repo, confirm the generated `.yml` content is correct, and run `check-brief-shape.js`/`audit.ts`'s direct-push path against crafted inputs — one coherent proof that adopter CI now converges correctly. One agent can hold it: all four bugs live in the same small subsystem (the install-artifact generator + the check engine it feeds), already fully dug here. Bounded file surface (six touched files, enumerated below). Single failure mode: "does a freshly-`vinaya init`'d adopter repo's CI now gate/trigger/detect/exempt correctly" — one question, even though it has four sub-checks, because all four were found and are verified by the exact same repro method in the same pass (this is why they combine into one task rather than split into four, per the verification-coupling test).

**Project(s) + blast radius** — `Project: vinaya`. One shared-package touch: `packages/aeg-core/src/brief-validation.ts` gains one new additive export (`isTaskBranch`) — no existing export's behavior changes. Consumers: `apps/vinaya/cli` (this task edits it), and this repo's own `packages/aeg-core/bin/verify-brief.ts`/`test-plan-gate.ts`/`archive-task.ts` (re-verification only — they keep their own local `TASK_BRANCH_PATTERN`, untouched by this task; a follow-up could dedupe them onto the new export but that's out of scope here). No other `@atta/aeg-core` consumer exists outside `apps/vinaya/**` and `packages/aeg-core/bin/**` (checked — Vāda/Herald do not import it).

**Dependency rationale** — No `depends-on`. **Possible file-level coupling, not a hard dependency**: open Issue #850 (`vinaya-verification-v1`, "CLI coverage gaps: audit.ts, prompt.ts, detect.ts") plans new tests against `audit.ts`'s CURRENT (pre-fix) direct-push logic; #850 has no branch/PR yet (confirmed via `gh api`), so it is not in-flight and does not block this task. Declaring a `conflicts-with #850` edge here so whoever picks up #850 next serializes behind this one and writes its new tests against the POST-fix (bounded-poll) `audit.ts`, not the buggy version — will post a heads-up comment on #850.

**Traps to avoid** — Do NOT re-add `PR_BODY` env to `reviewWorkflow()` — the whole point of fix 1 is decoupling the review-gate job from PR_BODY-driven checks; re-adding it regresses to the exact bug. Do NOT add `edited` to `reviewWorkflow()`'s trigger types — confirmed unnecessary post-fix-1, and cargo-culting it onto both workflows is the kind of unverified copy that caused bug 2's asymmetric-fix confusion in the source audit. Do NOT duplicate `TASK_BRANCH_PATTERN` a fourth time — export and reuse from `aeg-core`, matching how `isBriefShaped` is already exported and consumed. Do NOT forget the `BRANCH` env-allowlist declaration on `brief-shape` in `registry.ts` — without it the runner strips the var before the child spawns and the bypass silently never fires (confirmed pattern: this exact class of bug already bit two other checks per the registry file's own inline history). The archivist retry must still fail on a TRUE direct push after the poll ceiling — poll-then-decide, never poll-then-always-pass (a real direct push, no PR ever, was already confirmed live in this same repo as Issue #1 pre-audit). Verify like the audit did, not just with unit tests: build (`bun scripts/build.ts` in `apps/vinaya/cli`), run the built `dist/index.js init` against a scratch git repo, read the generated `.yml` files directly, and invoke `dist/checks/bin/check-brief-shape.js` with a crafted `PR_BODY`/`BRANCH` env pair — this exact method is what caught all four bugs originally; a green unit-test suite alone did not.

**Suggested agent-class** — mid. Mechanically well-scoped (all four fixes are already validated live in the adopter repo, exact shape known), but `reviewWorkflow()` sits inside `review-gate` — a check with a documented three-round security history (trust-anchor reads, verdict-author allowlist) — so the change needs care and round-trip proof, not blind pattern-matching. Not fast; not high (no open design question, just careful execution + verification).

**Stop-and-escalate** — If the archivist fix needs anything beyond a bounded poll against the existing `commits/{sha}/pulls` endpoint (e.g. the endpoint itself turns out unreliable beyond eventual consistency, or a 120s ceiling would flake real CI timing), stop and escalate `severity:strategy` rather than picking an arbitrary longer ceiling. If making `review-gate` work as the review workflow's sole check surfaces any need to change `check-review-gate.ts`'s own env/trust-anchor behavior (beyond the generated workflow's `run:` line), stop — that script's PR_BODY/BASE_SHA omissions are deliberate security decisions (see `.claude/skills/vinaya-architecture/SKILL.md`'s trust-anchor section) and any change there needs explicit review, not a quick patch bundled into this hotfix.
