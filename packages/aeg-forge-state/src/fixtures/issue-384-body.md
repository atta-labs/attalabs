The interactive skeleton is harvested from Cetana's `apps/cetana-ai/cli/src/commands/init.ts` + its abort-path regression tests. `init product` scaffolds an additional governed product area in an initialized monorepo, same diff-and-confirm contract. NOT: doctor/upgrade/eject (task 6), demo/waiver (task 7); NOT running init on THIS repo (that is the migration tranche's move).

**Sizing** — Passes: one verification story (init on a clean fixture repo → every artifact present, workflow green, `--dry-run` output exactly matches what install then does, abort path exits clean), one agent holds it, bounded surface, single failure mode (installer wrote wrong/partial state — which the diff-and-confirm contract exists to prevent).

**Amendment (2026-07-05, Planner) — hook-installation semantics made explicit** (routed finding: `vinaya-finding-husky-hook-installation`). No new decision entry needed — all three points derive from D-089 (non-destructive trust surface) + this task's own diff-and-confirm contract: (1) installed git hooks are thin, clearly-delimited STUBS that invoke the installed `vinaya` binary (`vinaya check`-family) — never inlined check logic, and never paths into this monorepo's `packages/aeg-core/bin/*` (that is this repo's shim wiring, not the product's); this matches the thin-dispatcher shape `.husky/pre-push` here has been converging to (tasks 25/32/33). (2) Pre-existing adopter hooks are NEVER clobbered: if a hook file exists, vinaya appends a delimited managed block (marker comments), shown verbatim in the diff-and-confirm output before anything is written; if none exists, it generates the stub fresh; `vinaya eject` removes exactly the managed block, or the whole file only if vinaya created it. (3) Hook-manager strategy — husky detected vs raw `.git/hooks`/`core.hooksPath` — is a Brief-Author dig-time call; if no clean activation path exists for a target repo shape, stop-and-escalate `severity:strategy` rather than inventing a new hook manager. Per-clone hook-presence drift is `vinaya doctor`'s job (#386), not the installer's — installer installs, doctor diagnoses.


**Amendment (2026-07-06, Planner) — workflow-installation semantics made explicit** (routed finding: `vinaya-finding-workflow-naming-convention`). Same shape as the hook amendment; no new decision entry needed — the naming rule already exists in D-085 ("machine-generated artifacts in adopter repos carry a `vinaya-` prefix") and the single-workflow design in D-104/the §5 contract. Explicit now: (1) init installs exactly ONE workflow file, `.github/workflows/vinaya.yml` (running `vinaya check --all --diff-only`) — enforcement consolidates behind the check engine, so there is no generated workflow *family*; if a future task ever generates additional workflows, D-085's `vinaya-` prefix is the mandatory scheme. (2) GitHub Actions reads workflow files ONLY flat inside `.github/workflows/` (no subfolder scanning) — no design here depends on subfolders, so this is recorded as a constraint, not a risk; the Developer may confirm it empirically in one line if any doubt arises during implementation. (3) Never-clobber applies to workflows exactly as to hooks: if `.github/workflows/vinaya.yml` already exists with content vinaya did not generate, init REFUSES to overwrite (shown in the diff-and-confirm output; explicit `--force`-class confirmation or manual resolution required); `vinaya eject` removes the file only if vinaya owns it. (4) Tier distinction recorded: `.github/workflows/` + `.husky/` are the MANDATORY enforcement substrate the installer must handle correctly; `.claude/**` (or any other assistant-specific projection) is OUT of this task's scope entirely — optional, tool-specific, never a blocker for Vinaya's core function (consistent with D-072's black-box principle). (5) This repo's own un-prefixed AEG workflows (`archivist.yml`, `forge-lifecycle.yml`, `verify-docs.yml`, `verify-test-plan.yml`) are REPLACED by the generated file at the `aeg-forge-state-v1` cutover, not renamed — no separate rename task exists; `ci.yml`/`conventions.yml`/`claude*.yml` are monorepo-generic and keep their names.
