# Vinaya — Product Spec (seed)

Status: draft

First mention of this file. Captures the ratified and pending decisions that define Vinaya so far. Some of them are still awaiting ratification — this doc summarizes intent, it is not itself a ratified commitment. Each decision's full reasoning lives in the pull request that made it.

## What Vinaya is

A governance layer for AI coding agents: deterministic checks every agent must satisfy before merge, installed with `npx @attalabs/vinaya init`. Vinaya doesn't block agents — it redirects them into a governed flow, so a human reviews judgment, not compliance. "Vinaya" means "discipline" / "the rules of conduct" in Pali.

## Architecture

- **Entry point:** `npx @attalabs/vinaya init`; site at `vinaya.attalabs.dev`. The command resolves for real — the CLI is published to the public npm registry as `@attalabs/vinaya` (see § Distribution). No editor extension; GitHub App (deployed Studio / org installs) deferred.
- **Vinaya Studio:** visual proof of derived status, not the acquisition hook. One derivation library with N consumers (CLI gates, local Studio, future deployed Studio); Studio renders `check --json`/forge-facts output and never re-implements governance logic; no database. In-repo, Studio is `apps/vinaya-studio/web` (split out of the original `apps/vinaya/web`, task 3/#885; the old app was deleted once task 2/#884's deployment cutover landed, task 4/#886) — a standalone app that is never deployed, structurally rather than by runtime gate. It ships bundled inside `@attalabs/vinaya` itself as a pre-built standalone Next.js server (`studio-standalone/`, § Distribution) rather than as a separate npm package — `vinaya studio` runs it directly outside a workspace checkout, no extra install; that bundling mechanism lives in the standalone `atta-labs/vinaya` repo and moves its own bundle source to `apps/vinaya-studio/web` on its own timeline, not this one. Deployment roadmap: Phase 1 (v1.0) local Studio, now including the standalone-via-npx shape; Phase 2 generated Projects view; Phase 3 (deferred) deployed self-hosted stateless read-only Studio on a GitHub App token; Phase 3½ dogfood-as-demo over Vinaya's own public repo.
- **Enforcement hierarchy:** deterministic checks → CI + branch protection (necessary, not sufficient — it guarantees a result is reported under the required check's name, not that the result came from running the real check; see § Forge writes) → git hooks (ring 0, universal) → forge-write interception (ring 1, opt-in accelerator only, never load-bearing).
- **Substrate:** GitHub Issues + labels are machine truth; Projects v2 is an optional generated view, never a source of truth; `init` prints the recommended branch-protection command and never applies it.
- **Custom checks:** any executable honoring the §5 error contract, registered in `vinaya.config.json`. Core gates use the same interface — no privileged API. Glob scoping is allowed; conditional logic (if/unless/except) is forbidden.
- **Error contract:** every check error carries `agent_recovery_prompt` — a corrective instruction for the executing model, not a restated diagnosis. The check contract + error schema are a versioned public surface.
- **State placement:** process/work state lives on the forge (Milestones, labels, comments); low-churn parseable artifacts (project registry, doc-owners) stay plain files wrapped in a code-free workspace package; universal AEG doctrine ships inside the npm package with a scaffolded, visible pointer in the adopter's repo.
- **Repo-root resolution is a deployment constraint, not just a lookup:** the site's doctrine-reading routes (`/docs/harness`, `/docs/reference`) are handed no root — they locate the repo by walking up from the working directory for a **marker file** (`vinaya.config.json`; the Studio's registry reader walks for `.vinaya/projects.md`). On a serverless host only traced files exist at runtime, so **the marker file is a deployment input in its own right** and must be declared alongside the doctrine itself in the web app's file-tracing config. Omit it and the walk fails before any doctrine is read — the routes 500 in production only, with a green build and a clean local run. Renaming a marker is therefore a two-place change. The failure this actually produced was subtler than a forgotten rename: one commit moved the repo-root marker **and** introduced a second marker for the registry reader, updated the tracing declaration for the second, and never declared the first — so the change looked complete, built green, and 500ed only the routes that walk for the marker nobody declared. The coupling is mechanized rather than documented: a guard test discovers the readers that walk and parses each one's marker out of source and fails when one is not declared for tracing, which is the check that was missing both times.

## Distribution

- **Published name:** `@attalabs/vinaya` — scoped, public, on the public npm registry (`npm publish --access public` from `apps/vinaya/cli`). **The bare name `vinaya` is unobtainable, not merely untaken.** The registry 404s for it, but npm's automated typosquat filter refuses the publish outright — `403 Package name too similar to existing package vinyl` — and that filter cannot be tested except by attempting a publish. Discovered at publish time on 2026-07-29; Principal chose the `attalabs` scope over npm's suggested `@daniboomerang/vinaya` (personal-username scope reads as a hobby package) and over blind attempts at `vinaya-cli`/`vinaya-harness` (the filter is opaque, and each attempt is an irreversible publish if it succeeds). Scoped names bypass the filter. **The installed command remains `vinaya`** — `bin.vinaya` is unchanged, so only the install line carries the scope. Every surface printing an install command therefore says `npx @attalabs/vinaya init`; a surface still printing the bare name is a defect, since that command 404s. Appealing to npm for a typosquat exception remains open as a later route to the bare name.
- **Node target, not bun.** The four advertised install commands are package-manager invocations, not runtime choices — npm/pnpm/yarn would happily install a bun-shebang binary and then fail at exec on any machine without bun, after the user already ran the command from the website. The published artifact is therefore a single Node-executable ESM bundle (`dist/index.js`, `#!/usr/bin/env node`, built by `scripts/build.ts` via `bun build --target=node`), `engines.node >= 20`. Bun remains the build toolchain; it is no longer a runtime requirement.
- **Dependency shape.** The whole `@atta/*` workspace graph (`@atta/aeg-core`, `@atta/aeg-forge-state`, `@atta/aeg-types`, `@atta/vinaya-sources`) is inlined by the bundle; the only declared runtime dependencies are the two genuinely external ones, `zod` and `gray-matter`. The build script derives its externals list from the manifest's non-`workspace:*` dependencies rather than a hand-written list, so a later real dependency cannot be silently inlined.
- **Tarball contents** are an explicit `files` allowlist: `dist/`, `templates/` (read at runtime by `vinaya new check`), `aeg-root/` (the bundled doctrine subset, read at runtime by the `doctrinePointer()`-generated `VINAYA.md`; see the Doctrine bundling entry in the Install-lifecycle chapter below), `studio-standalone/` (a pre-built standalone Next.js server for `vinaya studio` outside a workspace checkout, produced by `scripts/bundle-studio.ts` — see the `vinaya studio` entry in the Commands chapter below), `README.md`. No `src/`, no `tests/`, no `tsconfig.json` — a published version cannot be recalled, only deprecated, so the allowlist is the last line against an over-broad artifact.
- **License: Apache-2.0** (`apps/vinaya/cli/LICENSE` and `packages/aeg-core/LICENSE`, both full canonical text; npm ships the CLI's regardless of the `files` allowlist). Relicense from AGPL-3.0-only, Principal decision 2026-08-06 (Type 1, ratified) — sole copyright holder, zero external contributors, both OSS category competitors (Agentic OS, GitHub Spec Kit) are MIT, and AGPL blocked the adoption that is Vinaya's entire thesis. This supersedes the original AGPL-3.0-only decision recorded in this same bullet on 2026-07-29. Apache-2.0 is permissive, not copyleft — there is no share-alike obligation on derivatives; anyone may use, fork and modify Vinaya, including closed forks. Note this licenses the inlined `@atta/*` graph too, since the bundle distributes it. **Only `packages/aeg-forge-state` and `packages/aeg-types` still carry no LICENSE file of their own** — `packages/aeg-core` now has its own. Trademark on the "Vinaya" name is a separate instrument and does not exist yet; no license prevents a rebranded fork.
- **Deliberately not published:** the `@atta/*` packages as standalone registry packages — they ship inlined; their standalone extraction is a separate, not-yet-scoped question. (Studio itself is no longer in this category — it ships bundled as `studio-standalone/`, above, rather than as a separate package or a stub.) The 15 core AEG check bins ARE in the tarball, bundled — see Correction 7 in the Check engine chapter below for why an earlier `src/`-only shape left them unreachable through a real `npm install`, and the `dist/checks/bin/*.js` fix.
- **Published-lifecycle proof script (#705).** `apps/vinaya/cli/scripts/verify-published-lifecycle.ts` (`bun run verify-published-lifecycle`) installs `@attalabs/vinaya` from the real public npm registry into a scratch directory outside this repo and exercises every `status: 'shipped'` entry in `@atta/vinaya-sources`' `COMMANDS` registry against that installed artifact — never local source. Two deliberate non-green outcomes are asserted by design, independent of publish state: `check --all` outside a workspace reports 4 `status: 'error'` outcomes, never a crash; forge-write commands (`pr`/`issue` `create`/`edit`) run `--validate-only` only, with `issue edit` exempted (its label-fetch reaches the network unconditionally, even under `--validate-only`) — the script's own source carries no non-`--validate-only` `gh` invocation. **As of 2026-08-06, running this script against the currently-published `@attalabs/vinaya@0.1.0` is EXPECTED to exit non-zero**, naming four known, tracked gaps (issue #705 and its follow-up comment): `demo break` and `waiver` (#387) are unrecognized commands, `check --all` reports 5 checks instead of 4, and `init` never writes `.vinaya/doc-owners` (#665) — all four share one root cause, the published artifact predating source changes that landed after 2026-07-29, not four separate defects. ## Trust surface

`init` is non-destructive by contract (full diff → confirm → install; `--dry-run`); `demo break` is the productized belief moment (refusal → self-correction → pass, see its own chapter below); `waiver` is the only forge-authenticated escape hatch (see its own chapter below); `eject` restores stock in one command; `doctor` is treated as a product (diagnoses everything, mutates nothing).

- **Studio cannot lie by omission.** When live forge enumeration fails (rate limit, network, `gh`/token missing, or `resolveRepo()` unresolvable), Vinaya Studio's tranche lists render an explicit "live forge state unavailable" warning banner — never a truth-shaped empty "No active tranches." state. The flag (`TrancheLists.forgeAvailable`, `tranchesForProject().forgeAvailable` in `apps/vinaya-studio/web/src/lib/repo-state/read-root.ts`) is derived per-request from that request's failures only (Studio stores nothing); the legacy `completed/*.md` supplement is not a failure and never trips the banner. The genuine (forge-reachable) empty state is a first-class state, not an aside: on a project page it renders as a `Card` + lucide `Inbox` block under the tab strip rather than a small muted line, on the same surface and spacing as a populated tranche card (#627). The two states stay mutually exclusive — the emptiness is explained exactly once, by whichever surface actually knows why: **each tab consults its own `ForgeStatus`** — `ProjectTranchesTabs.tsx` passes a null hint whenever that tab's fetch did not succeed (`forge.active.kind`/`forge.archived.kind`), and the grid then renders nothing at all, leaving the banner as the sole explanation, so a forge failure can never acquire a confident "nothing here" panel on top of it. The Archived tab is included deliberately: it used to hardcode its hint string, which is exactly how a false "No archived tranches yet." survived a failed fetch.

- **Sidebar copy (#591)** — the left panel carries the page's editorial framing. On the overview: a page title (**"The Vinaya Harness"**, rendered above the ring in the diagram column, in the ring hub's own `font-mono`/`muted` type so the title and the diagram read as one type system), a sidebar heading (**"The forge rings that keep your code safe"**), an intro paragraph, and an 8-entry **legend** naming every ring outer→center (the six drill groups plus the `GitHub` substrate and the `main — Protected` hub). Drilling a ring swaps heading+intro for that ring's own name and one-line framing, and lists the ring's members by full (untruncated) name as a numbered `<ol>` — derived live from `drilledGroup.children`, not a hardcoded per-ring list. **The legend prose is fixed editorial copy with one hard rule: any fact that also lives in the diagram is DERIVED from the `DiagramModel` at render time, never typed into a string.** Today that is the actor roster (`The Actors` — the `actors` group's child labels) and the canonical-action count (`The Actions` — `actions.children.length`); a role added or an action retired updates this copy with zero page change, the same property the ring itself has. The drilled-ring framing is built from the same legend source, so overview and drilled text for a ring can never disagree.
- **Groupings** (`_lib/groupings.ts`) — six interactive drill groups derived purely from the model, outermost first: `actors` (`kind: 'role'` — 9), `contracts` (`kind: 'contract'` — 6), `ring0`, `actions` (`kind: 'action'` — all 10), `ring1`, `ring2` (the three ring groups being the `kind: 'ring'` nodes plus their `gate`/`check` children). A static "the forge" hub frames the center — not a `DiagramNode` (the model has no dedicated substrate node kind), so it carries no data, same status as a section heading. **10/9/6, per #508.**
  - **Two corrections against #508's original wording, both landed in task 4 (#553).** The brief's "two seam rings" were `action-github`/`action-internal` — actions split by `ACTIONS.crosses` — with contracts as chords across the drilled `actors` band. Contracts were promoted to a first-class drillable band instead (a chord-only overlay could not be clicked, and a contract is a doctrine object with its own file). That took a seam slot, and `actions` was left holding only the crossings under the name "GitHub Crossing" — which silently dropped the five non-crossing acts (`commit-the-work`, `author-the-brief`, `produce-the-verdict`, `post-provenance-comment`, `write-the-retrospective`) from the page entirely, against the brief's own "render the real 10/9/6". One `actions` ring now holds all ten; the crossing rides each node as `DiagramNode.crosses` and renders as a per-wedge badge (`reaches github` / `stays local`), which is where a fact about a node belongs. Six groups, seven bands, nothing dropped.
- **Geometry** (`_lib/geometry.ts`) — pure pixel math with zero `DiagramModel` knowledge: band/sector counts always come from the caller's real counts, never fixed. Coordinates are rounded to 2 decimal places — raw trig output otherwise differs in its last float digit between the server's SSR pass and the client's hydration pass, which React reports as a hydration mismatch.
- **Label sizing** — ring and wedge labels are sized on the Tailwind type scale for legibility at the diagram's rendered scale (#702), never by an arbitrary px value. A drilled wedge's own radial thickness — not the wider arc width a wedge nearer the top or bottom gets — is the binding constraint for a wedge sitting at the ring's left or right, since its label is horizontal text at the wedge's centroid; the longest label at each ring must be checked against that thickness, not assumed to fit. One ring's longest label currently exceeds it (see "Known limits") — a font-size change alone cannot close that gap without moving the wedge's own geometry, which is out of scope here.
- **Leaf panel** — exactly, in render order: a ring/kind tag, the doctrine `summary` (its question), the node's name in uppercase, a `category`-or-`actorType` `Badge`, a render-state indicator when not `active`, the node's `description`, and a dual link row — "Read more" followed by "View source". The question leads because it is the one line authored for a reader; the name only says which node was clicked, which a reader who just clicked it already knows. The badge is one flat filled default for every value, never keyed to WHICH value — the doctrine grades no category above another, so a per-value palette would assert a ranking that does not exist. `actorType: either` renders as two badges (HUMAN + AGENT) rather than the literal word: "either" only means something to a reader who already knows the other two values exist. `description` is one plain sentence and every node kind carries one (see "DiagramModel derivation" below). Both links resolve via `_lib/read-more.ts`'s `readMoreTarget`, which now returns an optional `docRoute` alongside the always-present GitHub `path`/`line` — one mapping, not two. "Read more" (an in-app `next/link`, no new tab) is the `docRoute`: gate/check nodes land on `/docs/enforcement` (no per-row anchor — `DocPage.tsx`'s renderer has no `rehype-slug`, so a deep line link would land a reader at the top of a 31-row table to hunt their own row; #568 ruled this the dual-link shape over teaching the generic doc renderer one document's table schema); role/contract nodes land on `/docs/roles|contracts/<id>` (the node's `label` *is* its doctrine frontmatter id). "View source" (external, new tab, unchanged from the pre-task single link) is the GitHub blob: `enforcement.md#L<sourceLine>` for gate/check, `aeg-root/roles|contracts/<id>.md` (no line) for role/contract, `packages/aeg-core/src/actions.ts` for action — action nodes carry no doctrine markdown, so they render "View source" alone, no "Read more".
- **Client/server boundary** — `DiagramExplorer`/`DiagramCanvas`/`LeafPanel` (all `'use client'`) never import `@atta/aeg-core` values, `@/lib/github-links`, or `@/lib/docs/load-aeg-docs` directly: all three transitively pull in `node:fs`/`node:child_process` (via `@atta/aeg-forge-state` or `server-only`), which Turbopack cannot bundle for the browser. `page.tsx` derives groups/chords/read-more-and-view-source hrefs once, server-side — asserting every role/contract `docRoute` against `loadAegDocs().nav.flat` there and throwing if one isn't surfaced, rather than shipping a dead "Read more" link — and passes plain serializable props down; client files import only `type` declarations from `@atta/aeg-core`/`groupings.ts`.
- **Render-state, cannot lie by omission** — a `disabled` gate/check stays present in its group's `children` array (dimmed, never hidden); a `locked` one stays `locked` even if config also tries to disable it (lock wins, mirroring `deriveDiagramModel`'s own precedence); an unknown `config.gates` key would surface as a visible finding banner on the page itself, not console-only (dormant in v1 since `config` is always `null`).
- **App-shell height model (#591)** — the page fills the viewport without scrolling, and does so through the shared shell rather than a hardcoded TopBar height. `(site)/layout.tsx` is a full-viewport flex column (`h-dvh flex-col`): the `TopBar` keeps its intrinsic height and a `flex-1 min-h-0 overflow-y-auto` region takes exactly the rest. Full-height pages (`docs/harness`, `docs/reference`) fill that region with `h-full` + `overflow-hidden`; long pages (Home) scroll *inside* it under the now-sticky TopBar. This replaced a per-page `h-[calc(100dvh-56px)]` that baked the 56px TopBar height into every such page and drifted a few pixels into a stray window scroll. The diagram column stacks a title row (`shrink-0`) over the canvas (`flex-1 min-h-0`); the SVG scales into whatever height is left (`h-full` + `viewBox` cropped 36px to shed the square viewBox's built-in whitespace, still clearing the drilled ring), so adding the title shrinks the ring rather than growing the page. Below `lg` the page reverts to natural height and the shell's scroll region handles overflow.

"AEG" (the builder's name; Vinaya is the user's name, per root `CLAUDE.md`) appears exactly once on the page, near the footer, framed as "the model that AEG implements."
