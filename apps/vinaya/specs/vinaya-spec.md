# Vinaya — Product Spec (seed)

Status: draft

First mention of this file — created by `vinaya-studio-v1` task 0. Captures the ratified and pending decisions that define Vinaya so far. Some of them are still awaiting ratification — this doc summarizes intent, it is not itself a ratified commitment. Each decision's full reasoning lives in the pull request that made it.

## What Vinaya is

A governance layer for AI coding agents: deterministic checks every agent must satisfy before merge, installed with `npx @attalabs/vinaya init`. Vinaya doesn't block agents — it redirects them into a governed flow, so a human reviews judgment, not compliance. "Vinaya" means "discipline" / "the rules of conduct" in Pali.

## Architecture

- **Entry point:** `npx @attalabs/vinaya init`; site at `vinaya.attalabs.dev`. The command resolves for real — the CLI is published to the public npm registry as `@attalabs/vinaya` (see § Distribution). No editor extension; GitHub App (deployed Studio / org installs) deferred.
- **Vinaya Studio:** visual proof of derived status, not the acquisition hook. One derivation library with N consumers (CLI gates, local Studio, future deployed Studio); Studio renders `check --json`/forge-facts output and never re-implements governance logic; no database. Ships as a separate optional npm package `@vinaya/studio` — in-repo, Studio is `apps/vinaya/web`. Deployment roadmap: Phase 1 (v1.0) local Studio only; Phase 2 generated Projects view; Phase 3 (deferred) deployed self-hosted stateless read-only Studio on a GitHub App token; Phase 3½ dogfood-as-demo over Vinaya's own public repo.
- **Enforcement hierarchy:** deterministic checks → CI + branch protection (the guarantee) → git hooks (ring 0, universal) → forge-write interception (ring 1, opt-in accelerator only, never load-bearing).
- **Substrate:** GitHub Issues + labels are machine truth; Projects v2 is an optional generated view, never a source of truth; `init` prints the recommended branch-protection command and never applies it.
- **Custom checks:** any executable honoring the §5 error contract, registered in `vinaya.config.json`. Core gates use the same interface — no privileged API. Glob scoping is allowed; conditional logic (if/unless/except) is forbidden.
- **Error contract:** every check error carries `agent_recovery_prompt` — a corrective instruction for the executing model, not a restated diagnosis. The check contract + error schema are a versioned public surface.
- **State placement:** process/work state lives on the forge (Milestones, labels, comments); low-churn parseable artifacts (project registry, doc-owners) stay plain files wrapped in a code-free workspace package; universal AEG doctrine ships inside the npm package with a scaffolded, visible pointer in the adopter's repo.
- **Repo-root resolution is a deployment constraint, not just a lookup:** the site's doctrine-reading routes (`/the-harness`, `/docs`) are handed no root — they locate the repo by walking up from the working directory for a **marker file** (`vinaya.config.json`; the Studio's registry reader walks for `.vinaya/projects.md`). On a serverless host only traced files exist at runtime, so **the marker file is a deployment input in its own right** and must be declared alongside the doctrine itself in the web app's file-tracing config. Omit it and the walk fails before any doctrine is read — the routes 500 in production only, with a green build and a clean local run. Renaming a marker is therefore a two-place change. The failure this actually produced was subtler than a forgotten rename: one commit moved the repo-root marker **and** introduced a second marker for the registry reader, updated the tracing declaration for the second, and never declared the first — so the change looked complete, built green, and 500ed only the routes that walk for the marker nobody declared. The coupling is mechanized rather than documented: a guard test discovers the readers that walk and parses each one's marker out of source and fails when one is not declared for tracing, which is the check that was missing both times.

## Distribution (`vinaya-cli-v1`, task 9, #700)

- **Published name:** `@attalabs/vinaya` — scoped, public, on the public npm registry (`npm publish --access public` from `apps/vinaya/cli`). **The bare name `vinaya` is unobtainable, not merely untaken.** The registry 404s for it, but npm's automated typosquat filter refuses the publish outright — `403 Package name too similar to existing package vinyl` — and that filter cannot be tested except by attempting a publish. Discovered at publish time on 2026-07-29; Principal chose the `attalabs` scope over npm's suggested `@daniboomerang/vinaya` (personal-username scope reads as a hobby package) and over blind attempts at `vinaya-cli`/`vinaya-harness` (the filter is opaque, and each attempt is an irreversible publish if it succeeds). Scoped names bypass the filter. **The installed command remains `vinaya`** — `bin.vinaya` is unchanged, so only the install line carries the scope. Every surface printing an install command therefore says `npx @attalabs/vinaya init`; a surface still printing the bare name is a defect, since that command 404s. Appealing to npm for a typosquat exception remains open as a later route to the bare name.
- **Node target, not bun.** The four advertised install commands are package-manager invocations, not runtime choices — npm/pnpm/yarn would happily install a bun-shebang binary and then fail at exec on any machine without bun, after the user already ran the command from the website. The published artifact is therefore a single Node-executable ESM bundle (`dist/index.js`, `#!/usr/bin/env node`, built by `scripts/build.ts` via `bun build --target=node`), `engines.node >= 20`. Bun remains the build toolchain; it is no longer a runtime requirement.
- **Dependency shape.** The whole `@atta/*` workspace graph (`@atta/aeg-core`, `@atta/aeg-forge-state`, `@atta/aeg-types`, `@atta/vinaya-sources`) is inlined by the bundle; the only declared runtime dependencies are the two genuinely external ones, `zod` and `gray-matter`. The build script derives its externals list from the manifest's non-`workspace:*` dependencies rather than a hand-written list, so a later real dependency cannot be silently inlined.
- **Tarball contents** are an explicit `files` allowlist: `dist/`, `templates/` (read at runtime by `vinaya new check`), `README.md`. No `src/`, no `tests/`, no `tsconfig.json` — a published version cannot be recalled, only deprecated, so the allowlist is the last line against an over-broad artifact.
- **License: AGPL-3.0-only** (`apps/vinaya/cli/LICENSE`, full text; npm ships it regardless of the `files` allowlist). Principal decision, 2026-07-29. No LICENSE file and no `license` field existed anywhere in this repo before this task — the code was all-rights-reserved despite the repo being public — so this is the first licensing act, not a change to an existing one. Copyleft is the deliberate choice: anyone may use, fork and modify Vinaya, but every derivative — including one an AI rewrites past recognition — must ship its source under the same license, so the work cannot be taken closed. The Affero variant over plain GPL because Vinaya Studio is a hostable surface, and the network clause is what keeps a hosted fork's source open. Note this licenses the inlined `@atta/*` graph too, since the bundle distributes it. **`packages/aeg-core`, `packages/aeg-forge-state` and `packages/aeg-types` still carry no LICENSE file of their own** — out of this task's §4 surface, tracked separately. Trademark on the "Vinaya" name is a separate instrument and does not exist yet; no license prevents a rebranded fork.
- **Deliberately not published:** `@vinaya/studio` (the `{ kind: 'missing' }` branch in `resolveStudioTarget` stays a stub) and the `@atta/*` packages as standalone registry packages — they ship inlined; their standalone extraction is #546's question. The five core AEG check bins (`src/checks/bin/*.ts`) are also not in the tarball: they are monorepo-bound gates (they read `aeg-root/**` relative to this repo), so outside a Vinaya workspace `vinaya check --all` reports them as `status: 'error'` rather than crashing; that surface also belongs with #546.

## Trust surface

`init` is non-destructive by contract (full diff → confirm → install; `--dry-run`); `demo break` is the productized belief moment (refusal → self-correction → pass); `eject` restores stock in one command; `doctor` is treated as a product (diagnoses everything, mutates nothing).

- **Studio cannot lie by omission.** When live forge enumeration fails (rate limit, network, `gh`/token missing, or `resolveRepo()` unresolvable), Vinaya Studio's tranche lists render an explicit "live forge state unavailable" warning banner — never a truth-shaped empty "No active tranches." state. The flag (`TrancheLists.forgeAvailable`, `tranchesForProject().forgeAvailable` in `apps/vinaya/web/src/lib/repo-state/read-root.ts`) is derived per-request from that request's failures only (Studio stores nothing); the legacy `completed/*.md` supplement is not a failure and never trips the banner. The genuine (forge-reachable) empty state is a first-class state, not an aside: on a project page it renders as a `Card` + lucide `Inbox` block under the tab strip rather than a small muted line, on the same surface and spacing as a populated tranche card (`vinaya-pages-v2` task 14, #627). The two states stay mutually exclusive — the emptiness is explained exactly once, by whichever surface actually knows why: **each tab consults its own `ForgeStatus`** — `ProjectTranchesTabs.tsx` passes a null hint whenever that tab's fetch did not succeed (`forge.active.kind`/`forge.archived.kind`), and the grid then renders nothing at all, leaving the banner as the sole explanation, so a forge failure can never acquire a confident "nothing here" panel on top of it. The Archived tab is included deliberately: it used to hardcode its hint string, which is exactly how a false "No archived tranches yet." survived a failed fetch.

## Check engine (`vinaya-cli-v1`, task 3, #383)

`vinaya check <name> | --all` ships as a runner plus an error contract, with the five core AEG gates (doc coverage, brief shape, coherence, dispatch readiness, reader-resolvable prose) expressed through the **same public interface** as custom checks — no privileged API. This is the task that makes real rather than asserted: `tests/checks/no-privileged-api.test.ts` mechanically proves a core `CheckSpec` and a config-registered one carry no field the other cannot, and that `runChecks` has no branch on provenance.

- **`CheckSpec` — how a check declares itself.** `{ name, run, args?, scope: 'diff' | 'full', include?, timeoutMs? }`. `scope: 'diff'` declares "I only care about the diff"; the runner may skip such a check under `--diff-only` when none of its `include` globs match a changed file (recorded in the outcome list as `status: 'skipped'`, never silently dropped — a dropped check would read as a passing one). `scope: 'full'` checks always run (today: `coherence`, `dispatch-readiness` — both read live forge state; `reader-resolvable-prose` — sweeps the doctrine tree and the public site's pages, not the local diff). `include` is glob **scoping only**; the config grammar (below) forbids conditionals entirely.
- **`reader-resolvable-prose` (report-only).** The fifth core check: two mechanizable classes of "words a reader cannot resolve" from a three-class analysis where the third (register/slop) stays human review (`aeg-root/roles/reviewer.md`). Class 1 — a bare forge number or an internal (including legacy pre-`-vN`) tranche slug cited in doctrine or a public site page. Class 2 — a coined term (`tranche`, `brief`, `forge`, `provenance`, `dispatch`, …) used with neither an inline definition nor a link to the glossary; the term list is parsed live from `aeg-root/glossary.md`'s own entry headings, never hard-coded. The pure rule (`packages/aeg-core/src/reader-resolvable-prose.ts`) takes file paths, contents, the term list and the legacy-slug list and returns findings — zero I/O, same purity charter as every other `@atta/aeg-core` check. Ships report-only (`aeg-root/enforcement.md`'s G1/G2 rollout precedent): findings print at `severity: 'warning'`, but the check's own exit code always stays `0`.
- **The error schema, field-by-field.** One JSON line on stderr per finding: `{ schema: 1, check, severity: 'error' | 'warning', message, agent_recovery_prompt, file?, line? }`. `message` is the diagnosis — what is wrong. `agent_recovery_prompt` is the corrective **instruction**, addressed to the model that will act on it — never a restatement of `message`. Compare: `message: "packages/ui/topbar/Nav.tsx changed but its owning SKILL.md is not in the diff"` vs. `agent_recovery_prompt: "Read .claude/skills/ui-components/SKILL.md, apply your change, and commit both files in this PR."` A prompt that merely rephrases the diagnosis fails the whole reason exists — the ring-0 self-correction loop.
- **Exit-code semantics.** The exit code IS the verdict: `0` = pass, `1` = findings (`status: 'fail'`). Any other exit code, or a stderr line that fails to parse as a `CheckError`, is read by the runner as `status: 'error'` — a check that emits garbage must be loud, never a silent pass.
- **Runner-enforced timeouts.** `timeoutMs` on a `CheckSpec` is advisory; the **runner** spawns, races against the timer, and kills the child on expiry (`status: 'timeout'`). A check trusted to time itself out cannot be trusted at all — checks never self-enforce their own deadline.
- **No-network-by-default.** A check must not reach the network unless it is a declared exception. Today's two declared exceptions are the core `coherence` and `dispatch-readiness` checks (`scope: 'full'`) — both read forge facts through the two primitives `@atta/aeg-core` re-exports for this purpose (`fetchForgeFacts`, `fetchOpenIssuesByLabel`), never a hand-rolled forge client.
- **Config registration.** `vinaya.config.json`'s `checks` object registers any executable honoring the contract above: `{ "checks": { "<name>": { "run", "scope", "include"?, "args"?, "timeoutMs"? } } }`. Glob scoping (`include`) is permitted; conditional logic (`if`/`unless`/`except`, or any expression string) is **never** part of this grammar — complexity that a check needs escapes into the executable, by design. A malformed `checks` entry surfaces as a `status: 'error'` outcome naming the invalid key (never a silent `null` that would make `vinaya check --all` print green over a broken registration).
- **Stability guarantee.** The check contract (`CheckSpec`/`CheckError`/`CheckOutcome`, `CHECK_SCHEMA_VERSION`) is a versioned public surface — third-party plugins will be written against it. Additive evolution only: fields may be added; never removed, renamed, or retyped. `CHECK_SCHEMA_VERSION` bumps only on a breaking change to the schema shape itself.
- **`vinaya new check <name>`** scaffolds a self-contained, worked custom check into `./scripts/vinaya-checks/<name>.ts` — no dependency on `@attalabs/vinaya`'s own source (it lives in the adopter's repo), runs unmodified through the runner, and emits one real `CheckError` out of the box.

**Known scope gap, recorded here rather than silently narrowed.** The core `dispatch-readiness` check's `priorTrancheArchival` predicate always reports empty (trivially passing) — resolving it for real needs `listActiveTrancheSlugs` to discover candidate prior tranches per project, which is not among the forge primitives this task's dependency boundary (`@atta/aeg-core` + `@atta/vinaya-sources` only) re-exports. Likewise the core `coherence` check runs A1, A3, T1, T2, T3, D1, R1, L1 (and the always-info L3) but not A2/L2/L4/L5, which need `fetchProvenance`/`listActiveTrancheSlugs`/`listIssueMilestonesForSlug` — also not re-exported. Both are real, narrower-than-`bin/verify-dispatch.ts`/`bin/verify-coherence.ts` parity gaps, not re-derivations of the missing facts — a future task exporting those primitives from `@atta/aeg-core` closes the gap without touching this task's contract.

## Forge writes (`vinaya-cli-v1`, task 5, #385)

`vinaya pr create | edit` and `vinaya issue create | edit` are the validated forge-write path: every write runs the full, **config-defined brief-schema validation LOCALLY, before any `gh` write** — prevention, not detection. A malformed body is refused at the CLI layer, in-session, before anything reaches the forge; the identical `@atta/aeg-core` validators run in CI purely as a backstop. The commands **adapt the semantics** of `packages/aeg-core/bin/open-pr.ts` / `open-issue.ts` — they never import them: those bins `process.chdir(REPO_ROOT)` and shell out to this repo's `bin/*` gate scripts, so importing them would drag this repo's layout into a distributable CLI. Instead, like `src/checks/bin/check-brief-shape.ts`, they call the aeg-core public exports and speak the versioned `CheckError` contract.

- **The config-defined brief schema (`briefSchema` in `vinaya.config.json`).** WHICH sections a `pr`/`issue` body must carry is expressed as **config, never hardcoded in the command code** — this repo's required-section set is just one instance (one derivation, N consumers). The schema key is `briefSchema: { pr?: { sections: [...] }, issue?: { sections: [...] } }`. Each section is declarative — no conditional grammar (no `if`/`unless`/`except`), any diff-conditionality living inside the built-in validator's code, never in the config:
  - `{ "builtin": "<name>" }` — runs the named battle-tested `@atta/aeg-core` validator. The names: `tier`, `testPlan`, `testPlanExclusivity`, `principalPlaceholder`, `surfaceMap`, `docUpdateList`, `worktreeStep0`, `stopConditions`, `autonomyClause`, `project`, `for`, `closesN`, `lockAck`, `premiseCoverage`, `issueRationale`. This repo's `pr` instance is the first fourteen (mirroring `checkBriefSections` + premise coverage); its `issue` instance is `issueRationale` (the eight-field Planner rationale, applied only to `tranche:*` task Issues).
  - `{ "heading": "…" }` / `{ "field": "…" }` / `{ "phrase": "…" }` — an adopter-authored generic matcher for their own required sections (a `## …` heading, a `Field:` header field, or a literal phrase anywhere). An adopter shapes their own brief schema through these without touching command code. If a validation this repo relies on cannot be expressed in this declarative, adopter-generic grammar, that is a config-contract gap to escalate — never a license to hardcode.
- **The refusal contract.** On any failure the command emits one `CheckError` JSON line per finding on stderr and exits 1 — the same versioned contract (`schema: 1`, `check`, `severity`, `message`, `agent_recovery_prompt`) the check engine defines. `agent_recovery_prompt` names the exact corrective `vinaya` command, never a restatement of `message` — engineering the ring-0 self-correction loop.
- **`--validate-only`.** Runs every gate, reports `PASS`, exits 0 **without writing** — the `[agent]`-testable path. `--json` envelopes the outcome (`{ schema: 1, data: { validated, written, … } }`).
- **Same-bytes body plumbing (#333).** A stream/heredoc body (`--body-file /dev/stdin`, process substitution) is empty on a *second* read by the time `gh` opens the original path, so the body is buffered ONCE, validated, then materialized into a fresh temp file whose path replaces the `--body-file` slot — `gh` reads the exact bytes this process validated, never an independent second read.
- **Gate-set-per-path — the forge is the truth on `edit` (#417).** On `create`, the diff context (changed files, lock-touch) comes from the local checkout, which IS the truthful source there. On `edit <n>`, that context is a property of the TARGET object, not of whatever checkout the command runs from: `pr edit` fetches the PR's real head branch + changed files (`gh pr view`); `issue edit` fetches the Issue's actual labels (`gh issue view`) and unions them with argv (argv is normally silent on edit). A failed forge fetch is a **hard refusal**, never a fall-back to the local checkout — the exact bypass that fall-back would reopen.
- **Not in v1.0 of this path.** The gh-shim / PreToolUse interception that would make these commands the *only* way to write to the forge is an explicit fast-follow, out of this task. This repo continues to use `packages/aeg-core/bin/open-pr.ts` as its own sanctioned path until that migration; `vinaya pr/issue` is the distributable, adopter-generic reference implementation.

## Install lifecycle: `init` / `init product` / `eject` (`vinaya-cli-v1`, task 4, #384)

`vinaya init` turns any GitHub repo into a Vinaya-governed repo, non-destructively; `vinaya eject` cleanly reverses it. They ship as one change-set because they are the forward and inverse of the same typed, owned operations — writing them apart risks `init` recording ownership too loosely for `eject` to undo (ratified 2026-07-21).

**The install rule (minimal manifest, re-ruled 2026-07-23): `init` installs only what a shipped check consumes.** The manifest is exactly five items — nothing that no gate reads is scaffolded into an adopter's repo. Live-testing the first implementation exposed that it had absorbed this monorepo's own operational apparatus (GitHub templates, a `governance/` folder, example check scripts) rather than the product's core; those are cut. See **Correction 1** below for the before/after.

The five installed items:

1. **`vinaya.config.json`** — the starter ruleset, with **`checks: {}` empty**.
2. **Git hooks** — thin pre-commit + pre-push managed-block stubs invoking `vinaya check` (`.husky/` if present, else raw `.git/hooks`; never a new dependency).
3. **Two workflows** — `.github/workflows/vinaya-checks.yml` + `vinaya-review.yml`.
4. **Root `VINAYA.md`** — the doctrine pointer.
5. **Labels** — create-if-absent, never modify.

- **The change-set spine (`src/lib/ops.ts`).** One model of typed operations both commands consume: `create-file`, `managed-block`, `create-label`, `print`. `planInstall` classifies every op against current on-disk state BEFORE any write (`create` / `skip-owned` / `refuse-foreign` for files; `create-host` / `append` / `skip-present` for blocks); `renderInstallDiff` turns that classification into the COMPLETE diff the user confirms; `applyInstall` writes and returns the ownership manifest. `planEject`/`applyEject` are the exact inverse, driven purely by the recorded manifest — the spine carries its own inverses, so shrinking the manifest is a pure op-list edit; `eject` needs no per-artifact change. Nothing is ever written without a shown diff + confirmation.
- **Ownership records = the `managed` manifest (`vinaya.config.json`) + in-file markers.** `applyInstall` records what it created into `managed: { version, files[], blocks[], labels[] }` inside `vinaya.config.json`; managed blocks are additionally self-delimited by `>>> vinaya:managed:<marker> >>>` / `<<< … <<<` comment markers in the host file. `eject` reads the manifest; if it is absent (untouched repo) `eject` is a no-op, and if it is present-but-corrupt `eject` STOPS short of any delete rather than guess (Section 10 stop condition).
- **Non-destructive by contract.** Workflows, config, and the root `VINAYA.md` pointer are `create-file` **refuse-if-foreign** — a file vinaya did not create is never overwritten. Git hooks are the only `managed-block` artifact — a pre-existing adopter hook keeps its lines; vinaya appends a marker-delimited block. Labels are **create-if-absent**; an existing label is never modified, and `eject` **reports** created labels for manual removal (never auto-deletes — a label may be in use elsewhere). No `postinstall`; PATH is never touched; branch protection is **printed, never applied**.
- **Two workflows.** `init` installs `.github/workflows/vinaya-checks.yml` (on `pull_request`, runs `vinaya check --all --diff-only`) AND `.github/workflows/vinaya-review.yml` (on `pull_request` **and** `issue_comment`, guarded by a cheap `contains(..., 'VERDICT')` before any checkout cost, so a verdict *comment* re-fires the gate). A single workflow would re-introduce the action-filtered-skip bug the split fixed. Both are `vinaya-`-prefixed and refuse-if-foreign.
- **The starter ruleset is EXTRACTED, not invented — but `checks` starts empty.** `vinaya.config.json` is seeded from this repo's real gates: `rings` (opt-in accelerators, off), an **empty `checks: {}`** (no example checks and no example scripts ship — `vinaya new check` is the add-path), and `briefSchema` defaults (a PR body must carry Tier / a tagged Test Plan / `Closes #N` / Project; a task Issue the Planner rationale). Tier definitions ride the created labels (`vinaya/tier:0/1/3` — no `vinaya/tier:2`).
- **The doctrine pointer — root `VINAYA.md`, the only orientation artifact.** A thin, git-tracked, tool-agnostic file at the repo root (the reading-order convention an agent orienting in a fresh repo actually hits — beside README, not buried in a subfolder) naming where the full doctrine lives (inside the installed npm package, updated by `vinaya upgrade` — no in-repo copy to drift). Tool-SPECIFIC projections (`.claude/`, an auto-loaded `CLAUDE.md`) are OUT of v1.0.
- **`.claude` independence audited (#722).** Every `.claude` reference reachable from `apps/vinaya` is build-time-only, never shipped to an adopter. Confirmed: the doctrine-pointer statement directly above is the intended tool-agnostic doctrine, not a coupling; `apps/vinaya/web/design/vinaya-landing-brief.md`'s `.claude` mentions sit inside an explicitly-marked historical-record build brief for monorepo contributors building `apps/vinaya/web`, never bundled or read at runtime by `apps/vinaya/cli`; `ProductSwitchControl.tsx`'s `.claude/skills/ui-library-system/SKILL.md` code-comment citation lives in `apps/vinaya/web` (Vinaya Studio, hosted at `vinaya.attalabs.dev`, not npm-published), outside `apps/vinaya/cli`'s published `files` allowlist (`dist`, `templates`, `README.md`). Also confirmed: `aeg-root/skills/{aeg,aeg-roles,brief-authoring}/SKILL.md` — Vinaya's own skill set — carry only prose cross-references to `.claude/skills/*` (the host-repo generated view relationship), no functional dependency on it.
- **Hook host resolution (locked default).** Prefer `.husky/` if present, else raw `.git/hooks`; never add husky as a dependency. A custom `core.hooksPath` is the one shape `init` refuses to guess at — it STOPS and asks (Section 10) rather than inventing a hook manager.
- **`init product <name>`** extends an already-initialized repo with a governed product area — shrunk (2026-07-23) to creating a single **`project:<name>` label** (create-if-absent). Same diff-and-confirm contract; refuses if the repo is not yet initialized (`vinaya.config.json`'s ownership manifest is the marker that `init` has run).
- **`--dry-run` / `--yes`.** `--dry-run` prints the full diff and writes nothing — byte-identical to what a real install then writes for every content artifact (the one exception is `vinaya.config.json`, whose `managed` manifest is injected at apply time). `--yes` skips the confirmation prompt. The interactive abort path calls `process.stdin.destroy()` so a declined prompt exits clean rather than hanging (ported from Cetana's `init.ts`, recovered from git history after #638 deleted `apps/cetana-ai`).
- **Proof (`tests/ops.test.ts`, `tests/init.test.ts`).** Fixture-repo tests assert: exactly the 5-item manifest installs and NOTHING else (a full fixture-tree assertion — no `governance/`, no templates, no `scripts/vinaya-checks/`); `--dry-run` writes nothing yet shows the exact install bytes; the abort path writes nothing; never-clobber (a pre-existing hook gets an appended block; a foreign workflow and a pre-existing root `VINAYA.md` are REFUSED); both workflows install with the correct triggers; `init product` creates only the `project:<name>` label; and the round-trip `init` → `eject` returns the fixture to its exact pre-init filesystem (managed blocks stripped from surviving adopter files, labels reported not deleted, orphan-manifest eject refused).

## Install lifecycle: `doctor` / `upgrade` (`vinaya-cli-v1`, task 6, #386)

`vinaya doctor` diagnoses the installation `init` created; `vinaya upgrade` is the only sanctioned way back to a clean one. Together they close the lifecycle #384/#656 opened: install → diagnose → migrate → (still) eject.

- **`doctor` never mutates.** Every check is read-only — it re-runs the SAME op list `buildInitOps` gives `init` (`src/lib/artifacts.ts`) and classifies each op against on-disk state + the `managed` manifest instead of applying it (`src/commands/doctor.ts`'s `diagnoseInstall`). It reports; it does not fix. Seven checks: (1) git hooks — present, executable, managed block intact, including the per-clone drift case where a `.git/hooks`-based install's stubs were never tracked by git and are silently absent after a fresh clone (the reason doctor exists, per #384's amendment-2); (2) both workflows — present, byte-content matches the installed package's current generator (skew reported, never patched); (3) `vinaya.config.json` — loud on parse/schema failure (`loadConfigChecked`'s contract, reused here), and the `managed` manifest checked BOTH directions against disk (a recorded file missing on disk, and a vinaya-marked file/block present on disk but unrecorded in the manifest); (4) root `VINAYA.md` — present, managed marker intact; (5) environment — `gh auth status` detail, Node/Bun version, and a "package vs installed artifacts" skew line pointing at `vinaya upgrade` whenever any check above found drift (a self-explaining message, never a bare mismatch); (6) branch protection — report-only via `gh api`, never applied, unknown/unreachable reported honestly rather than guessed; (7) custom checks — every `checks` entry's `run` script path resolves on disk (registration shape itself is already the schema's job). Exit 0 when every finding is `ok`/`info`; exit 1 on any `warn`/`error`. `--json` emits the same findings enveloped (`schema: 1`).
- **`upgrade` regenerates vinaya-owned artifacts only, via the same detect → plan → render diff → confirm → apply engine `init` uses** (`src/commands/upgrade.ts`'s `planUpgrade` / `renderUpgradeDiff` / `applyUpgrade`) — inverted in intent: where `init`'s `applyInstall` never touches an already-owned file (idempotent re-install), `upgrade`'s whole job is bringing an owned-but-stale artifact current. A file/block vinaya does not own — foreign content, or never installed — is left exactly alone (reported `REFUSE`/`skip`, never touched); `upgrade` regenerates what `init` already owns, it does not perform a fresh install. `vinaya.config.json`'s semantic fields (`rings`/`checks`/`briefSchema`) are adopter-owned from day one and are never diffed or rewritten by `upgrade` — only the `managed` ownership sub-object is regenerated (its `version` bumped forward when stale). A no-op upgrade (everything already current) prints "already current" and exits 0 without prompting. `--dry-run` / `--yes` behave exactly as they do for `init`/`eject`.
- **Manifest version is a real range check, not an exact pin.** `managed.version` in `vinaya.config.json`'s schema (`src/lib/config.ts`) changed from `z.literal(MANAGED_MANIFEST_VERSION)` to `z.number().int().positive()` so `upgrade` can read a manifest recorded by an older package version instead of that manifest failing schema validation outright. `upgrade` refuses loudly and self-explains when the repo's recorded version is NEWER than the installed package understands ("upgrade the vinaya package itself first"); migrating an older manifest forward is currently a no-op beyond the version bump, since v1 remains the only version that has ever shipped.
- **Init's no-remote graceful-skip (spec D3).** `vinaya init` (and `init product`) used to crash mid-run on the first `gh label create` when the repo had no `origin` remote (or it wasn't a GitHub URL) — `detectGitRepo` already tolerates this (owner/repo come back blank), but every downstream label op still assumed a real remote. Both commands now detect this up front, print a warning, skip label creation (and the gh-auth requirement that existed only for it) entirely, and continue installing everything else — the final summary still prints. `init product`'s only op IS a label, so a remoteless run scaffolds nothing and says so, rather than reporting success for an install that didn't happen.
- **Doctrine bundling into the package is NOT shipped by this task.** Issue #386 also owned bundling `aeg-root/{roles,contracts,state-machine.md,templates}` into the CLI package as neutral-named adopter-facing reference content (no internal-methodology name reaching an adopter). Investigation found the whole corpus — not just `state-machine.md` — is saturated with this-repo-specific implementation detail (`packages/aeg-core/bin/*.ts` paths, specific historical PR-number citations, `.github/workflows/forge-lifecycle.yml` step names) that a mechanical AEG→Vinaya name swap cannot fix without authoring new doctrine prose, which the brief this task executed explicitly forbids. Escalated `severity:strategy` in this task's PR body; `VINAYA.md`'s doctrine-lives-in-the-package promise remains unfulfilled until a follow-up authors genuinely portable content. `doctor` does NOT check for a doctrine bundle — there is none to check for yet.

## Renderer contract (`vinaya-studio-v1`, task 4, #389)

**The rule: Studio renders, it never re-derives.** Governance state enters Studio only through one of two permitted entry paths — `@atta/aeg-core`'s public API, **or** the `@atta/vinaya-sources` `StateSource` adapters. Both are legitimate; this is an OR, not a hierarchy — do not "fix" an aeg-core-direct call site into a `StateSource` one on the strength of this chapter alone. What both paths rule out is a third option: Studio computing any piece of governance state itself. The gates (`vinaya check`, and today `packages/aeg-core/bin/*`) compute governance state; Studio's only job is to render what they computed. If Studio ever re-derives any of it, Studio and the gates can disagree about the same repo — and a product whose dashboard contradicts its own gate has no product left.

**The one-way import corollary.** `apps/vinaya/web` must never import `apps/vinaya/cli` internals, and `apps/vinaya/cli` must never import web internals — either direction crossing the boundary would let one surface reach around the other's derivation and compute governance facts on its own. This is now mechanically enforced, not asserted in prose: `apps/vinaya/web/src/lib/import-boundary.test.ts` (vitest) walks every `.ts`/`.tsx` file under `web/src` and fails on any import/export statement whose specifier names `@attalabs/vinaya` — or its pre-publish workspace name `@atta/vinaya-cli`, still matched so an import written against the old name is caught rather than silently allowed — including subpaths, or reaches relatively into `../cli/`; `apps/vinaya/cli/tests/import-boundary.test.ts` (bun test) is the converse, walking `cli/src` and `cli/tests` for `@atta/vinaya-web` or `../web/` reaches. Each package guards its own boundary and fails its own CI; the two tests intentionally do not share an imported helper — that import would itself cross the boundary they exist to defend.

**What is not a violation.** Fetching facts — plain I/O — in the web app is fine. `load-snapshot.ts` fetching forge facts over the network and handing them to `@atta/aeg-core`'s `deriveTranche` is the contract working as designed, not a breach: the derivation still happens inside aeg-core, not in Studio. The rule is about **derivation**, not about where an HTTP call lives. This is the distinction most likely to be misread: "Studio fetches data" is not the same claim as "Studio computes governance state," and only the second is forbidden.

## StateSource (`vinaya-cli-v1`, task 2, #382)

The seam every pure evaluator (`deriveTranche`, `sumLedger`, ...) consumes state through, so they never care whether an `Tranche` came from a git-tracked file or the forge.

- **Contract:** `StateSource` (`packages/aeg-core/src/state-source.ts`, re-exported from `@atta/aeg-core`'s `index.ts`) — one method, `getTranche(slug: string): Promise<Tranche>`. Builds on `@atta/aeg-types`'s existing `Tranche`/`Task` shapes; does not redefine them. `aeg-core`'s zero-I/O purity charter (post-#372) means this file holds only the type — no adapter implementation lives here.
- **Adapters** — both live in a new workspace, `apps/vinaya/sources` (`@atta/vinaya-sources`), the only package in this seam allowed I/O:
  - `createForgeSource` (`src/forge-adapter.ts`) — the **primary** design. Wires `@atta/aeg-forge-state`'s `deriveTrancheFromForge` behind the contract. **Imported as a workspace dependency (`workspace:*`), not re-homed** — `@atta/aeg-forge-state` (built by `aeg-forge-state-v1` #425, resequencing) is already a clean, general-purpose, repo/owner-parameterized package with its own existing consumers (`packages/aeg-core/bin/*`, both apps' `read-root.ts`/`stale-blocker.ts`); re-homing it would be a rename with no functional benefit and would break those consumers.
  - `createFileSource` (`src/file-adapter.ts`) — **transitional**, a deliberate throwaway deleted once every `StateSource` consumer is forge-backed. ## DiagramModel derivation (enforcement-derivation-v1 task 5, #506)

One pure library turns governance doctrine into a renderer-agnostic model every diagram consumer reads — Studio, `/the-harness`, a CLI visualizer — so none re-implements the governance logic (one derivation library, N consumers).

- **Contract:** `deriveDiagramModel(doctrine, config, tranche): DiagramModel` (`packages/aeg-core/src/diagram-model.ts`, exported from `@atta/aeg-core`'s `index.ts`). Pure — zero I/O, zero `fs`/`node:` imports (aeg-core's purity charter, #372/#521). Doctrine arrives already-read as `DoctrineContent` (raw `enforcement.md` + roles/contracts markdown); config is the declarative `DiagramConfig` (ring-level + per-gate enable/disable booleans, `null` = nothing disabled); `tranche` is the `StateSource` live-context passthrough, carried on the model and **never** used to compute render-state.
- **Model shape:** `nodes` (kind `ring | gate | check | action | role | contract`, each with a kind-prefixed stable id, label, optional `ringIndex`, and a derived `renderState`), `edges` (`guards` gate→action, `performs` role→action, `produces`/`consumes` role→contract), `findings` (config keys that reference no real gate/check), and the passthrough `tranche`. **Geometry — radius, angle, colour, coordinates — is NOT in the model; the renderer owns it.** A ring index and a render-state are structural facts; a pixel is not.
- **A node's three text fields, and why they are three (`vinaya-pages-v1` task 4, #553):** `summary` is the rhetorical question (#551); `detail` is one plain sentence saying what the node does; `label` is its name. Each `detail` comes from its own source's `description` — `enforcement.md`'s `Description` column for gate/check, `description:` frontmatter for role/contract, the `ACTIONS` entry's field for action — so every kind reads in one register, because a reader cannot see what kind of node they clicked. `detail` is never `GateRow.spec`, the enforcement table's own "what must be true" column: that column is written to ENFORCE (17 of 31 rows cite a decision id, issue number or file path; the longest runs 2708 chars), which is correct for a gate and unreadable on a page. Rendering `spec` is the bug `description` exists to prevent; "Read more" is what carries a reader to it. This closed the gap #508's leaf-panel spec left — it listed `summary` and a link, with no field answering the question it asks.
- Every gate/check/action/role/contract node also carries an optional `summary` (a short, non-technical question, e.g. "Ever had someone push straight to main and nobody noticed?") — gate/check nodes additionally carry `category` (`ci`/`hook`/`event`, describing when the check fires relative to a bare repo with no governance installed) and role nodes carry `actorType` (`agent`/`human`/`either`, from the role's own pre-existing frontmatter). Added by `vinaya-pages-v1` task 3 (#551), consumed by task 4's (#508) drill panels.
- **Render-state is derived, never authored** (precedence top-down): `locked` when the doctrine row's `lock` column is non-empty (config can never override a lock, e.g. a principal/foundational gate); `disabled` when config disables it (per-gate `gates[slug] === false`, or the ring-level `ring1_forgeWriteInterception`/`ring2_asyncAudits` switch for that ring's checks); else `active`. Ring 0 has no ring-level switch — only a per-gate entry can disable a ring-0 gate, and a locked one ignores even that.
- **DoctrineSource seam:** the library takes doctrine, not `aeg-root/` paths (it must be packageable for adopters with no `aeg-root/`). The type `DoctrineSource` (`packages/aeg-core/src/doctrine-source.ts`, I/O-free, mirrors `StateSource`) is implemented by `createFileDoctrineSource({ root? })` in `@atta/vinaya-sources` (`src/doctrine-file-adapter.ts`), reading `<root>/enforcement.md`, `<root>/roles/*.md`, `<root>/contracts/*.md` over a configurable root (default `DEFAULT_GOVERNANCE_ROOT`, never a hardcoded literal).
- **No-drift substrate:** the derivation consumes the canonical `ACTIONS` and its `CROSSING_KEYWORDS` map (promoted into `actions.ts` this task) — the same list G3's crossing check reads — so gate→action edge counts can never drift from G3's completeness set. The markdown-table parser is likewise the one aeg-core-owned `markdown-table.ts` (promoted out of the web app this task); `registry-parse.ts` and the Vinaya `/aeg` renderer both sit on it.
- **Proof:** fixture tests (`diagram-model.test.ts`) assert the exact node set, a config-disabled gate `disabled`, a locked gate `locked` even when config also disables it, an unknown config key surfacing as exactly one finding, and edge counts matching `ACTIONS`; a real-`aeg-root/` cross-check asserts every `into-github` action gets ≥1 `guards` edge, every `performedBy` role resolves to a role node, and node ids are globally unique.
- **Out of scope for this task:** the renderer (pages own SVG/geometry — the rings-drilldown application landed as `vinaya-pages-v1` task 4, #508); wiring per-gate switches into the CLI's `VinayaConfigSchema` (a later CLI task — `DiagramConfig` is this task's only config surface).
- **Render decision (`vinaya-pages-v1` task 4, #508):** `/the-harness`'s leaf panel shows `category`/`actorType` as a neutral filled `Badge` — one fill for every value, never per-value color-coded, and distinct from the diagram's own per-ring visual distinction (an unrelated, pre-existing concept). #508's amendment specifies `variant='outline'`; outline renders near-invisible against this page's cream background, so the filled default is a deliberate departure on that one point, preserving the brief's actual constraint (no per-value colour coding) rather than its literal wording. "Read more" links to a real GitHub blob line (`enforcement.md#L<sourceLine>` for gate/check nodes; `roles|contracts/<id>.md` with no line for role/contract nodes; `packages/aeg-core/src/actions.ts` for action nodes — no doctrine markdown backs them, but that file does define them, and a panel with no way out was the worse answer). `DiagramModel.tranche` is passthrough task-lifecycle data, not per-check live status — so `/the-harness` carries no "checks N/N" live pill, deliberately, even though the pre-existing design mockup this page's interaction pattern is drawn from shows one.
