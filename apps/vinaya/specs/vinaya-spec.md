## What Vinaya is

A governance layer for AI coding agents: deterministic checks every agent must satisfy before merge, installed with `npx vinaya init`. Vinaya doesn't block agents — it redirects them into a governed flow, so a human reviews judgment, not compliance. "Vinaya" means "discipline" / "the rules of conduct" in Pali.

## Architecture

- **Entry point:** `npx vinaya init`; site at `vinaya.attalabs.dev`. No editor extension; GitHub App (deployed Studio / org installs) deferred (D-086).
- **Vinaya Studio:** visual proof of derived status, not the acquisition hook. One derivation library with N consumers (CLI gates, local Studio, future deployed Studio); Studio renders `check --json`/forge-facts output and never re-implements governance logic; no database (D-087). Ships as a separate optional npm package `@vinaya/studio` — in-repo, Studio is `apps/vinaya/web` (D-098). Deployment roadmap: Phase 1 (v1.0) local Studio only; Phase 2 generated Projects view; Phase 3 (deferred) deployed self-hosted stateless read-only Studio on a GitHub App token; Phase 3½ dogfood-as-demo over Vinaya's own public repo (D-101).
- **Enforcement hierarchy (D-090):** deterministic checks → CI + branch protection (the guarantee) → git hooks (ring 0, universal) → forge-write interception (ring 1, opt-in accelerator only, never load-bearing).
- **Substrate (D-091):** GitHub Issues + labels are machine truth; Projects v2 is an optional generated view, never a source of truth; `init` prints the recommended branch-protection command and never applies it.
- **Custom checks (D-092, D-109):** any executable honoring the §5 error contract, registered in `vinaya.config.json`. Core gates use the same interface — no privileged API. Glob scoping is allowed; conditional logic (if/unless/except) is forbidden.
- **Error contract (D-100):** every check error carries `agent_recovery_prompt` — a corrective instruction for the executing model, not a restated diagnosis. The check contract + error schema are a versioned public surface.
- **State placement (D-096, D-110, D-111):** process/work state lives on the forge (Milestones, labels, comments); low-churn parseable artifacts (decision log, project registry, doc-owners) stay plain files wrapped in a code-free workspace package; universal AEG doctrine ships inside the npm package with a scaffolded, visible pointer in the adopter's repo.

## Trust surface (D-089)

`init` is non-destructive by contract (full diff → confirm → install; `--dry-run`); `demo break` is the productized belief moment (refusal → self-correction → pass); `eject` restores stock in one command; `doctor` is treated as a product (diagnoses everything, mutates nothing).

- **Studio cannot lie by omission (D-087).** When live forge enumeration fails (rate limit, network, `gh`/token missing, or `resolveRepo()` unresolvable), Vinaya Studio's iteration lists render an explicit "live forge state unavailable" warning banner — never a truth-shaped empty "No active iterations." state. The flag (`IterationLists.forgeAvailable`, `iterationsForProject().forgeAvailable` in `apps/vinaya/web/src/lib/repo-state/read-root.ts`) is derived per-request from that request's failures only (Studio stores nothing); the legacy `completed/*.md` supplement is not a failure and never trips the banner.

## `/the-harness` page (`vinaya-pages-v1` task 4, #508; renamed from `/how-it-works` in task 13, #591, D-127)

`apps/vinaya/web/src/app/(site)/the-harness/` replaces the former `/aeg` methodology page (task 0b, #480) entirely — `/aeg`'s page, its 6 `_components/*`, and all of `src/lib/aeg/*` (the hand-rolled roles/rings/contracts parsers) are deleted. `/aeg` was briefly a 301 Route Handler to here (D-102's citability requirement); **the route is gone too — "AEG" is retired as a public name (D-123), so a redirect preserving its URL would be that name still published, one hop away.** The site names no predecessor. Where the old page read `aeg-root/**` through its own bespoke parsers, this page reads it through the shared, aeg-core-owned `deriveDiagramModel` (see "DiagramModel derivation" below) — one derivation library, N consumers, per D-087.

- **Data spine** (`_lib/load-diagram.ts`) — `createFileDoctrineSource({ root: findAegRoot() }).getDoctrine()` + `deriveDiagramModel(doctrine, null, null)`, called at module scope inside the Server Component (`page.tsx`), never a request handler. `config` is `null` (no `vinaya.config.json` UI yet); `iteration` is `null` — `DiagramModel.iteration` is passthrough task-lifecycle data with no per-check pass/fail signal, so there is nothing honest to render from it. No live "checks N/N" pill exists on this page, deliberately, even though the design mockup this page's interaction is based on (`design/how-it-works-rings-drilldown.html`) shows one.
- **Sidebar copy (`vinaya-pages-v1` task 13, #591)** — the left panel carries the page's editorial framing. On the overview: a page title (**"The Vinaya Harness"**, rendered above the ring in the diagram column, in the ring hub's own `font-mono`/`muted` type so the title and the diagram read as one type system), a sidebar heading (**"The forge rings that keep your code safe"**), an intro paragraph, and an 8-entry **legend** naming every ring outer→center (the six drill groups plus the `GitHub` substrate and the `main — Protected` hub). Drilling a ring swaps heading+intro for that ring's own name and one-line framing, and lists the ring's members by full (untruncated) name as a numbered `<ol>` — derived live from `drilledGroup.children`, not a hardcoded per-ring list. **The legend prose is fixed editorial copy with one hard rule: any fact that also lives in the diagram is DERIVED from the `DiagramModel` at render time, never typed into a string (D-119).** Today that is the actor roster (`The Actors` — the `actors` group's child labels) and the canonical-action count (`The Actions` — `actions.children.length`); a role added or an action retired updates this copy with zero page change, the same property the ring itself has. The drilled-ring framing is built from the same legend source, so overview and drilled text for a ring can never disagree.
- **Groupings** (`_lib/groupings.ts`) — six interactive drill groups derived purely from the model, outermost first: `actors` (`kind: 'role'` — 9), `contracts` (`kind: 'contract'` — 6), `ring0`, `actions` (`kind: 'action'` — all 10), `ring1`, `ring2` (the three ring groups being the `kind: 'ring'` nodes plus their `gate`/`check` children). A static "the forge" hub frames the center — not a `DiagramNode` (the model has no dedicated substrate node kind), so it carries no data, same status as a section heading. **10/9/6, per #508.**
  - **Two corrections against #508's original wording, both landed in task 4 (#553).** The brief's "two seam rings" were `action-github`/`action-internal` — actions split by `ACTIONS.crosses` — with contracts as chords across the drilled `actors` band. Contracts were promoted to a first-class drillable band instead (a chord-only overlay could not be clicked, and a contract is a doctrine object with its own file). That took a seam slot, and `actions` was left holding only the crossings under the name "GitHub Crossing" — which silently dropped the five non-crossing acts (`commit-the-work`, `author-the-brief`, `produce-the-verdict`, `post-provenance-comment`, `write-the-retrospective`) from the page entirely, against the brief's own "render the real 10/9/6". One `actions` ring now holds all ten; the crossing rides each node as `DiagramNode.crosses` and renders as a per-wedge badge (`reaches github` / `stays local`), which is where a fact about a node belongs. Six groups, seven bands, nothing dropped.
- **Geometry** (`_lib/geometry.ts`) — pure pixel math with zero `DiagramModel` knowledge: band/sector counts always come from the caller's real counts, never fixed. Coordinates are rounded to 2 decimal places — raw trig output otherwise differs in its last float digit between the server's SSR pass and the client's hydration pass, which React reports as a hydration mismatch.
- **Leaf panel** — exactly, in render order: a ring/kind tag, the doctrine `summary` (its question), the node's name in uppercase, a `category`-or-`actorType` `Badge`, a render-state indicator when not `active`, the node's `description`, and a dual link row — "Read more" followed by "View source". The question leads because it is the one line authored for a reader; the name only says which node was clicked, which a reader who just clicked it already knows. The badge is one flat filled default for every value, never keyed to WHICH value — the doctrine grades no category above another, so a per-value palette would assert a ranking that does not exist. `actorType: either` renders as two badges (HUMAN + AGENT) rather than the literal word: "either" only means something to a reader who already knows the other two values exist. `description` is one plain sentence and every node kind carries one (see "DiagramModel derivation" below). Both links resolve via `_lib/read-more.ts`'s `readMoreTarget`, which now returns an optional `docRoute` alongside the always-present GitHub `path`/`line` — one mapping, not two. "Read more" (an in-app `next/link`, no new tab) is the `docRoute`: gate/check nodes land on `/docs/enforcement` (no per-row anchor — `DocPage.tsx`'s renderer has no `rehype-slug`, so a deep line link would land a reader at the top of a 31-row table to hunt their own row; `vinaya-pages-v1` task 8, #568, ruled this the dual-link shape over teaching the generic doc renderer one document's table schema); role/contract nodes land on `/docs/roles|contracts/<id>` (the node's `label` *is* its doctrine frontmatter id). "View source" (external, new tab, unchanged from the pre-task single link) is the GitHub blob: `enforcement.md#L<sourceLine>` for gate/check, `aeg-root/roles|contracts/<id>.md` (no line) for role/contract, `packages/aeg-core/src/actions.ts` for action — action nodes carry no doctrine markdown, so they render "View source" alone, no "Read more".
- **Client/server boundary** — `DiagramExplorer`/`DiagramCanvas`/`LeafPanel` (all `'use client'`) never import `@atta/aeg-core` values, `@/lib/github-links`, or `@/lib/docs/load-aeg-docs` directly: all three transitively pull in `node:fs`/`node:child_process` (via `@atta/aeg-forge-state` or `server-only`), which Turbopack cannot bundle for the browser. `page.tsx` derives groups/chords/read-more-and-view-source hrefs once, server-side — asserting every role/contract `docRoute` against `loadAegDocs().nav.flat` there and throwing if one isn't surfaced, rather than shipping a dead "Read more" link — and passes plain serializable props down; client files import only `type` declarations from `@atta/aeg-core`/`groupings.ts`.
- **Render-state, cannot lie by omission (D-087)** — a `disabled` gate/check stays present in its group's `children` array (dimmed, never hidden); a `locked` one stays `locked` even if config also tries to disable it (lock wins, mirroring `deriveDiagramModel`'s own precedence); an unknown `config.gates` key would surface as a visible finding banner on the page itself, not console-only (dormant in v1 since `config` is always `null`).
- **App-shell height model (`vinaya-pages-v1` task 13, #591)** — the page fills the viewport without scrolling, and does so through the shared shell rather than a hardcoded TopBar height. `(site)/layout.tsx` is a full-viewport flex column (`h-dvh flex-col`): the `TopBar` keeps its intrinsic height and a `flex-1 min-h-0 overflow-y-auto` region takes exactly the rest. Full-height pages (`the-harness`, `docs`) fill that region with `h-full` + `overflow-hidden`; long pages (Home) scroll *inside* it under the now-sticky TopBar. This replaced a per-page `h-[calc(100dvh-56px)]` that baked the 56px TopBar height into every such page and drifted a few pixels into a stray window scroll. The diagram column stacks a title row (`shrink-0`) over the canvas (`flex-1 min-h-0`); the SVG scales into whatever height is left (`h-full` + `viewBox` cropped 36px to shed the square viewBox's built-in whitespace, still clearing the drilled ring), so adding the title shrinks the ring rather than growing the page. Below `lg` the page reverts to natural height and the shell's scroll region handles overflow.

"AEG" (the builder's name; Vinaya is the user's name, per root `CLAUDE.md`) appears exactly once on the page, near the footer, framed as "the model that AEG implements."

## Check engine (`vinaya-cli-v1`, task 3, #383)

`vinaya check <name> | --all` ships as a runner plus an error contract, with the four core AEG gates (doc coverage, brief shape, coherence, dispatch readiness) expressed through the **same public interface** as custom checks — no privileged API (D-092, `Lock: YES`). This is the task that makes D-092's lock real rather than asserted: `tests/checks/no-privileged-api.test.ts` mechanically proves a core `CheckSpec` and a config-registered one carry no field the other cannot, and that `runChecks` has no branch on provenance.

- **`CheckSpec` — how a check declares itself (D-099).** `{ name, run, args?, scope: 'diff' | 'full', include?, timeoutMs? }`. `scope: 'diff'` declares "I only care about the diff"; the runner may skip such a check under `--diff-only` when none of its `include` globs match a changed file (recorded in the outcome list as `status: 'skipped'`, never silently dropped — a dropped check would read as a passing one). `scope: 'full'` checks always run (today: `coherence`, `dispatch-readiness` — both read live forge state, not the local diff). `include` is glob **scoping only**; the config grammar (below) forbids conditionals entirely.
- **The error schema, field-by-field (D-100).** One JSON line on stderr per finding: `{ schema: 1, check, severity: 'error' | 'warning', message, agent_recovery_prompt, file?, line? }`. `message` is the diagnosis — what is wrong. `agent_recovery_prompt` is the corrective **instruction**, addressed to the model that will act on it — never a restatement of `message`. Compare: `message: "packages/ui/topbar/Nav.tsx changed but its owning SKILL.md is not in the diff"` vs. `agent_recovery_prompt: "Read .claude/skills/ui-components/SKILL.md, apply your change, and commit both files in this PR."` A prompt that merely rephrases the diagnosis fails the whole reason D-100 exists — the ring-0 self-correction loop.
- **Exit-code semantics.** The exit code IS the verdict: `0` = pass, `1` = findings (`status: 'fail'`). Any other exit code, or a stderr line that fails to parse as a `CheckError`, is read by the runner as `status: 'error'` — a check that emits garbage must be loud, never a silent pass.
- **Runner-enforced timeouts.** `timeoutMs` on a `CheckSpec` is advisory; the **runner** spawns, races against the timer, and kills the child on expiry (`status: 'timeout'`). A check trusted to time itself out cannot be trusted at all — checks never self-enforce their own deadline.
- **No-network-by-default.** A check must not reach the network unless it is a declared exception. Today's two declared exceptions are the core `coherence` and `dispatch-readiness` checks (`scope: 'full'`) — both read forge facts through the two primitives `@atta/aeg-core` re-exports for this purpose (`fetchForgeFacts`, `fetchOpenIssuesByLabel`), never a hand-rolled forge client.
- **Config registration (D-092, D-109).** `vinaya.config.json`'s `checks` object registers any executable honoring the contract above: `{ "checks": { "<name>": { "run", "scope", "include"?, "args"?, "timeoutMs"? } } }`. Glob scoping (`include`) is permitted; conditional logic (`if`/`unless`/`except`, or any expression string) is **never** part of this grammar — complexity that a check needs escapes into the executable, by design. A malformed `checks` entry surfaces as a `status: 'error'` outcome naming the invalid key (never a silent `null` that would make `vinaya check --all` print green over a broken registration).
- **Stability guarantee (D-103).** The check contract (`CheckSpec`/`CheckError`/`CheckOutcome`, `CHECK_SCHEMA_VERSION`) is a versioned public surface — third-party plugins will be written against it. Additive evolution only: fields may be added; never removed, renamed, or retyped. `CHECK_SCHEMA_VERSION` bumps only on a breaking change to the schema shape itself.
- **`vinaya new check <name>`** scaffolds a self-contained, worked custom check into `./scripts/vinaya-checks/<name>.ts` — no dependency on `@atta/vinaya-cli`'s own source (it lives in the adopter's repo), runs unmodified through the runner, and emits one real `CheckError` out of the box.

**Known scope gap, recorded here rather than silently narrowed.** The core `dispatch-readiness` check's `priorIterationArchival` predicate always reports empty (trivially passing) — resolving it for real needs `listActiveIterationSlugs` to discover candidate prior iterations per project, which is not among the forge primitives this task's dependency boundary (`@atta/aeg-core` + `@atta/vinaya-sources` only) re-exports. Likewise the core `coherence` check runs A1, A3, T1, T2, T3, D1, R1, L1 (and the always-info L3) but not A2/L2/L4/L5, which need `fetchProvenance`/`listActiveIterationSlugs`/`listIssueMilestonesForSlug` — also not re-exported. Both are real, narrower-than-`bin/verify-dispatch.ts`/`bin/verify-coherence.ts` parity gaps, not re-derivations of the missing facts (D-087) — a future task exporting those primitives from `@atta/aeg-core` closes the gap without touching this task's contract.

## Forge writes (`vinaya-cli-v1`, task 5, #385)

`vinaya pr create | edit` and `vinaya issue create | edit` are the validated forge-write path: every write runs the full, **config-defined brief-schema validation LOCALLY, before any `gh` write** — prevention, not detection. A malformed body is refused at the CLI layer, in-session, before anything reaches the forge; the identical `@atta/aeg-core` validators run in CI purely as a backstop. The commands **adapt the semantics** of `packages/aeg-core/bin/open-pr.ts` / `open-issue.ts` — they never import them: those bins `process.chdir(REPO_ROOT)` and shell out to this repo's `bin/*` gate scripts, so importing them would drag this repo's layout into a distributable CLI. Instead, like `src/checks/bin/check-brief-shape.ts`, they call the aeg-core public exports and speak the versioned `CheckError` contract.

- **The config-defined brief schema (`briefSchema` in `vinaya.config.json`, D-087).** WHICH sections a `pr`/`issue` body must carry is expressed as **config, never hardcoded in the command code** — this repo's required-section set is just one instance (one derivation, N consumers). The schema key is `briefSchema: { pr?: { sections: [...] }, issue?: { sections: [...] } }`. Each section is declarative — no conditional grammar (D-109: no `if`/`unless`/`except`), any diff-conditionality living inside the built-in validator's code, never in the config:
  - `{ "builtin": "<name>" }` — runs the named battle-tested `@atta/aeg-core` validator. The names: `tier`, `testPlan`, `testPlanExclusivity`, `principalPlaceholder`, `surfaceMap`, `docUpdateList`, `worktreeStep0`, `stopConditions`, `autonomyClause`, `project`, `for`, `closesN`, `lockAck`, `premiseCoverage`, `issueRationale`. This repo's `pr` instance is the first fourteen (mirroring `checkBriefSections` + premise coverage); its `issue` instance is `issueRationale` (the eight-field Planner rationale, applied only to `iteration:*` task Issues).
  - `{ "heading": "…" }` / `{ "field": "…" }` / `{ "phrase": "…" }` — an adopter-authored generic matcher for their own required sections (a `## …` heading, a `Field:` header field, or a literal phrase anywhere). An adopter shapes their own brief schema through these without touching command code. If a validation this repo relies on cannot be expressed in this declarative, adopter-generic grammar, that is a config-contract gap to escalate — never a license to hardcode.
- **The refusal contract.** On any failure the command emits one `CheckError` JSON line per finding on stderr and exits 1 — the same versioned contract (`schema: 1`, `check`, `severity`, `message`, `agent_recovery_prompt`) the check engine defines (D-100/D-103). `agent_recovery_prompt` names the exact corrective `vinaya` command, never a restatement of `message` — engineering the ring-0 self-correction loop.
- **`--validate-only`.** Runs every gate, reports `PASS`, exits 0 **without writing** — the `[agent]`-testable path. `--json` envelopes the outcome (`{ schema: 1, data: { validated, written, … } }`).
- **Same-bytes body plumbing (#333).** A stream/heredoc body (`--body-file /dev/stdin`, process substitution) is empty on a *second* read by the time `gh` opens the original path, so the body is buffered ONCE, validated, then materialized into a fresh temp file whose path replaces the `--body-file` slot — `gh` reads the exact bytes this process validated, never an independent second read.
- **Gate-set-per-path — the forge is the truth on `edit` (#417).** On `create`, the diff context (changed files, lock-touch) comes from the local checkout, which IS the truthful source there. On `edit <n>`, that context is a property of the TARGET object, not of whatever checkout the command runs from: `pr edit` fetches the PR's real head branch + changed files (`gh pr view`); `issue edit` fetches the Issue's actual labels (`gh issue view`) and unions them with argv (argv is normally silent on edit). A failed forge fetch is a **hard refusal**, never a fall-back to the local checkout — the exact bypass that fall-back would reopen.
- **Not in v1.0 of this path (D-104).** The gh-shim / PreToolUse interception that would make these commands the *only* way to write to the forge is an explicit fast-follow, out of this task. This repo continues to use `packages/aeg-core/bin/open-pr.ts` as its own sanctioned path until that migration; `vinaya pr/issue` is the distributable, adopter-generic reference implementation.

## Renderer contract (`vinaya-studio-v1`, task 4, #389)

**The rule (D-087): Studio renders, it never re-derives.** Governance state enters Studio only through one of two permitted entry paths — `@atta/aeg-core`'s public API, **or** the `@atta/vinaya-sources` `StateSource` adapters. Both are legitimate; this is an OR, not a hierarchy — do not "fix" an aeg-core-direct call site into a `StateSource` one on the strength of this chapter alone. What both paths rule out is a third option: Studio computing any piece of governance state itself. The gates (`vinaya check`, and today `packages/aeg-core/bin/*`) compute governance state; Studio's only job is to render what they computed. If Studio ever re-derives any of it, Studio and the gates can disagree about the same repo — and a product whose dashboard contradicts its own gate has no product left.

**The one-way import corollary.** `apps/vinaya/web` must never import `apps/vinaya/cli` internals, and `apps/vinaya/cli` must never import web internals — either direction crossing the boundary would let one surface reach around the other's derivation and compute governance facts on its own. This is now mechanically enforced, not asserted in prose: `apps/vinaya/web/src/lib/import-boundary.test.ts` (vitest) walks every `.ts`/`.tsx` file under `web/src` and fails on any import/export statement whose specifier names `@atta/vinaya-cli` (including subpaths) or reaches relatively into `../cli/`; `apps/vinaya/cli/tests/import-boundary.test.ts` (bun test) is the converse, walking `cli/src` and `cli/tests` for `@atta/vinaya-web` or `../web/` reaches. Each package guards its own boundary and fails its own CI; the two tests intentionally do not share an imported helper — that import would itself cross the boundary they exist to defend.

**What is not a violation.** Fetching facts — plain I/O — in the web app is fine. `load-snapshot.ts` fetching forge facts over the network and handing them to `@atta/aeg-core`'s `deriveIteration` is the contract working as designed, not a breach: the derivation still happens inside aeg-core, not in Studio. The rule is about **derivation**, not about where an HTTP call lives. This is the distinction most likely to be misread: "Studio fetches data" is not the same claim as "Studio computes governance state," and only the second is forbidden.

## DiagramModel derivation (enforcement-derivation-v1 task 5, #506)

One pure library turns governance doctrine into a renderer-agnostic model every diagram consumer reads — Studio, `/the-harness` (task 4, #508), a CLI visualizer — so none re-implements the governance logic (D-087: one derivation library, N consumers).

- **Contract:** `deriveDiagramModel(doctrine, config, iteration): DiagramModel` (`packages/aeg-core/src/diagram-model.ts`, exported from `@atta/aeg-core`'s `index.ts`). Pure — zero I/O, zero `fs`/`node:` imports (aeg-core's purity charter, #372/#521). Doctrine arrives already-read as `DoctrineContent` (raw `enforcement.md` + roles/contracts markdown); config is the declarative `DiagramConfig` (ring-level + per-gate enable/disable booleans, `null` = nothing disabled); `iteration` is the `StateSource` live-context passthrough, carried on the model and **never** used to compute render-state.
- **Model shape:** `nodes` (kind `ring | gate | check | action | role | contract`, each with a kind-prefixed stable id, label, optional `ringIndex`, and a derived `renderState`), `edges` (`guards` gate→action, `performs` role→action, `produces`/`consumes` role→contract), `findings` (config keys that reference no real gate/check), and the passthrough `iteration`. **Geometry — radius, angle, colour, coordinates — is NOT in the model; the renderer owns it.** A ring index and a render-state are structural facts; a pixel is not.
- **A node's three text fields, and why they are three (`vinaya-pages-v1` task 4, #553):** `summary` is the rhetorical question (#551); `detail` is one plain sentence saying what the node does; `label` is its name. Each `detail` comes from its own source's `description` — `enforcement.md`'s `Description` column for gate/check, `description:` frontmatter for role/contract, the `ACTIONS` entry's field for action — so every kind reads in one register, because a reader cannot see what kind of node they clicked. `detail` is never `GateRow.spec`, the enforcement table's own "what must be true" column: that column is written to ENFORCE (17 of 31 rows cite a decision id, issue number or file path; the longest runs 2708 chars), which is correct for a gate and unreadable on a page. Rendering `spec` is the bug `description` exists to prevent; "Read more" is what carries a reader to it. This closed the gap #508's leaf-panel spec left — it listed `summary` and a link, with no field answering the question it asks.
- Every gate/check/action/role/contract node also carries an optional `summary` (a short, non-technical question, e.g. "Ever had someone push straight to main and nobody noticed?") — gate/check nodes additionally carry `category` (`ci`/`hook`/`event`, describing when the check fires relative to a bare repo with no governance installed) and role nodes carry `actorType` (`agent`/`human`/`either`, from the role's own pre-existing frontmatter). Added by `vinaya-pages-v1` task 3 (#551), consumed by task 4's (#508) drill panels.
- **Render-state is derived, never authored** (precedence top-down): `locked` when the doctrine row's `lock` column is non-empty (config can never override a lock, e.g. a principal/foundational gate); `disabled` when config disables it (per-gate `gates[slug] === false`, or the ring-level `ring1_forgeWriteInterception`/`ring2_asyncAudits` switch for that ring's checks); else `active`. Ring 0 has no ring-level switch (D-117) — only a per-gate entry can disable a ring-0 gate, and a locked one ignores even that.
- **DoctrineSource seam:** the library takes doctrine, not `aeg-root/` paths (D-111 — it must be packageable for adopters with no `aeg-root/`). The type `DoctrineSource` (`packages/aeg-core/src/doctrine-source.ts`, I/O-free, mirrors `StateSource`) is implemented by `createFileDoctrineSource({ root? })` in `@atta/vinaya-sources` (`src/doctrine-file-adapter.ts`), reading `<root>/enforcement.md`, `<root>/roles/*.md`, `<root>/contracts/*.md` over a configurable root (default `DEFAULT_GOVERNANCE_ROOT`, never a hardcoded literal).
- **No-drift substrate:** the derivation consumes the canonical `ACTIONS` and its `CROSSING_KEYWORDS` map (promoted into `actions.ts` this task) — the same list G3's crossing check reads — so gate→action edge counts can never drift from G3's completeness set (D-119). The markdown-table parser is likewise the one aeg-core-owned `markdown-table.ts` (promoted out of the web app this task); `registry-parse.ts` and the Vinaya `/aeg` renderer both sit on it.
- **Proof:** fixture tests (`diagram-model.test.ts`) assert the exact node set, a config-disabled gate `disabled`, a locked gate `locked` even when config also disables it, an unknown config key surfacing as exactly one finding, and edge counts matching `ACTIONS`; a real-`aeg-root/` cross-check asserts every `into-github` action gets ≥1 `guards` edge, every `performedBy` role resolves to a role node, and node ids are globally unique.
- **Out of scope for this task:** the renderer (pages own SVG/geometry — the rings-drilldown application landed as `vinaya-pages-v1` task 4, #508); wiring per-gate switches into the CLI's `VinayaConfigSchema` (a later CLI task — `DiagramConfig` is this task's only config surface).
- **Render decision (`vinaya-pages-v1` task 4, #508):** `/the-harness`'s leaf panel shows `category`/`actorType` as a neutral filled `Badge` — one fill for every value, never per-value color-coded, and distinct from the diagram's own per-ring visual distinction (an unrelated, pre-existing concept). #508's amendment specifies `variant='outline'`; outline renders near-invisible against this page's cream background, so the filled default is a deliberate departure on that one point, preserving the brief's actual constraint (no per-value colour coding) rather than its literal wording.
