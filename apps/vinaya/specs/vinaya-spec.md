# Vinaya — Product Spec (seed)

Status: draft

First mention of this file. Captures the ratified and pending decisions that define Vinaya so far. Some of them are still awaiting ratification — this doc summarizes intent, it is not itself a ratified commitment. Each decision's full reasoning lives in the pull request that made it.

## What Vinaya is

A governance layer for AI coding agents: deterministic checks every agent must satisfy before merge, installed with `npx @attalabs/vinaya init`. Vinaya doesn't block agents — it redirects them into a governed flow, so a human reviews judgment, not compliance. "Vinaya" means "discipline" / "the rules of conduct" in Pali.

## Architecture

- **Entry point:** `npx @attalabs/vinaya init`; site at `vinaya.attalabs.dev`. The command resolves for real — the CLI is published to the public npm registry as `@attalabs/vinaya` (see § Distribution). No editor extension; GitHub App (deployed Studio / org installs) deferred.
- **Vinaya Studio:** visual proof of derived status, not the acquisition hook. One derivation library with N consumers (CLI gates, local Studio, future deployed Studio); Studio renders `check --json`/forge-facts output and never re-implements governance logic; no database. Ships as a separate optional npm package `@vinaya/studio` — in-repo, Studio is `apps/vinaya/web`. Deployment roadmap: Phase 1 (v1.0) local Studio only; Phase 2 generated Projects view; Phase 3 (deferred) deployed self-hosted stateless read-only Studio on a GitHub App token; Phase 3½ dogfood-as-demo over Vinaya's own public repo.
- **Enforcement hierarchy:** deterministic checks → CI + branch protection (the guarantee) → git hooks (ring 0, universal) → forge-write interception (ring 1, opt-in accelerator only, never load-bearing).
- **Substrate:** GitHub Issues + labels are machine truth; Projects v2 is an optional generated view, never a source of truth; `init` prints the recommended branch-protection command and never applies it.
- **Custom checks:** any executable honoring the §5 error contract, registered in `vinaya.config.json`. Core gates use the same interface — no privileged API. Glob scoping is allowed; conditional logic (if/unless/except) is forbidden.
- **Error contract:** every check error carries `agent_recovery_prompt` — a corrective instruction for the executing model, not a restated diagnosis. The check contract + error schema are a versioned public surface.
- **State placement:** process/work state lives on the forge (Milestones, labels, comments); low-churn parseable artifacts (project registry, doc-owners) stay plain files wrapped in a code-free workspace package; universal AEG doctrine ships inside the npm package with a scaffolded, visible pointer in the adopter's repo.
- **Repo-root resolution is a deployment constraint, not just a lookup:** the site's doctrine-reading routes (`/docs/harness`, `/docs/reference`) are handed no root — they locate the repo by walking up from the working directory for a **marker file** (`vinaya.config.json`; the Studio's registry reader walks for `.vinaya/projects.md`). On a serverless host only traced files exist at runtime, so **the marker file is a deployment input in its own right** and must be declared alongside the doctrine itself in the web app's file-tracing config. Omit it and the walk fails before any doctrine is read — the routes 500 in production only, with a green build and a clean local run. Renaming a marker is therefore a two-place change. The failure this actually produced was subtler than a forgotten rename: one commit moved the repo-root marker **and** introduced a second marker for the registry reader, updated the tracing declaration for the second, and never declared the first — so the change looked complete, built green, and 500ed only the routes that walk for the marker nobody declared. The coupling is mechanized rather than documented: a guard test discovers the readers that walk and parses each one's marker out of source and fails when one is not declared for tracing, which is the check that was missing both times.

## Distribution (#700)

- **Published name:** `@attalabs/vinaya` — scoped, public, on the public npm registry (`npm publish --access public` from `apps/vinaya/cli`). **The bare name `vinaya` is unobtainable, not merely untaken.** The registry 404s for it, but npm's automated typosquat filter refuses the publish outright — `403 Package name too similar to existing package vinyl` — and that filter cannot be tested except by attempting a publish. Discovered at publish time on 2026-07-29; Principal chose the `attalabs` scope over npm's suggested `@daniboomerang/vinaya` (personal-username scope reads as a hobby package) and over blind attempts at `vinaya-cli`/`vinaya-harness` (the filter is opaque, and each attempt is an irreversible publish if it succeeds). Scoped names bypass the filter. **The installed command remains `vinaya`** — `bin.vinaya` is unchanged, so only the install line carries the scope. Every surface printing an install command therefore says `npx @attalabs/vinaya init`; a surface still printing the bare name is a defect, since that command 404s. Appealing to npm for a typosquat exception remains open as a later route to the bare name.
- **Node target, not bun.** The four advertised install commands are package-manager invocations, not runtime choices — npm/pnpm/yarn would happily install a bun-shebang binary and then fail at exec on any machine without bun, after the user already ran the command from the website. The published artifact is therefore a single Node-executable ESM bundle (`dist/index.js`, `#!/usr/bin/env node`, built by `scripts/build.ts` via `bun build --target=node`), `engines.node >= 20`. Bun remains the build toolchain; it is no longer a runtime requirement.
- **Dependency shape.** The whole `@atta/*` workspace graph (`@atta/aeg-core`, `@atta/aeg-forge-state`, `@atta/aeg-types`, `@atta/vinaya-sources`) is inlined by the bundle; the only declared runtime dependencies are the two genuinely external ones, `zod` and `gray-matter`. The build script derives its externals list from the manifest's non-`workspace:*` dependencies rather than a hand-written list, so a later real dependency cannot be silently inlined.
- **Tarball contents** are an explicit `files` allowlist: `dist/`, `templates/` (read at runtime by `vinaya new check`), `aeg-root/` (the bundled doctrine subset, read at runtime by the `doctrinePointer()`-generated `VINAYA.md`; see the Doctrine bundling entry in the Install-lifecycle chapter below), `README.md`. No `src/`, no `tests/`, no `tsconfig.json` — a published version cannot be recalled, only deprecated, so the allowlist is the last line against an over-broad artifact.
- **License: Apache-2.0** (`apps/vinaya/cli/LICENSE` and `packages/aeg-core/LICENSE`, both full canonical text; npm ships the CLI's regardless of the `files` allowlist). Relicense from AGPL-3.0-only, Principal decision 2026-08-06 (Type 1, ratified) — sole copyright holder, zero external contributors, both OSS category competitors (Agentic OS, GitHub Spec Kit) are MIT, and AGPL blocked the adoption that is Vinaya's entire thesis. This supersedes the original AGPL-3.0-only decision recorded in this same bullet on 2026-07-29. Apache-2.0 is permissive, not copyleft — there is no share-alike obligation on derivatives; anyone may use, fork and modify Vinaya, including closed forks. Note this licenses the inlined `@atta/*` graph too, since the bundle distributes it. **Only `packages/aeg-forge-state` and `packages/aeg-types` still carry no LICENSE file of their own** — `packages/aeg-core` now has its own. Trademark on the "Vinaya" name is a separate instrument and does not exist yet; no license prevents a rebranded fork.
- **Deliberately not published:** `@vinaya/studio` (the `{ kind: 'missing' }` branch in `resolveStudioTarget` stays a stub) and the `@atta/*` packages as standalone registry packages — they ship inlined; their standalone extraction is #546's question. The 15 core AEG check bins ARE in the tarball, bundled — see Correction 7 in the Check engine chapter below for why an earlier `src/`-only shape left them unreachable through a real `npm install`, and the `dist/checks/bin/*.js` fix.
- **Published-lifecycle proof script (#705).** `apps/vinaya/cli/scripts/verify-published-lifecycle.ts` (`bun run verify-published-lifecycle`) installs `@attalabs/vinaya` from the real public npm registry into a scratch directory outside this repo and exercises every `status: 'shipped'` entry in `@atta/vinaya-sources`' `COMMANDS` registry against that installed artifact — never local source. Three deliberate non-green outcomes are asserted by design, independent of publish state: `check --all` outside a workspace reports 4 `status: 'error'` outcomes, never a crash; `studio` reports the clean `missing` refusal, never a real server; forge-write commands (`pr`/`issue` `create`/`edit`) run `--validate-only` only, with `issue edit` exempted (its label-fetch reaches the network unconditionally, even under `--validate-only`) — the script's own source carries no non-`--validate-only` `gh` invocation. **As of 2026-08-06, running this script against the currently-published `@attalabs/vinaya@0.1.0` is EXPECTED to exit non-zero**, naming four known, tracked gaps (issue #705 and its follow-up comment): `demo break` and `waiver` (#387) are unrecognized commands, `check --all` reports 5 checks instead of 4, and `init` never writes `.vinaya/doc-owners` (#665) — all four share one root cause, the published artifact predating source changes that landed after 2026-07-29, not four separate defects. A republish resolves all four at once; the script needs no change when that happens.
- **CI branding + decoupling audit (#721).** This repo's own Vinaya-mechanism CI now reads Vinaya-branded in the Actions tab (`forge-lifecycle.yml` → `Vinaya: Gate Suite`, `archivist.yml` → `Vinaya: Archivist`, `review-gate.yml` → `Vinaya: Review Gate`; job ids/job-level names unchanged); the paired decoupling audit found `packages/aeg-forge-state/src` clean but two genuine hardcoded attalabs-app-path literals in `packages/aeg-core/src`'s shipped logic (`FROZEN_ARCHIVES` in `file-classify.ts`, `READER_FACING_PREFIX` in `reader-resolvable-prose.ts`), tracked as a real architecture gap in #724 rather than patched there. **`FROZEN_ARCHIVES` has since been removed** — the suffix rule already subsumed every path it held, so the coupling was deletable with no behavior change; **`READER_FACING_PREFIX` has since been parameterized** — `classifyProseFile` and its callers in `reader-resolvable-prose.ts` now take the reader-facing prefix/suffix as caller-supplied arguments, with the one real consumer (`check-reader-resolvable-prose.ts`) passing its own literal in — so #724 is fully closed. ## Trust surface

`init` is non-destructive by contract (full diff → confirm → install; `--dry-run`); `demo break` is the productized belief moment (refusal → self-correction → pass, see its own chapter below); `waiver` is the only forge-authenticated escape hatch (see its own chapter below); `eject` restores stock in one command; `doctor` is treated as a product (diagnoses everything, mutates nothing).

- **Studio cannot lie by omission.** When live forge enumeration fails (rate limit, network, `gh`/token missing, or `resolveRepo()` unresolvable), Vinaya Studio's tranche lists render an explicit "live forge state unavailable" warning banner — never a truth-shaped empty "No active tranches." state. The flag (`TrancheLists.forgeAvailable`, `tranchesForProject().forgeAvailable` in `apps/vinaya/web/src/lib/repo-state/read-root.ts`) is derived per-request from that request's failures only (Studio stores nothing); the legacy `completed/*.md` supplement is not a failure and never trips the banner. The genuine (forge-reachable) empty state is a first-class state, not an aside: on a project page it renders as a `Card` + lucide `Inbox` block under the tab strip rather than a small muted line, on the same surface and spacing as a populated tranche card (#627). The two states stay mutually exclusive — the emptiness is explained exactly once, by whichever surface actually knows why: **each tab consults its own `ForgeStatus`** — `ProjectTranchesTabs.tsx` passes a null hint whenever that tab's fetch did not succeed (`forge.active.kind`/`forge.archived.kind`), and the grid then renders nothing at all, leaving the banner as the sole explanation, so a forge failure can never acquire a confident "nothing here" panel on top of it. The Archived tab is included deliberately: it used to hardcode its hint string, which is exactly how a false "No archived tranches yet." survived a failed fetch.

## Check engine (#383)

`vinaya check <name> | --all` ships as a runner plus an error contract, with 15 core AEG gates — `brief-shape`, `doc-coverage`, `coherence`, `dispatch-readiness` (task 3, #383), plus `closes-n`, `single-plan-pr`, `test-plan`, `no-disk-state`, `registry-gates` (a collapsed G1–G5), `review-gate`, `branch-topology`, `dead-branch-push`, `first-push-dispatch`, `doc-coverage-push`, `issue-assignment` (task 4, #760 — see Correction 4 below) — expressed through the **same public interface** as custom checks — no privileged API. This is the task that makes real rather than asserted: `tests/checks/no-privileged-api.test.ts` mechanically proves a core `CheckSpec` and a config-registered one carry no field the other cannot, and that `runChecks` has no branch on provenance. (`reader-resolvable-prose` is still NOT part of this adopter-facing set — see Correction 2 below.)

- **`CheckSpec` — how a check declares itself.** `{ name, run, args?, scope: 'diff' | 'full', include?, timeoutMs? }`. `scope: 'diff'` declares "I only care about the diff"; the runner may skip such a check under `--diff-only` when none of its `include` globs match a changed file (recorded in the outcome list as `status: 'skipped'`, never silently dropped — a dropped check would read as a passing one). `scope: 'full'` checks always run (`coherence`, `dispatch-readiness` — both read live forge state). `include` is glob **scoping only**; the config grammar (below) forbids conditionals entirely.
- **The error schema, field-by-field.** One JSON line on stderr per finding: `{ schema: 1, check, severity: 'error' | 'warning', message, agent_recovery_prompt, file?, line? }`. `message` is the diagnosis — what is wrong. `agent_recovery_prompt` is the corrective **instruction**, addressed to the model that will act on it — never a restatement of `message`. Compare: `message: "packages/ui/topbar/Nav.tsx changed but its owning SKILL.md is not in the diff"` vs. `agent_recovery_prompt: "Read .claude/skills/ui-components/SKILL.md, apply your change, and commit both files in this PR."` A prompt that merely rephrases the diagnosis fails the whole reason exists — the ring-0 self-correction loop.
- **Exit-code semantics.** The exit code IS the verdict: `0` = pass, `1` = findings (`status: 'fail'`). Any other exit code, or a stderr line that fails to parse as a `CheckError`, is read by the runner as `status: 'error'` — a check that emits garbage must be loud, never a silent pass.
- **Runner-enforced timeouts.** `timeoutMs` on a `CheckSpec` is advisory; the **runner** spawns, races against the timer, and kills the child on expiry (`status: 'timeout'`). A check trusted to time itself out cannot be trusted at all — checks never self-enforce their own deadline.
- **No-network-by-default.** A check must not reach the network unless it is a declared exception. Task 3 shipped two declared exceptions, `coherence` and `dispatch-readiness`; task 4 (#760) adds nine more that legitimately shell to `gh` or the same two forge primitives — `closes-n` (reverse `Closes #N` lookup), `single-plan-pr` (other open PRs' files), `registry-gates` (G4's citation-resolution probe), `review-gate` (PR comments/labels/timeline), `branch-topology`, `dead-branch-push`, `first-push-dispatch` (all three read the forge for the current branch's PR/topology state), `doc-coverage-push` (same diff-only C5 evaluation as `doc-coverage`, no extra network surface), and `issue-assignment` (reads AND writes — see Correction 4). Every network-reaching check still goes through `@atta/aeg-core`'s re-exported primitives (`fetchForgeFacts`, `fetchOpenIssuesByLabel`, `fetchTaskIssueRefs`) or a direct `gh` shell-out, never a hand-rolled forge client.
- **Config registration.** `vinaya.config.json`'s `checks` object registers any executable honoring the contract above: `{ "checks": { "<name>": { "run", "scope", "include"?, "args"?, "timeoutMs"? } } }`. Glob scoping (`include`) is permitted; conditional logic (`if`/`unless`/`except`, or any expression string) is **never** part of this grammar — complexity that a check needs escapes into the executable, by design. A malformed `checks` entry surfaces as a `status: 'error'` outcome naming the invalid key (never a silent `null` that would make `vinaya check --all` print green over a broken registration).
- **Stability guarantee.** The check contract (`CheckSpec`/`CheckError`/`CheckOutcome`, `CHECK_SCHEMA_VERSION`) is a versioned public surface — third-party plugins will be written against it. Additive evolution only: fields may be added; never removed, renamed, or retyped. `CHECK_SCHEMA_VERSION` bumps only on a breaking change to the schema shape itself.
- **`vinaya new check <name>`** scaffolds a self-contained, worked custom check into `./scripts/vinaya-checks/<name>.ts` — no dependency on `@attalabs/vinaya`'s own source (it lives in the adopter's repo), runs unmodified through the runner, and emits one real `CheckError` out of the box.

**Known scope gap, recorded here rather than silently narrowed.** The core `dispatch-readiness` check's `priorTrancheArchival` predicate always reports empty (trivially passing) — resolving it for real needs `listActiveTrancheSlugs` to discover candidate prior tranches per project, which is not among the forge primitives this task's dependency boundary (`@atta/aeg-core` + `@atta/vinaya-sources` only) re-exports. Likewise the core `coherence` check runs A1, A3, T1, T2, T3, D1, R1, L1 (and the always-info L3) but not A2/L2/L4/L5, which need `fetchProvenance`/`listActiveTrancheSlugs`/`listIssueMilestonesForSlug` — also not re-exported. Both are real, narrower-than-`bin/verify-dispatch.ts`/`bin/verify-coherence.ts` parity gaps, not re-derivations of the missing facts — a future task exporting those primitives from `@atta/aeg-core` closes the gap without touching this task's contract.

### Correction 2 (2026-08-04) — repo-root resolution (#713)

A live `[principal]` test-plan run on the trust-surface PR found `demo break` (and therefore any real `npx vinaya check` an installed hook runs) could not complete outside this monorepo, and reproduced a real state leak — a fixture repo's `vinaya check` run reported on THIS repo's own tranche/branch facts instead of the fixture's. Three root causes, all fixed in the same PR:

1. **Bundled-path resolution.** `registry.ts`'s `BIN_DIR` was computed from a fixed `join(dirname(...), '..', '..')` walk — correct only when running unbundled from `src/checks/`. Once bundled into a single-file `dist/index.js` (what a real `npm install` ships), that fixed depth lands one directory short, so every core check fails with "executable ... was not found on PATH." Fixed by extracting the walk-up-to-`package.json` helper already proven in `doctor.ts`/`new-check.ts` (copy-pasted twice before this fix) into one shared `lib/package-root.ts` export, parameterized by the calling module's own `import.meta.url`, used by all three call sites.
2. **The state leak.** `check-coherence.ts` and `check-dispatch-readiness.ts` both `chdir`'d to wherever the CLI's own script physically lives (this monorepo from source; the CLI's install location once bundled) before shelling `git remote get-url origin` / `git rev-parse --abbrev-ref HEAD` — never the repo `vinaya check` is meant to evaluate. The runner's `spawn()` sets no explicit `cwd`, so it already inherits the caller's cwd correctly; the `chdir` was not just wrong, it was unnecessary. Fixed by deleting both `REPO_ROOT` constants and `chdir` calls outright — no replacement logic needed.
3. **A non-portable check registered as if generic.** `check-reader-resolvable-prose.ts` hardcodes this monorepo's own doctrine layout (`aeg-root/glossary.md`, `aeg-root/tranches/completed/`) and its own marketing-site source path (`apps/vinaya/web/src/app/(site)/**/page.tsx`) — a scope-registration bug, not a pathing one, and no `packageRoot()`-style fix makes those paths exist in an arbitrary adopter's repo. Fixed by removing its entry from `coreCheckRegistry()` (5 checks → 4: `brief-shape`, `doc-coverage`, `coherence`, `dispatch-readiness`). The bin and its underlying `@atta/aeg-core` logic are left in place as a potential internal doc-quality tool for this repo; wiring that is a separate, unstarted obligation.

Regression coverage (`tests/checks/repo-root-resolution.test.ts`): `packageRoot()` resolves to the same package root from both a synthetic "source-depth" and "bundled-depth" fixture; every real `coreCheckRegistry()` bin path exists on disk; `coreCheckRegistry()` no longer contains `reader-resolvable-prose` and a bare fixture repo (no `aeg-root/`) runs `vinaya check --all` clean; and — the direct regression for the leak itself — `check-coherence.ts`/`check-dispatch-readiness.ts` run with `cwd` set to a disposable fixture repo (a distinct fake remote and branch) resolve and report on the FIXTURE's own identity, never this monorepo's. Verified against the actual pre-fix code (reverted locally, confirmed the leak test fails by reproducing the exact real-world symptom — this repo's own dependency-gate message leaking into the fixture's output — then restored the fix).

### Correction 8 (2026-08-07) — a brand-new adopter repo could never make its first commit

A third real bug, found re-running the dress rehearsal against the real, fixed `0.1.2` publish: the pre-commit hook refused a fresh repo's very first `git commit` outright, reporting `coherence`/`dispatch-readiness` as `error` (not a real finding — the runner's own `status: 'error'` classification, meaning "the check emitted something that isn't a `CheckError`"). Both adapters' `git()` helpers (`check-coherence.ts`, `check-dispatch-readiness.ts`) built their own copy of the shared `try { execFileSync(...) } catch { return '' }` pattern every other check bin already uses, but WITHOUT the `stdio: ['ignore', 'pipe', 'pipe']` option those others carry. On a zero-commit repo, `git rev-parse --abbrev-ref HEAD` (used to derive the current branch, correctly caught and handled as "not a task branch, bypass") still writes its raw `fatal: ambiguous argument 'HEAD'` text to the check's real stderr stream before the JS `catch` block ever runs — `execFileSync`'s default `stdio` inherits, it does not silently suppress. `runner.ts` treats every stderr line as a candidate `CheckError` JSON payload; one non-JSON line sets `malformed = true` and reports `status: 'error'` regardless of the check's real (correct, exit-0, silent-bypass) behavior — misreporting a clean pass as a crash, and blocking the pre-commit hook on every project's very first commit.

Fixed by adding the same `stdio: ['ignore', 'pipe', 'pipe']` every other check bin's `git()` helper already carries — `check-doc-coverage.ts`'s own doc comment names this exact failure mode explicitly, which is what made it findable. Verified against a real packed `0.1.2` tarball, installed as a real local dependency (so the pre-commit hook's own `npx --no-install` resolves it, not a stale registry cache), on a genuinely fresh zero-commit repo: the real `git commit` now succeeds, all 15 checks pass.

**The lesson, stated plainly, twice now:** the specific class of bug that keeps surviving review is "correct JS-level logic, undermined by a process-boundary detail (a `files` allowlist, a `stdio` default) invisible from inside the monorepo." Local-source testing, and even a first real packed-tarball test, can each individually miss this — only testing the FULL realistic sequence (a truly fresh, zero-commit adopter repo, first commit included) on the ACTUAL locally-resolved package surfaces it.

## Configuration architecture (design — implementation tranche #774–#785)

**Status: design, frozen at v11 (2026-08-07) after nine external review rounds, approved for implementation.** Landed so far: the `env` model's grammar, construction, and audited core declarations (task 2, #775 — Correction 9), the default-spawn flip onto it (task 3, #776 — Correction 10), and the checks-side resolver plus `vinaya check --plan` / `--plan --json` and the namespace grammar (task 4, #777 — Correction 11 below), all feeding `--plan` only. Still design-only, not built yet: execution wiring the resolver into `vinaya check`'s real run (task 5) and the roles config block — schema, resolution, rendering-ID collision check (task 6). Checks and roles/contracts share one registry-resolution model — identity, resolution states, namespacing, fail-closed validation, one resolver — because the *algorithm* is shared even though the *data* isn't (checks are executable specs a runner consumes; roles are markdown contracts a renderer consumes). This chapter is that model, derived from the frozen design for implementation; the tasks that build it (#775–#785) own the mechanics of shipping it in stages.

### The gap this closes

Today's real behavior, verified against the code above: `coreCheckRegistry()` returns 15 unconditional entries (`check.ts:76`, `const allSpecs = [...coreCheckRegistry(), ...customSpecs]` — a flat concat). **No override capability exists** — a `vinaya.config.json` entry named `brief-shape` does not replace the core check, it runs alongside it. Every check, core or custom, is `spawn`ed with no explicit `env` (`runner.ts`), so the child inherits the parent's entire environment — every token, every secret, whether the check needs it or not; a documented gap in the runner's own comments, not a surprise finding. Roles have no config surface at all — `DoctrineSource` (`packages/aeg-core/src/doctrine-source.ts`) already lets the *whole* doctrine root be swapped (`createFileDoctrineSource({ root? })` in `@atta/vinaya-sources`), but there is no way to override one role while keeping the other seven, and no way to register a new one. And the hierarchical config loader (`config.ts`'s `findLocalConfig`/`configPath`) falls back to `~/.vinaya/config.json` — a file outside any git repo, never PR-reviewed, invisible to CI — which can register `checks` today with the same authority as the repo-local file.

### The three resolution states

Every check and role ID resolves to exactly one of three states — the machine-facing vocabulary, used everywhere (the resolver, `--plan`/`--plan --json`, this chapter):

| State | Meaning | Set by |
|---|---|---|
| `default` | Shipped with Vinaya, running unmodified — no config entry claims this ID. | Nobody; the starting state of every core ID. |
| `overridden` | A config entry currently claims a core ID and satisfies its contract. | A team pointing a config entry at their own implementation. |
| `additive` | A wholly new, namespaced entry Vinaya has no opinion on. | Purely opt-in. |

These are resolution states, not permissions — the resolver has exactly two branches (key matches an existing ID → override it; key doesn't match → additive), and nothing refuses an override attempt on the grounds that a core ID is "protected." A core ID that is `default` today becomes `overridden` the moment a config entry claims it; every core entry publishes an override contract from the moment it ships. A true non-overridable tier (e.g. a check verifying the resolver's own contract validation wasn't bypassed) is a real, separate mechanism this design does not build — a `protected: true` flag the resolver would check before accepting any override attempt for that ID.

**The core-ID list, for namespace-collision purposes, is the current `coreCheckRegistry()` set — all 15 names**: `brief-shape`, `doc-coverage`, `coherence`, `dispatch-readiness`, `closes-n`, `single-plan-pr`, `test-plan`, `no-disk-state`, `registry-gates`, `review-gate`, `branch-topology`, `dead-branch-push`, `first-push-dispatch`, `doc-coverage-push`, `issue-assignment` (see the Check engine chapter's Correction 4 above for how the last eleven joined the first four). `reader-resolvable-prose` stays out of this set — its registry comment explains why (it hardcodes this monorepo's own doctrine layout) — so it is not part of the override-collision surface below; it becomes a candidate core ID only once parameterized for adopter use, a separate, unstarted obligation.

**The core role IDs** (verified against `aeg-root/roles/*.md` frontmatter) are the eight real `role_id` values: `archivist`, `brief-author`, `developer`, `planner`, `principal`, `reviewer`, `security`, `tranche-archivist`.

### Namespacing

- A config key that exactly matches an existing core ID (case-sensitive, no prefix) is an **override attempt**: it must satisfy that ID's published contract, or the resolver refuses to load — fail closed, not silently ignored.
- Any other key **must contain exactly one `/`** — both segments non-empty, matching `[a-z0-9][a-z0-9-]*`; the prefix `vinaya` is reserved (exact segment match — `vinaya/x` is rejected, `vinayatools/x` is fine). A bare key with no `/` that matches no core ID is a config error, never silently treated as additive. This is a monotonicity guarantee: upgrading Vinaya must never change which checks run in an adopter's repo, which only holds if a future core ID can never silently collide with an adopter's additive one.

### Resolution algorithm

One resolver, run once at the start of `vinaya check` and exposed directly via `vinaya check --plan` (prints the resolved table without running anything):

```
resolved = core_registry (unconditional)
         ⊕ overridden entries from config (contract-validated, replace in place)
         ⊕ additive entries from config (contract-validated, appended, namespaced)
```

A malformed override or additive entry fails the whole run loudly (`FAIL_CLOSED`) — it never silently falls back to the default or drops the entry, because a partially-applied ruleset that looks green is worse than a loud refusal. Registry IDs are globally unique after resolution; precedence is `core registry → matching override → additive append`, deterministic and order-independent with respect to config-file key order. An override is a **complete replacement of the spec, never a patch** — nothing (not `include`, not `scope`) is inherited from the replaced default.

For roles, the config key (the *registry* ID, namespaced for additive entries) and the file's `role_id` frontmatter (the *rendering* ID, always slash-free — what `DiagramModel` and everything downstream sees) are decoupled identifiers with different jobs: for an override, `role_id` must equal the config key exactly; for an additive role, `role_id` must equal the key's segment after the `/`. The resolver additionally rejects a rendering-layer collision the namespace can't see on its own — an additive `role_id` matching a core role's, or two additive roles from different namespaces rendering to the same id.

### The `env` model — the security fix

Today's spawn inherits the full parent environment. The fix builds an explicit `env` object per check: a **fixed safe baseline** (`PATH`, `LANG`, `HOME`, `HTTPS_PROXY`, `HTTP_PROXY`, `NO_PROXY`, `TMPDIR` — the proxy vars and `TMPDIR` exist so a network-declaring check behind a corporate proxy fails fast instead of hanging to timeout; none of these carry secrets worth guarding) plus the check's declared allowlist, by **expansion, not a literal spread** (a spread can't express the fourth form below — the child must receive every set member under its own name).

Four declared forms, keyed by var name:

- `true` — required passthrough; absent from the caller's environment synthesizes a `CheckError` before the check even spawns.
- `{ optional: true }` — passthrough if set, simply absent from the child otherwise, never fatal. Exists because a check declaring a CI-only secret as `true` would hard-block `git push` on every developer laptop that hasn't set it — a structural ring-0/ring-1 disagreement.
- a literal string — set exactly as written, never interpolated (`spawn` takes an explicit `env` object, no shell expands `$VAR`).
- `{ anyOf: [...] }` — an either/or requirement (e.g. `JIRA_TOKEN`-or-`JIRA_PAT`) with no deeper fallback; at least one member must be set, else a synthesized `CheckError`, same as `true`. Every set member passes through under its own name. The Record key must be one of its own members (preserves the key-is-a-real-var-name invariant everything else relies on); ≥2 unique members are required, or it's `true` wearing a costume. This form is **adopter-facing only**.

**Core checks declare `{ optional: true }` throughout, not `anyOf`** — this is the one item in this design that was audited to the wrong thing once and corrected on code evidence, and the corrective rule is now load-bearing: **the env audit quotes each bin's absence-handling line next to its declaration.** `resolveToken()` (`coherence`, `dispatch-readiness`) is a three-tier fallback — `GITHUB_TOKEN` → `GH_TOKEN` → a `gh auth token` subprocess — so `anyOf` on the token pair would hard-fail pre-spawn exactly the laptop that works today with neither var set but `gh` logged in. `doc-coverage`'s PR-body read falls through to `''`, the normal case at ring 0 where no PR exists yet. `brief-shape` reads a single `PR_BODY` with no paired var at all. The constraint is behavior preservation, not maximizing pre-spawn coverage — zero pre-spawn coverage of core is the *correct* outcome, because every core bin already carries deeper absence-handling the env grammar can't see.

Declared entries can override a baseline key's value but cannot remove one; there is no `false` form. `env` values live in a committed file — a literal must never carry a secret; `vinaya doctor` warns on a high-entropy literal as a backstop, and on a literal `"true"`/`"false"` (almost certainly meant as the boolean passthrough form).

**Threat model, stated honestly:** this is least privilege against *accidental* exposure by trusted local code, not a sandbox. `HOME` is in the baseline, so a deliberately malicious check still reads `~/.config/gh/hosts.yml` or SSH keys off disk regardless of its `env` declaration — the defense against a malicious check is PR review of the check's code, which is why every pointer in this design stays a local, relative, repo-tracked path (Out of scope, below).

### `vinaya check --plan` / `--plan --json`

Prints the resolved registry — one glance answers both "what's installed" and "what did we change." Human table columns: `NAME`, `STATE`, `SOURCE`, `ENV` (an `anyOf` group renders as `NAME|ALT`, alongside the `?` marker for optional). The `--plan --json` schema: `{ schema: 1, checks: Record<name, { state, source, env: Record<name, 'passthrough'|'optional'|'literal'|'anyOf'>, envAnyOf?, scope }>, roles: Record<id, { state, source, renderId }> }` — `env` labels how a value resolves, never the actual value, since a security reviewer auditing the plan needs to see "reads the caller's real token" vs. "sets a fixed string." **`FAIL_CLOSED` never swallows `--plan`** — a broken config is precisely when the table matters most, so `--plan` always renders, marking failing entries inline and exiting non-zero.

The resolver ships as a pure function feeding `--plan` **one release before** execution rewires onto it — so `--plan` previews a change a full release before it takes effect, rather than arriving simultaneously with the behavior it exists to preview.

### The role contract

Every role today is YAML frontmatter (`role_id`, `description`, `actor`, `performs`, `refuses_when`, `summary`, plus `title`/`order` consumed by `DiagramModel`'s `extractRole`) followed by a `## The short version` section. The structural contract for a replaceable or additive role: all six frontmatter keys present and non-empty, `title` and `order` present (both optional in the extractor but required here — a role missing them renders unnamed and unordered, bad enough that a contract-validated override should not permit it), and a non-empty `## The short version` heading. Validation is **structural only** — no semantic check of field content, since that would require understanding the meaning of every possible custom role. A role override, like a check override, is a complete replacement — no frontmatter field is inherited from the replaced core role.

**No grace period for roles**, unlike the checks-side namespace flip below: roles config is wholly new, with no existing bare-key population to protect, and a roles grace period is unimplementable anyway — checks' grace period works because the legacy flat-concat execution path keeps running during the warn window; roles have no legacy path, so "warn" would mean either failing anyway or silently dropping an entry, which this design forbids. Roles fail closed from day one.

### Rollout mechanics — two flips, separate minors, env first

Both breaking changes ship warn-then-flip, in this order, never in the same minor:

1. **The `env` allowlist.** First release: warn-only — spawn still inherits the full environment; the runner and `vinaya check`'s own output warn on every env-pattern-positive check lacking an `env` block. Next minor: the default flips to baseline + allowlist.
2. **Namespace enforcement.** The resolver, fail-closed validation, and `--plan`/`--plan --json` ship as a pure function one release ahead of execution (above). `vinaya doctor` warns for one minor version on every un-namespaced additive key ("this key will be rejected in the next release — rename to `<yourname>/x`") before the hard `FAIL_CLOSED` rejection ships.

An adopter tracking minors sees one behavior change at a time; an adopter skipping versions can still land on both in one upgrade — unavoidable with any versioned scheme.

### Core IDs as a public compatibility contract

Renaming or removing a core check or role ID — or shipping a new core role whose ID a plausible adopter namespace would render to — is a **major-version event**, the same discipline as removing a field from a versioned API. This is what makes overriding a core ID safe to build on: an adopter overriding `brief-shape` is pinning a name the core has promised not to break inside a major.

### Explicitly out of scope for this design

Remote sources (`npm:`, `github:`) — every pointer here is a local, relative path inside the adopter's own repo, reviewed the same way any other code change is. OS-level sandboxing. A signing/registry mechanism for overrides — ordinary PR review is the approval trail for a local-file-only model. Per-contract override/additive for the 6 contract files — contracts stay whole-doctrine-root-only in v1; they are the typed seams *between* roles, and swapping one side of a handoff without the other is exactly the half-coherent state this tool exists to prevent. `checks`/`roles` registration from the global config (`~/.vinaya/config.json`) — stripped at config-*loading* time (a loud warning naming the file), not resolved; the resolver itself stays source-blind, taking one `config` parameter with no source distinction.

## Forge writes (#385)

`vinaya pr create | edit` and `vinaya issue create | edit` are the validated forge-write path: every write runs the full, **config-defined brief-schema validation LOCALLY, before any `gh` write** — prevention, not detection. A malformed body is refused at the CLI layer, in-session, before anything reaches the forge; the identical `@atta/aeg-core` validators run in CI purely as a backstop. The commands **adapt the semantics** of `packages/aeg-core/bin/open-pr.ts` / `open-issue.ts` — they never import them: those bins `process.chdir(REPO_ROOT)` and shell out to this repo's `bin/*` gate scripts, so importing them would drag this repo's layout into a distributable CLI. Instead, like `src/checks/bin/check-brief-shape.ts`, they call the aeg-core public exports and speak the versioned `CheckError` contract.

- **The config-defined brief schema (`briefSchema` in `vinaya.config.json`).** WHICH sections a `pr`/`issue` body must carry is expressed as **config, never hardcoded in the command code** — this repo's required-section set is just one instance (one derivation, N consumers). The schema key is `briefSchema: { pr?: { sections: [...] }, issue?: { sections: [...] } }`. Each section is declarative — no conditional grammar (no `if`/`unless`/`except`), any diff-conditionality living inside the built-in validator's code, never in the config:
  - `{ "builtin": "<name>" }` — runs the named battle-tested `@atta/aeg-core` validator. The names: `tier`, `testPlan`, `testPlanExclusivity`, `principalPlaceholder`, `surfaceMap`, `docUpdateList`, `worktreeStep0`, `stopConditions`, `autonomyClause`, `project`, `for`, `closesN`, `lockAck`, `premiseCoverage`, `issueRationale`. This repo's `pr` instance is the first fourteen (mirroring `checkBriefSections` + premise coverage); its `issue` instance is `issueRationale` (the eight-field Planner rationale, applied only to `tranche:*` task Issues).
  - `{ "heading": "…" }` / `{ "field": "…" }` / `{ "phrase": "…" }` — an adopter-authored generic matcher for their own required sections (a `## …` heading, a `Field:` header field, or a literal phrase anywhere). An adopter shapes their own brief schema through these without touching command code. If a validation this repo relies on cannot be expressed in this declarative, adopter-generic grammar, that is a config-contract gap to escalate — never a license to hardcode.
- **The refusal contract.** On any failure the command emits one `CheckError` JSON line per finding on stderr and exits 1 — the same versioned contract (`schema: 1`, `check`, `severity`, `message`, `agent_recovery_prompt`) the check engine defines. `agent_recovery_prompt` names the exact corrective `vinaya` command, never a restatement of `message` — engineering the ring-0 self-correction loop.
- **`--validate-only`.** Runs every gate, reports `PASS`, exits 0 **without writing** — the `[agent]`-testable path. `--json` envelopes the outcome (`{ schema: 1, data: { validated, written, … } }`).
- **Same-bytes body plumbing (#333).** A stream/heredoc body (`--body-file /dev/stdin`, process substitution) is empty on a *second* read by the time `gh` opens the original path, so the body is buffered ONCE, validated, then materialized into a fresh temp file whose path replaces the `--body-file` slot — `gh` reads the exact bytes this process validated, never an independent second read.
- **Gate-set-per-path — the forge is the truth on `edit` (#417).** On `create`, the diff context (changed files, lock-touch) comes from the local checkout, which IS the truthful source there. On `edit <n>`, that context is a property of the TARGET object, not of whatever checkout the command runs from: `pr edit` fetches the PR's real head branch + changed files (`gh pr view`); `issue edit` fetches the Issue's actual labels (`gh issue view`) and unions them with argv (argv is normally silent on edit). A failed forge fetch is a **hard refusal**, never a fall-back to the local checkout — the exact bypass that fall-back would reopen.
- **Not in v1.0 of this path.** The gh-shim / PreToolUse interception that would make these commands the *only* way to write to the forge is an explicit fast-follow, out of this task. This repo continues to use `packages/aeg-core/bin/open-pr.ts` as its own sanctioned path until that migration; `vinaya pr/issue` is the distributable, adopter-generic reference implementation.

## Install lifecycle: `init` / `init product` / `eject` (#384)

`vinaya init` turns any GitHub repo into a Vinaya-governed repo, non-destructively; `vinaya eject` cleanly reverses it. They ship as one change-set because they are the forward and inverse of the same typed, owned operations — writing them apart risks `init` recording ownership too loosely for `eject` to undo (ratified 2026-07-21).

**The install rule (minimal manifest, re-ruled 2026-07-23): `init` installs only what a shipped check or ring-2 mechanism consumes.** The manifest is exactly six items — nothing that no gate or ring-2 mechanism reads is scaffolded into an adopter's repo. Live-testing the first implementation exposed that it had absorbed this monorepo's own operational apparatus (GitHub templates, a `governance/` folder, example check scripts) rather than the product's core; those are cut. See **Correction 1** below for the before/after, and **Correction 2** for the 5→6 item that later returned. The workflows item grew from two files to three with #761 (see the ring-2 mechanisms chapter below) — the item count itself is unchanged.

The six installed items:

1. **`vinaya.config.json`** — the starter ruleset, with **`checks: {}` empty**.
2. **Git hooks** — thin pre-commit + pre-push managed-block stubs invoking `npx --no-install @attalabs/vinaya check` (`.husky/` if present, else raw `.git/hooks`; never a new dependency) — the real published package name, not the bare `vinaya` name npm's typosquat filter refuses (see Correction 3).
3. **Four workflows** — `.github/workflows/vinaya-checks.yml` + `vinaya-review.yml` + `vinaya-review-verdict.yml` + `vinaya-archivist.yml` (#761; verdict split 2026-08-09).
4. **Root `VINAYA.md`** — the doctrine pointer.
5. **`.vinaya/doc-owners`** — an empty, self-teaching starter for the C5 code → doc coherence seam (#665). Grammar-only (format line, glob syntax, pointer forms, the `# no-doc:` escape hatch, the dormancy note) reproduced as comments from this monorepo's own `.vinaya/doc-owners` header; zero real bindings ship — an adopter's bindings are theirs to add.
6. **Labels** — create-if-absent, never modify.

- **The change-set spine (`src/lib/ops.ts`).** One model of typed operations both commands consume: `create-file`, `managed-block`, `create-label`, `print`. `planInstall` classifies every op against current on-disk state BEFORE any write (`create` / `skip-owned` / `refuse-foreign` for files; `create-host` / `append` / `skip-present` for blocks); `renderInstallDiff` turns that classification into the COMPLETE diff the user confirms; `applyInstall` writes and returns the ownership manifest. `planEject`/`applyEject` are the exact inverse, driven purely by the recorded manifest — the spine carries its own inverses, so shrinking the manifest is a pure op-list edit; `eject` needs no per-artifact change. Nothing is ever written without a shown diff + confirmation.
- **Ownership records = the `managed` manifest (`vinaya.config.json`) + in-file markers.** `applyInstall` records what it created into `managed: { version, files[], blocks[], labels[] }` inside `vinaya.config.json`; managed blocks are additionally self-delimited by `>>> vinaya:managed:<marker> >>>` / `<<< … <<<` comment markers in the host file. `eject` reads the manifest; if it is absent (untouched repo) `eject` is a no-op, and if it is present-but-corrupt `eject` STOPS short of any delete rather than guess (Section 10 stop condition).
- **Non-destructive by contract.** Workflows, config, and the root `VINAYA.md` pointer are `create-file` **refuse-if-foreign** — a file vinaya did not create is never overwritten. Git hooks are the only `managed-block` artifact — a pre-existing adopter hook keeps its lines; vinaya appends a marker-delimited block. Labels are **create-if-absent**; an existing label is never modified, and `eject` **reports** created labels for manual removal (never auto-deletes — a label may be in use elsewhere). No `postinstall`; PATH is never touched; branch protection is **printed, never applied**.
- **Four workflows.** `init` installs `.github/workflows/vinaya-checks.yml` (on `pull_request`, runs `vinaya check --all --diff-only`), `.github/workflows/vinaya-review.yml` (the **required** review gate, on `pull_request` only), `.github/workflows/vinaya-review-verdict.yml` (the comment half: on `issue_comment` guarded by a cheap `contains(..., 'VERDICT')` before any checkout cost, it evaluates `vinaya check review-gate` with zero write permissions and — on a clean evaluation — a separate `actions: write` job re-runs the required workflow, so the gate flips green natively; check-run conclusions cannot be written cross-workflow since GitHub's 2025-02-12 restriction, so re-running is the supported propagation channel; the split also keeps permanently-skipped comment jobs off the PR checks panel), and — since #761 — `.github/workflows/vinaya-archivist.yml` (see the ring-2 mechanisms chapter below). A single checks/review workflow would re-introduce the action-filtered-skip bug the checks/review split fixed. All four are `vinaya-`-prefixed and refuse-if-foreign.
- **The starter ruleset is EXTRACTED, not invented — but `checks` starts empty.** `vinaya.config.json` is seeded from this repo's real gates: `rings` (opt-in accelerators, off), an **empty `checks: {}`** (no example checks and no example scripts ship — `vinaya new check` is the add-path), and `briefSchema` defaults (a PR body must carry Tier / a tagged Test Plan / `Closes #N` / Project; a task Issue the Planner rationale). Tier definitions ride the created labels (`vinaya/tier:0/1/3` — no `vinaya/tier:2`).
- **The doctrine pointer — root `VINAYA.md`, the only orientation artifact.** A thin, git-tracked, tool-agnostic file at the repo root (the reading-order convention an agent orienting in a fresh repo actually hits — beside README, not buried in a subfolder) naming where the full doctrine lives (inside the installed npm package, updated by `vinaya upgrade` — no in-repo copy to drift). Tool-SPECIFIC projections (`.claude/`, an auto-loaded `CLAUDE.md`) are OUT of v1.0.
- **`.claude` independence audited (#722).** Every `.claude` reference reachable from `apps/vinaya` is build-time-only, never shipped to an adopter. Confirmed: the doctrine-pointer statement directly above is the intended tool-agnostic doctrine, not a coupling; `apps/vinaya/web/design/vinaya-landing-brief.md`'s `.claude` mentions sit inside an explicitly-marked historical-record build brief for monorepo contributors building `apps/vinaya/web`, never bundled or read at runtime by `apps/vinaya/cli`; `ProductSwitchControl.tsx`'s `.claude/skills/ui-library-system/SKILL.md` code-comment citation lives in `apps/vinaya/web` (Vinaya Studio, hosted at `vinaya.attalabs.dev`, not npm-published), outside `apps/vinaya/cli`'s published `files` allowlist (`dist`, `templates`, `README.md`). Also confirmed: `aeg-root/skills/{aeg,aeg-roles,brief-authoring}/SKILL.md` — Vinaya's own skill set — carry only prose cross-references to `.claude/skills/*` (the host-repo generated view relationship), no functional dependency on it.
- **Hook host resolution (locked default).** Prefer `.husky/` if present, else raw `.git/hooks`; never add husky as a dependency. A custom `core.hooksPath` is the one shape `init` refuses to guess at — it STOPS and asks (Section 10) rather than inventing a hook manager.
- **`init product <name>`** extends an already-initialized repo with a governed product area — shrunk (2026-07-23) to creating a single **`project:<name>` label** (create-if-absent). Same diff-and-confirm contract; refuses if the repo is not yet initialized (`vinaya.config.json`'s ownership manifest is the marker that `init` has run).
- **`--dry-run` / `--yes`.** `--dry-run` prints the full diff and writes nothing — byte-identical to what a real install then writes for every content artifact (the one exception is `vinaya.config.json`, whose `managed` manifest is injected at apply time). `--yes` skips the confirmation prompt. The interactive abort path calls `process.stdin.destroy()` so a declined prompt exits clean rather than hanging (ported from Cetana's `init.ts`, recovered from git history after #638 deleted `apps/cetana-ai`).
- **Proof (`tests/ops.test.ts`, `tests/init.test.ts`).** Fixture-repo tests assert: exactly the 6-item manifest installs and NOTHING else (a full fixture-tree assertion — no `governance/`, no templates, no `scripts/vinaya-checks/`); `--dry-run` writes nothing yet shows the exact install bytes; the abort path writes nothing; never-clobber (a pre-existing hook gets an appended block; a foreign workflow, a pre-existing root `VINAYA.md`, and a pre-existing `.vinaya/doc-owners` are REFUSED); both workflows install with the correct triggers; `init product` creates only the `project:<name>` label; and the round-trip `init` → `eject` returns the fixture to its exact pre-init filesystem (managed blocks stripped from surviving adopter files, labels reported not deleted, orphan-manifest eject refused).

## Install lifecycle: `doctor` / `upgrade` (#386)

`vinaya doctor` diagnoses the installation `init` created; `vinaya upgrade` is the only sanctioned way back to a clean one. Together they close the lifecycle #384/#656 opened: install → diagnose → migrate → (still) eject.

- **`doctor` never mutates.** Every check is read-only — it re-runs the SAME op list `buildInitOps` gives `init` (`src/lib/artifacts.ts`) and classifies each op against on-disk state + the `managed` manifest instead of applying it (`src/commands/doctor.ts`'s `diagnoseInstall`). It reports; it does not fix. Seven checks: (1) git hooks — present, executable, managed block intact, including the per-clone drift case where a `.git/hooks`-based install's stubs were never tracked by git and are silently absent after a fresh clone (the reason doctor exists, per #384's amendment-2); (2) both workflows — present, byte-content matches the installed package's current generator (skew reported, never patched); (3) `vinaya.config.json` — loud on parse/schema failure (`loadConfigChecked`'s contract, reused here), and the `managed` manifest checked BOTH directions against disk (a recorded file missing on disk, and a vinaya-marked file/block present on disk but unrecorded in the manifest); (4) root `VINAYA.md` — present, managed marker intact; (5) environment — `gh auth status` detail, Node/Bun version, and a "package vs installed artifacts" skew line pointing at `vinaya upgrade` whenever any check above found drift (a self-explaining message, never a bare mismatch); (6) branch protection — report-only via `gh api`, never applied, unknown/unreachable reported honestly rather than guessed; (7) custom checks — every `checks` entry's `run` script path resolves on disk (registration shape itself is already the schema's job). Exit 0 when every finding is `ok`/`info`; exit 1 on any `warn`/`error`. `--json` emits the same findings enveloped (`schema: 1`).
- **`upgrade` regenerates vinaya-owned artifacts only, via the same detect → plan → render diff → confirm → apply engine `init` uses** (`src/commands/upgrade.ts`'s `planUpgrade` / `renderUpgradeDiff` / `applyUpgrade`) — inverted in intent: where `init`'s `applyInstall` never touches an already-owned file (idempotent re-install), `upgrade`'s whole job is bringing an owned-but-stale artifact current. A file/block vinaya does not own — foreign content, or never installed — is left exactly alone (reported `REFUSE`/`skip`, never touched); `upgrade` regenerates what `init` already owns, it does not perform a fresh install. `vinaya.config.json`'s semantic fields (`rings`/`checks`/`briefSchema`) are adopter-owned from day one and are never diffed or rewritten by `upgrade` — only the `managed` ownership sub-object is regenerated (its `version` bumped forward when stale). A no-op upgrade (everything already current) prints "already current" and exits 0 without prompting. `--dry-run` / `--yes` behave exactly as they do for `init`/`eject`.
- **Manifest version is a real range check, not an exact pin.** `managed.version` in `vinaya.config.json`'s schema (`src/lib/config.ts`) changed from `z.literal(MANAGED_MANIFEST_VERSION)` to `z.number().int().positive()` so `upgrade` can read a manifest recorded by an older package version instead of that manifest failing schema validation outright. `upgrade` refuses loudly and self-explains when the repo's recorded version is NEWER than the installed package understands ("upgrade the vinaya package itself first"); migrating an older manifest forward is currently a no-op beyond the version bump, since v1 remains the only version that has ever shipped.
- **Init's no-remote graceful-skip (spec D3).** `vinaya init` (and `init product`) used to crash mid-run on the first `gh label create` when the repo had no `origin` remote (or it wasn't a GitHub URL) — `detectGitRepo` already tolerates this (owner/repo come back blank), but every downstream label op still assumed a real remote. Both commands now detect this up front, print a warning, skip label creation (and the gh-auth requirement that existed only for it) entirely, and continue installing everything else — the final summary still prints. `init product`'s only op IS a label, so a remoteless run scaffolds nothing and says so, rather than reporting success for an install that didn't happen.
- **Doctrine bundling into the package is now shipped (#762).** A prior investigation under Issue #386 found that bundling the RAW `aeg-root/{roles,contracts,state-machine.md,templates}` corpus verbatim was blocked — it is saturated with this-repo-specific implementation detail (`packages/aeg-core/bin/*.ts` paths, specific historical PR-number citations, `.github/workflows/forge-lifecycle.yml` step names) that a mechanical AEG→Vinaya name swap cannot fix without authoring new doctrine prose. #762 shipped bundling anyway, on the premise that the corpus travels as internal-methodology reference content for an agent already working inside this monorepo — not as neutral-named adopter-onboarding prose — so the this-repo-specific detail is a property of the source, not a defect for this use. `apps/vinaya/cli/scripts/bundle-doctrine.ts` (wired into `prepack`, ahead of `scripts/build.ts`) copies ten named categories — `state-machine.md`, `enforcement.md`, `coordination.md`, `tranche-model.md`, `process.md`, `glossary.md`, `roles/`, `contracts/`, `skills/`, `templates/` — from the monorepo's `aeg-root/` into `apps/vinaya/cli/aeg-root/`, a gitignored build artifact shipped via the `files` allowlist the same way `templates/` already is. `aeg-root/tranches/` (this repo's execution history) and three this-repo-only prose files (`aeg-manual-flow.md`, `documentation-coherence.md`, `reviewer-prompt.md`) are deliberately excluded. `doctor` still does not check for the bundle — that remains open.
- **`VINAYA.md`'s generated text corrected to match the shipped state (#762, superseding #722's correction).** `doctrinePointer()` (`apps/vinaya/cli/src/lib/artifacts.ts`) no longer claims bundling is planned-but-unshipped. It resolves `join(packageRoot(import.meta.url), 'aeg-root')` — the same `packageRoot()` helper `new-check.ts` already used to find `templates/custom-check.template.ts` post-install — and embeds that install's own real, resolved absolute path directly into the generated `VINAYA.md` text at `vinaya init` time. Verified against a real `npm pack` → fresh `npm install` (not a local `file:` symlink, which resolves to the source tree rather than a copy) → `vinaya init` → read `state-machine.md` from the printed path round-trip.
- **Proof (`tests/doctor.test.ts`, `tests/upgrade.test.ts`).** Fixture-repo tests assert: a clean `init` → `doctor` reports healthy and the fixture tree is byte-identical before/after every `doctor` run (the non-mutation guarantee, asserted mechanically, not just claimed); each of the Issue's named perturbations (a deleted hook, a corrupted managed block, a broken `vinaya.config.json`, a removed workflow, a manifest entry dropped, a custom check pointed at a missing script) is flagged while doctor still mutates nothing; `upgrade --dry-run` shows the regeneration diff and writes nothing; `upgrade` then regenerates the owned artifacts and a following `doctor` run is clean again; an adopter-edited `vinaya.config.json` (custom `rings`/`checks`/`briefSchema`) survives `upgrade` unchanged on every key `upgrade` doesn't own; a remoteless fixture's `init` warns, skips labels, and still completes.

## Ring-2 mechanisms: `archive` / `audit` (#761)

`vinaya archive` and `vinaya audit` are new CLI verbs, not `check` adapters — `vinaya check` is a pre-merge gate abstraction (diff-scoped or full-repo-scoped, evaluated once per PR); the three mechanisms these commands wrap are post-merge, repo-wide, event-/schedule-triggered — they audit history after the fact rather than gating a diff, so they do not fit the `check` verb's contract at all. This is the third generated workflow file `init` installs (see the install-lifecycle chapter above), reproducing this monorepo's own live `.github/workflows/archivist.yml`'s exact three-job shape — triggers, permissions, `continue-on-error` on the drift job — for any adopter repo.

- **`vinaya archive [--merge-sha=<sha>]`** — the post-merge Archivist. Resolves the merge commit's associated PR via `gh`; if it's a task PR (a `task/<tranche>/<n>` branch, or its closed Issue carrying a `vinaya/tranche:*` label) without a provenance comment yet, posts the provenance block and closes the linked Issue. Idempotent — re-running against an already-archived PR is a no-op. Defaults `--merge-sha` to the current `HEAD`.
- **`vinaya audit [--only=dead-branches|direct-push] [--sha=<sha>] [--json]`** — the two remaining ring-2 checks. Dead-branch-push is never-red: a notification channel that flags (label + PR comment) any `task/*` branch whose tip commit lands after its own PR already resolved. Direct-main-push is a real pass/fail: it opens an incident Issue and exits 1 if a commit on `main` has no associated merged PR via the commits→pulls association API. `--only` scopes to one half — the generated workflow's three jobs each invoke a single scope, matching `archivist.yml`'s own job split.
- **Same auth/repo-resolution path as every other command.** Both commands resolve owner/repo via `detectGitRepo()` (`src/lib/detect.ts`) — never a second mechanism — and shell to `gh` exactly as `packages/aeg-core/bin/archive-task.ts` / `dead-branch-audit.ts` / `check-direct-main-push.ts` do today; the underlying evaluators (`@atta/aeg-core`'s `buildProvenanceBlock`, `findDeadBranchPushes`, `checkDirectMainPush`) are unchanged, imported rather than re-implemented.
- **No live-mutation test fixture against this monorepo's own real branches/Issues.** `gh pr merge` is blocked in the environment this task was executed in (a safety gate unrelated to attalabs, "green status cannot be verified... gate fails closed"), and the token available lacked `delete_repo` scope to clean up a disposable scratch GitHub repo created for the purpose — so the dead-branch-push flagging path's live end-to-end behavior is verified by parity (the same `gh` command shapes as `dead-branch-audit.ts`, reviewed side-by-side) and by a unit test against the shared, already-tested `findDeadBranchPushes` pure function, rather than a live scratch-repo mutation run. `vinaya archive`'s and `vinaya audit --only=direct-push`'s read-only paths ARE live-verified, against this repo's own real merge history, output byte-compared against direct `bin/*.ts` invocation.

## Trust surface: `demo break` / `waiver` (#387)

The behavioral trust surface — the two commands that prove the product is real rather than asserted, and the one legitimate way to bypass it. This task **productizes** the actor-verified waiver-label mechanism `aeg-governance-hardening` task 29 (#380) already proved live in this repo; it does not redesign it.

**`vinaya demo break` — the productized belief moment.** On an **isolated, discardable branch of the current repo** (never a separate temp-dir sandbox repo — an earlier scratch doc speculated one; Issue #387's Boundary is authoritative and rejects it, so the demo rides the exact same git hooks a human or agent already installed): stage a deliberately malformed brief → attempt a real `git commit` → the repo's actually-installed pre-commit hook refuses it with its real output → apply the minimal fix → commit again, passing → switch back and delete the demo branch.

- **Branch isolation.** A collision-safe `vinaya/demo-break-<timestamp>-<random>` branch, retried on the rare name collision. Refuses outright — before creating anything — on a dirty working tree or a detached `HEAD`, so the demo never has to guess what to do with the user's in-progress work.
- **The staged artifact is real, and so is the refusal.** The hook installed by `init` runs `vinaya check --all --diff-only` — a git commit's real invocation point. Of the core checks, `coherence` and `dispatch-readiness` bypass on any branch that isn't `task/<tranche>/<n>`, and `doc-coverage` is dormant without a bound `.vinaya/doc-owners` entry — none of those three can fire deterministically on a throwaway branch in an arbitrary repo. `brief-shape` is the one whose input (`PR_BODY`) this command can supply honestly: the artifact staged for commit **is** a draft brief body, missing exactly one required section (`Tier:`) so the refusal is a single, legible finding rather than a wall of unrelated errors. The check that refuses it is the unmodified `checkBriefSections` the CI brief-shape gate itself runs — real code, real output, verbatim on stdout, never a scripted string. (`coherence`/`dispatch-readiness` correctly evaluate the CALLER's repo, not this monorepo's own — Correction 2 fixed a `chdir` bug that leaked this repo's own tranche facts into any other repo's check run; see the Check engine chapter above.)
- **Guided fix, then pass.** The command rewrites the same file adding the missing `Tier:` field, re-stages, and commits again — the identical hook, now passing.
- **Cleanup and crash recovery.** Default behavior switches back to the original branch and force-deletes the demo branch; `--keep` skips this and prints the branch name plus the manual cleanup command. A small state marker (`<git-dir>/vinaya-demo-state.json`, in the checkout's own gitdir — never a tracked file) records the original and demo branch names before any mutation; on the next invocation, a leftover marker (or a stray `vinaya/demo-break-*` branch with `HEAD` sitting on it) is detected and cleaned up — switching back to the recorded original branch and deleting every stray demo branch — before a fresh run starts. This is what makes the command safe to run twice, and safe after a crash.
- **Never touches a real branch.** The original branch's `HEAD` never moves — only the demo branch receives commits, and it is always deleted (or explicitly kept, never left silently).

**`vinaya waiver` — the forge-authenticated escape hatch.** Prompts for which label (`docs` | `review`), the PR number (auto-detected via `gh pr view` from the current branch when omitted), and a short reason, then applies the label via `gh pr edit --add-label` under the invoking human's own authenticated `gh` identity, and posts the reason as a `gh pr comment` so the rationale sits next to the label event rather than folded into a body field.

- **A waiver is never an agent-emittable string.** Not a PR body field, not a commit trailer, not a comment the config could recognize. The only mechanism ring 1 honors is `isWaiverLabelActorVerified` (`packages/aeg-core/src/waiver-label.ts`) — the `vinaya/waiver:docs` / `vinaya/waiver:review` label **plus** its own labeling-timeline event's actor being a configured principal. This command wraps that already-proven predicate; it does not reimplement or relax it, and label presence alone is never sufficient.
- **This command cannot fabricate that actor.** It shells out to `gh`, which authenticates as whoever is logged in. The label's recorded actor is therefore always the real, live `gh` identity that ran the command — this code has no path to assert a different one.
- **`--print-only`** prints the exact `gh pr edit` / `gh pr comment` commands and executes nothing — for a human who wants to run them personally, or a CI/non-interactive context where an agent session should never be the one applying its own waiver.
- **The shared-credential caveat, documented plainly rather than implying false assurance.** In a repo where an agent session and the human share one `gh` credential — this monorepo included — `waiver` structurally cannot prove which of them actually ran it: the labeling-timeline actor is whoever `gh` is authenticated as, and a shared token makes that ambiguous between "a human ran `vinaya waiver`" and "an agent session ran it, unsupervised." This command does not attempt to close that gap — the real actor-differentiation mechanism lives at the hook layer (`aeg-governance-hardening` task 29's own part 2, out of this task's surface), not in the CLI. `--print-only` is the practical mitigation available here: it lets a human be the one who actually executes the mutating `gh` call, even when the credential itself cannot prove it.
- **Proof (`apps/vinaya/cli/tests/demo.test.ts`, `apps/vinaya/cli/tests/waiver.test.ts`).** `demo break` is tested against a disposable fixture repo with a REAL `.git/hooks/pre-commit` invoking the real check runner (not a simulated call) — asserting the double-run branch-cleanliness guarantee, the verbatim real refusal text, `--keep`, the dirty-tree and hooks-not-installed refusals, and crash recovery from a stray branch + state file. `waiver` is tested against a fake `gh` on `PATH` that logs every invocation — asserting `--print-only` never invokes `gh` at all, a real run applies the exact label and posts the exact reason, and PR-number auto-detection works.

## Renderer contract (#389)

**The rule: Studio renders, it never re-derives.** Governance state enters Studio only through one of two permitted entry paths — `@atta/aeg-core`'s public API, **or** the `@atta/vinaya-sources` `StateSource` adapters. Both are legitimate; this is an OR, not a hierarchy — do not "fix" an aeg-core-direct call site into a `StateSource` one on the strength of this chapter alone. What both paths rule out is a third option: Studio computing any piece of governance state itself. The gates (`vinaya check`, and today `packages/aeg-core/bin/*`) compute governance state; Studio's only job is to render what they computed. If Studio ever re-derives any of it, Studio and the gates can disagree about the same repo — and a product whose dashboard contradicts its own gate has no product left.

**The one-way import corollary.** `apps/vinaya/web` must never import `apps/vinaya/cli` internals, and `apps/vinaya/cli` must never import web internals — either direction crossing the boundary would let one surface reach around the other's derivation and compute governance facts on its own. This is now mechanically enforced, not asserted in prose: `apps/vinaya/web/src/lib/import-boundary.test.ts` (vitest) walks every `.ts`/`.tsx` file under `web/src` and fails on any import/export statement whose specifier names `@attalabs/vinaya` — or its pre-publish workspace name `@atta/vinaya-cli`, still matched so an import written against the old name is caught rather than silently allowed — including subpaths, or reaches relatively into `../cli/`; `apps/vinaya/cli/tests/import-boundary.test.ts` (bun test) is the converse, walking `cli/src` and `cli/tests` for `@atta/vinaya-web` or `../web/` reaches. Each package guards its own boundary and fails its own CI; the two tests intentionally do not share an imported helper — that import would itself cross the boundary they exist to defend.

**What is not a violation.** Fetching facts — plain I/O — in the web app is fine. `load-snapshot.ts` fetching forge facts over the network and handing them to `@atta/aeg-core`'s `deriveTranche` is the contract working as designed, not a breach: the derivation still happens inside aeg-core, not in Studio. The rule is about **derivation**, not about where an HTTP call lives. This is the distinction most likely to be misread: "Studio fetches data" is not the same claim as "Studio computes governance state," and only the second is forbidden.

## DiagramModel derivation (#506)

One pure library turns governance doctrine into a renderer-agnostic model every diagram consumer reads — Studio, `/docs/harness`, a CLI visualizer — so none re-implements the governance logic (one derivation library, N consumers).

- **Contract:** `deriveDiagramModel(doctrine, config, tranche): DiagramModel` (`packages/aeg-core/src/diagram-model.ts`, exported from `@atta/aeg-core`'s `index.ts`). Pure — zero I/O, zero `fs`/`node:` imports (aeg-core's purity charter, #372/#521). Doctrine arrives already-read as `DoctrineContent` (raw `enforcement.md` + roles/contracts markdown); config is the declarative `DiagramConfig` (ring-level + per-gate enable/disable booleans, `null` = nothing disabled); `tranche` is the `StateSource` live-context passthrough, carried on the model and **never** used to compute render-state.
- **Model shape:** `nodes` (kind `ring | gate | check | action | role | contract`, each with a kind-prefixed stable id, label, optional `ringIndex`, and a derived `renderState`), `edges` (`guards` gate→action, `performs` role→action, `produces`/`consumes` role→contract), `findings` (config keys that reference no real gate/check), and the passthrough `tranche`. **Geometry — radius, angle, colour, coordinates — is NOT in the model; the renderer owns it.** A ring index and a render-state are structural facts; a pixel is not.
- **A node's three text fields, and why they are three (#553):** `summary` is the rhetorical question (#551); `detail` is one plain sentence saying what the node does; `label` is its name. Each `detail` comes from its own source's `description` — `enforcement.md`'s `Description` column for gate/check, `description:` frontmatter for role/contract, the `ACTIONS` entry's field for action — so every kind reads in one register, because a reader cannot see what kind of node they clicked. `detail` is never `GateRow.spec`, the enforcement table's own "what must be true" column: that column is written to ENFORCE (17 of 31 rows cite a decision id, issue number or file path; the longest runs 2708 chars), which is correct for a gate and unreadable on a page. Rendering `spec` is the bug `description` exists to prevent; "Read more" is what carries a reader to it. This closed the gap #508's leaf-panel spec left — it listed `summary` and a link, with no field answering the question it asks.
- Every gate/check/action/role/contract node also carries an optional `summary` (a short, non-technical question, e.g. "Ever had someone push straight to main and nobody noticed?") — gate/check nodes additionally carry `category` (`ci`/`hook`/`event`, describing when the check fires relative to a bare repo with no governance installed) and role nodes carry `actorType` (`agent`/`human`/`either`, from the role's own pre-existing frontmatter). Added (#551), consumed by task 4's (#508) drill panels.
- **Render-state is derived, never authored** (precedence top-down): `locked` when the doctrine row's `lock` column is non-empty (config can never override a lock, e.g. a principal/foundational gate); `disabled` when config disables it (per-gate `gates[slug] === false`, or the ring-level `ring1_forgeWriteInterception`/`ring2_asyncAudits` switch for that ring's checks); else `active`. Ring 0 has no ring-level switch — only a per-gate entry can disable a ring-0 gate, and a locked one ignores even that.
- **DoctrineSource seam:** the library takes doctrine, not `aeg-root/` paths (it must be packageable for adopters with no `aeg-root/`). The type `DoctrineSource` (`packages/aeg-core/src/doctrine-source.ts`, I/O-free, mirrors `StateSource`) is implemented by `createFileDoctrineSource({ root? })` in `@atta/vinaya-sources` (`src/doctrine-file-adapter.ts`), reading `<root>/enforcement.md`, `<root>/roles/*.md`, `<root>/contracts/*.md` over a configurable root (default `DEFAULT_GOVERNANCE_ROOT`, never a hardcoded literal).
- **No-drift substrate:** the derivation consumes the canonical `ACTIONS` and its `CROSSING_KEYWORDS` map (promoted into `actions.ts` this task) — the same list G3's crossing check reads — so gate→action edge counts can never drift from G3's completeness set. The markdown-table parser is likewise the one aeg-core-owned `markdown-table.ts` (promoted out of the web app this task); `registry-parse.ts` and the Vinaya `/aeg` renderer both sit on it.
- **Proof:** fixture tests (`diagram-model.test.ts`) assert the exact node set, a config-disabled gate `disabled`, a locked gate `locked` even when config also disables it, an unknown config key surfacing as exactly one finding, and edge counts matching `ACTIONS`; a real-`aeg-root/` cross-check asserts every `into-github` action gets ≥1 `guards` edge, every `performedBy` role resolves to a role node, and node ids are globally unique.
- **Out of scope for this task:** the renderer (pages own SVG/geometry — the rings-drilldown application landed as #508); wiring per-gate switches into the CLI's `VinayaConfigSchema` (a later CLI task — `DiagramConfig` is this task's only config surface).
- **Render decision (#508):** `/docs/harness`'s leaf panel shows `category`/`actorType` as a neutral filled `Badge` — one fill for every value, never per-value color-coded, and distinct from the diagram's own per-ring visual distinction (an unrelated, pre-existing concept). #508's amendment specifies `variant='outline'`; outline renders near-invisible against this page's cream background, so the filled default is a deliberate departure on that one point, preserving the brief's actual constraint (no per-value colour coding) rather than its literal wording. "Read more" links to a real GitHub blob line (`enforcement.md#L<sourceLine>` for gate/check nodes; `roles|contracts/<id>.md` with no line for role/contract nodes; `packages/aeg-core/src/actions.ts` for action nodes — no doctrine markdown backs them, but that file does define them, and a panel with no way out was the worse answer). `DiagramModel.tranche` is passthrough task-lifecycle data, not per-check live status — so `/docs/harness` carries no "checks N/N" live pill, deliberately, even though the pre-existing design mockup this page's interaction pattern is drawn from shows one.
