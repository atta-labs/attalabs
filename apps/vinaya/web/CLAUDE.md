# Vinaya Web

Next.js web app for Vinaya — landing page plus the methodology surfaces (The Harness, Docs, Install, Studio). The landing (`/`) applies the v3 design (`vinaya-landing-v3-implementation-brief`): hand-rolled `<canvas>` hero scenes (`src/app/(site)/_components/canvas/NormalEraCanvas.tsx`/`LightSpeedEraCanvas.tsx`/`ProtectedCanvas.tsx`, each an isolated props-free client component — the original SVG+CSS-keyframe renderer was reworked to canvas per `vinaya-landing-v3-canvas-rework-brief` after the SVG scenes read as disconnected floating debris) and the v3 hero copy, all rendered through semantic theme tokens (canvas colors resolved from CSS custom properties, never hardcoded) — never the fixture's own cream palette. Has its own Sanity CMS identity (D-124, reusing Vitakka's project `o56nzgrr`): layout fetches its own config/branding via `getProductCms('vinaya')`, the generic key-addressed pattern every consumer uses (D-125). See [vinaya-spec.md](../specs/vinaya-spec.md).

The Hero and `#eras` sections' rotating bullet questions ("Ever clicked a link in your own docs and hit a dead end?" etc.) are not hardcoded copy — `src/lib/aeg/doctrine-questions.ts` reads `aeg-root/` doctrine content and calls `deriveDiagramModel()` from `@atta/aeg-core` to collect every node's `summary` as a real doctrine question, deduped. `RandomQuestionText.tsx` picks a random subset per page load and reveals them sequentially; its reserved-height box under `#eras` uses `minHeight` (not `height`) specifically because the line-count estimate is a heuristic (character-count based) and a hard cap let misestimates overflow into the "Meet Vinaya" button below — `minHeight` makes the box self-correct instead. `ProtectedCanvasPortrait.tsx` is a second, portrait-orientation variant of `ProtectedCanvas.tsx` (robots-only firing down into the ring, no human cluster) — `ProtectedSection.tsx` currently renders the portrait variant only, sized to match the era canvases' footprint.

The `/studio` subtree (`src/app/studio/**`, `src/app/api/coherence/route.ts`) is Vinaya Studio's dashboard, ported from the old AEG Studio (#493; that app was deleted outright by `deprecation-v1` task 1, D-132). It reads governance state via its own `repo-state`/`forge` derivation layers (`src/lib/repo-state/`, `src/lib/forge/`) — no governance logic is re-implemented here — the corresponding web/cli one-way import boundary is enforced by `src/lib/import-boundary.test.ts` (D-087, `vinaya-studio-v1` task 4, #389). `src/lib/repo-state/` was `src/lib/aeg-fs/` until #553: the name came over with the port, and Vinaya names nothing after AEG. The local `/studio` home (`studio/page.tsx`) is a three-card dashboard (`vinaya-pages-v1` task 11, #571) — Projects and Iterations preview cards, then a single full-width **Tasks** card that is the one work surface: every Ready / active / blocked iteration task plus the backlog, in one status-filterable list (`studio/_components/TasksPanel.tsx`). Backlog was folded into the Tasks card rather than shown as its own card — a Principal-directed consolidation from the original four-card design during the design pass; the standalone `/studio/backlog` table stays. Rows are minimal and column-aligned — `#issue` links to GitHub in a fixed-width leading cell (rendered even when a task has no Issue, so a two-digit and a four-digit number leave the rest of the row starting at the same x), then a status badge and the plain (non-clickable) title, with the iteration slug linking to its board (backlog rows carry no iteration). On wide viewports the title absorbs the leftover width and wraps within its own cell, so the slug holds the right edge of the first line; on narrow ones the row wraps and the slug drops to its own line, left-aligned under the issue number rather than stranded against the far edge. Rows stay flex, not a `<table>`. The Tasks card's chip row carries the same FILTER BY heading treatment as the backlog table (task 11, #624), so both filter surfaces are announced as one labelled control. An iteration's board href is derived in one place — `studio/_lib/iteration-href.ts`'s `boardHref()` — as its first project's route. All three surfaces that reference a board go through it: the home Iterations card and `iterations/IterationsTabs.tsx` (via the `iterationHref()` summary wrapper) and the Tasks card's per-task slug (via `load-dashboard-tasks.ts`, which resolves per `task.projects`, not per summary — which is why the shared rule takes a project list rather than an `IterationSummary`). An iteration's `projects` is the union of the `project:*` labels **and** each Issue body's `**Project:**` field (derived in `@atta/aeg-forge-state`), so an iteration has no board to point at only when **both** are absent — a missing label alone still resolves via the field (`state-machine-v1`). That genuinely board-less state is real, not an error, and every such reference renders non-clickable but **self-explaining**: `NO_BOARD_REASON` as a `title=` tooltip on all three, plus an inline muted note on the `IterationCard`. Board-less rows never render silently dead (D-087 — the Studio does not lie by omission, including by omitting the reason). The Tasks list aggregates via `studio/_lib/load-dashboard-tasks.ts`, which reads the iteration board's own `deriveIteration` + `checkDispatchReadiness` (via `loadIterationSnapshot`/`loadDispatchReadiness`) and consumes the `status-display.ts` label vocabulary rather than re-deriving status. `studio/backlog/page.tsx` was rebuilt in that task as a filterable `@atta/ui` Table (client `backlog/_components/BacklogTable.tsx`, project + tier + flags inline toggle-chip filters — every option visible, no dropdown) — one row per Issue, so a cross-project Issue carries both `project:*` badges in a single row (matched by the project filter under either) instead of being dropped to its first label (D-091); iteration/state are deliberately not filters (the backlog is the open, no-`iteration:*` set by definition), and the chip rows carry a **FILTER BY** `h2` with a left-pinned `Filter` icon, which also labels the chip block (`role='group' aria-labelledby`) so the filter controls have a programmatic name and not merely a visual one. The table is `table-fixed`, so its `w-[..%]` column widths are one 100% budget that has to be rebalanced as a set — Flags is the widest label column at 32% (`vinaya-pages-v2` task 11, #624) because its labels are the longest, its +6 funded out of Title (37→32%, it wraps freely anyway) and Tier (11→10%). Since `vinaya-web` resolves the **retro** library, whose `Badge` ships `whitespace-nowrap` + a fixed `h-5` + `overflow-hidden`, the label cells relax those three on their children (`BacklogTable.tsx`'s `LABEL_CELL`) so a long label wraps INSIDE its column instead of overhanging the neighbour — the relaxation is on the cell, not on the shared `LabelBadge`, because the constraint belongs to this table's fixed layout rather than to the badge. Forge honesty is uniform (D-087): `fetchOpenIssuesWithoutIterationLabel` returns `{ issues, forge }` carrying a `ForgeStatus`, and both pages render `ForgeBanners`/`ForgeUnavailableBanner` on failure instead of a truth-shaped empty list — the Projects card, sourced from the local registry, still renders when the forge is down. Portal and Studio are two products sharing this one deployment (D-101, D-126, task 6 #544): `src/lib/env.ts`'s `isVercelDeploy()` gates on `VERCEL_ENV` **presence**, not equality to `'production'` — `VERCEL_ENV` is also `'preview'` on every preview deploy, and an equality check left preview ungated until code/security review caught it — so a local `bun run build && bun run start` (neither var set) still shows the real dashboard while both production and preview redirect. In either case `/studio` renders nothing of its own, it `redirect()`s to `/the-studio` (a Portal page under `(site)/the-studio/page.tsx` carrying the same honest local-only copy `StudioLocalOnlyLanding` used to render in-shell before this task deleted it), and `/studio/projects`/`/studio/iterations`/`/studio/backlog` still 404 on any Vercel deploy; `/docs` (moved out of `studio/` into the `(site)` route group, `vinaya-pages-v1` task 8, #568) is unaffected since it reads `aeg-root/**.md` at build time, not the forge — `/studio/docs` and every `/studio/docs/<slug>` now permanently redirect there. Both TopBars (`(site)/layout.tsx`, `studio/layout.tsx`) render the CMS logo (`getProductCms('vinaya')`'s `branding.logoSolidDark`/`logoSolidLight`) plus `src/app/_components/ProductSwitch.tsx`, a Portal↔Studio switch gated `!isVercelDeploy() && hasForgeConnection()` (`src/lib/forge-connection.ts`) — see D-126 for why forge-reachability alone is never sufficient authorization.

`/docs` is the **generated reference view of the harness** (`src/lib/docs/load-aeg-docs.ts`) — moved out of `studio/` into the `(site)` route group by `vinaya-pages-v1` task 8 (#568); `/studio/docs` and every `/studio/docs/<slug>` now permanently redirect here. Its surfacing rule is **model-backed** (`vinaya-pages-v1` task 12, #590, D-079/D-087): the loader derives the same `DiagramModel` `/the-harness` draws and publishes a doc **iff a node points at it** — `modelBackedDocPaths` (in `@atta/aeg-core/docs`) maps gate/check → `enforcement.md`, role → `roles/<id>.md`, contract → `contracts/<id>.md` (16 files today), and the `surfaced` frontmatter flag is the only override. The loader passes that allowlist to `isSurfacedDoc`; C6 (`docs-coherence` via `verify-docs`) checks against the same set, so the raw-markdown ~60% that backs no reachable node (`state-machine.md`, `process.md`, `coordination.md`, `skills/**`, Cetana's `diagrams/**`, …) stops being public without a word being rewritten. The nav is the **harness tree**, not the file tree (sidebar titled **The Harness**): sections **Roles / Contracts / Actions / The Rings** (no "Overview"), at a granularity that follows content size. File-sized nodes keep their own page — `/docs/roles/<id>`, `/docs/contracts/<id>` (raw doctrine under the model frame). Row-sized nodes become `#`-anchored sections: `/docs/rings/ring-<0|1|2>` renders that ring's gates/checks as model-derived sections (label/badge/summary/detail, and for ring-0 the guarded action), and `/docs/actions` renders `ACTIONS` the same way; `/docs/rings` is the landing = `enforcement.md`'s three-ring intro prose (the one place its raw text renders). The one node→route source is `@atta/aeg-core`'s `nodeDocRoute`/`nodeDocHref` (`src/docs/node-route.ts`) — consumed by the nav, `the-harness/_lib/read-more.ts`, and the `/docs` map alike, so a card's deep-link, a "Read more" anchor, and a heading `id` are the identical slug (reused from the node id aeg-core stamps, never re-derived). The `/docs` index (the map) renders each part with its model `detail`/badges/what-it-guards and deep-links to the exact node. `/docs/enforcement` 307-redirects to `/docs/rings` (old surfaced URL kept alive). It is distinct from `/install`, Vinaya's own CLI command reference (`vinaya-pages-v1` task 9, #569), which renders `@atta/vinaya-sources`' `COMMANDS` registry (moved out of `apps/vinaya/cli` in task 9's re-dispatch, so `web` depends on it directly without reaching into `cli` internals — D-087) rather than reading `aeg-root/**.md`. On `lg:` and up `/install` is a two-pane command reference (`vinaya-pages-v2` task 1, #599, the `cli.github.com/manual` shape): a sticky command sidebar (`install/_components/InstallSidebar.tsx`) beside the content pane, reusing the `/docs` `SidebarProvider`/`SidebarMenu` primitives rather than a custom one — but active state is scroll-position-driven (an on-page TOC via `IntersectionObserver`), not pathname-driven, since every command is a section on this one page, and clicking an item anchor-scrolls to it. The sidebar's hrefs and the content sections share one slug via `install/_components/command-slug.ts` (a plain, non-`'use client'` module so the server page can stamp the section ids the client sidebar links to). Below `lg` the sidebar is hidden and the page is the same centered `max-w-3xl` stacked column as before. Both render code through `@atta/ui`'s `Code`/`CodeBlock` (task 9 added them to the cross-library contract; task 8 adopted them here, deleting the class strings task 9 had copied from this file). Nav is two-tier: root `layout.tsx` only wires `NextWebShell` (theme/shell, no TopBar of its own); the `(site)` route group (Home, The Harness, Studio, Install, Docs) carries the site TopBar; `src/app/studio/layout.tsx` carries its own TopBar (logo "Vinaya Studio", links Home/Projects/Iterations/Backlog/Docs — `Home` points at `/studio`, `Docs` at `/docs`) with no left sidebar, mirroring the old AEG Studio's TopBar-only chrome. The `/studio/projects` sub-bar (`ProjectsSubBar`) is `sticky top-0` within StudioShell's scroll container so it stays pinned under the topbar as the page scrolls; `projects/layout.tsx` adds no overflow/height of its own (StudioShell owns the scroll container). **StudioShell owns the page padding too** — it is the single source of the `px-8 py-8` gutter, the `max-w-6xl` column, and the one scroll container, and a nested layout re-applying any of them is a bug, not a local override. Both nested layouts used to: `iterations/layout.tsx` re-added `px-8 py-8` *and* an `h-full overflow-y-auto` scroller inside the shell's, and `projects/layout.tsx` re-added `px-8 py-8`. That doubled the gutter to 4rem, cut the projects measure to 52rem against 56rem elsewhere, and left `/studio/iterations` with 4rem of top space where the board had 2rem. The asymmetry hid the shared cause: `ProjectsSubBar`'s `-mt-8` cancels the shell's top padding so the bar can pin flush, so on `projects/**` the layout's `py-8` read as correct spacing rather than as duplication, while `/studio/iterations` — which has no sub-bar to absorb it — showed the doubling plainly. Both now render only `mx-auto max-w-4xl`; `projects/layout.tsx` keeps a `pt-8` that is **the sub-bar's counterweight, not padding** — deleting it butts the first heading against the bar. The iteration board (`studio/projects/[name]/iterations/[slug]/page.tsx`) carries no breadcrumb — the topbar and sub-bar are the only nav — and its body below the header is two tabs, **Tasks** (the topology table, plus the backlog and coherence sections) and **Token Ledger** (`vinaya-pages-v2` task 10, #623). Tab state is the only client-side piece: `_components/IterationTabs.tsx` is a thin `'use client'` shell around `@atta/ui` `Tabs` that takes both panels as `ReactNode` props, so the page itself stays a server component and its `dynamic = 'force-dynamic'` live-forge reads are unaffected. The ledger tab always renders — its forge-unavailable banner and its no-rows empty state live inside the tab rather than replacing it. A project page's "no iterations" state (`projects/[name]/ProjectIterationsTabs.tsx`) renders as a `Card` + lucide `Inbox` block under the tab strip rather than a small muted line — on the **same** surface and spacing as a populated `IterationCard` (library-default `Card` padding, no `mt-*` of its own, since neither `TabsContent` nor the populated grid adds top spacing), so the tab body's rhythm does not change with its contents (`vinaya-pages-v2` task 14, #627) — but **only when the hint is non-null**: a null hint means that tab's forge fetch failed and the `ForgeBanners` above already carry the real explanation, so the grid renders nothing rather than a second, vaguer "nothing here" panel (D-087 — the Studio explains emptiness once, accurately). **Both** tabs derive the hint from their own `ForgeStatus` (`forge.active`/`forge.archived`); Archived hardcoded its string until this task, so a failed fetch rendered a confident "No archived iterations yet." directly above the banner contradicting it.
