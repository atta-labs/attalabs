# Vinaya Web

Next.js web app for Vinaya — landing page plus the methodology surfaces (The Harness, State Machine, Docs, Start, CLI, Studio). Has its own Sanity CMS identity (reusing Vitakka's project `o56nzgrr`): the layout fetches its own config/branding via `getProductCms('vinaya')`, the generic key-addressed pattern every consumer uses. See [vinaya-spec.md](../specs/vinaya-spec.md).

## Landing (`/`) — hero

The v3 design: hand-rolled `<canvas>` hero scenes (`src/app/(site)/_components/canvas/NormalEraCanvas.tsx`/`LightSpeedEraCanvas.tsx`/`ProtectedCanvas.tsx`, each an isolated props-free client component), rendered through semantic theme tokens (canvas colors resolved from CSS custom properties, never hardcoded) — never the fixture's own cream palette. `ProtectedCanvasPortrait.tsx` is a second, portrait-orientation variant of `ProtectedCanvas.tsx` (robots-only firing down into the ring, no human cluster) — `ProtectedSection.tsx` currently renders the portrait variant only, sized to match the era canvases' footprint.

The Hero and `#eras` sections' rotating bullet questions ("Ever clicked a link in your own docs and hit a dead end?" etc.) are not hardcoded copy — `src/lib/aeg/doctrine-questions.ts` reads `aeg-root/` doctrine content and calls `deriveDiagramModel()` from `@atta/aeg-core` to collect every node's `summary` as a real doctrine question, deduped. `RandomQuestionText.tsx` picks a random subset per page load and reveals them sequentially; its reserved-height box under `#eras` uses `minHeight` (not `height`) specifically because the line-count estimate is a heuristic (character-count based) and a hard cap let misestimates overflow into the "Meet Vinaya" button below — `minHeight` makes the box self-correct instead.

## `/studio` — dashboard

`src/app/studio/**` and `src/app/api/coherence/route.ts` are Vinaya Studio's dashboard. It reads governance state via its own `repo-state`/`forge` derivation layers (`src/lib/repo-state/`, `src/lib/forge/`) — no governance logic is re-implemented here — the corresponding web/cli one-way import boundary is enforced by `src/lib/import-boundary.test.ts`.

The local `/studio` home (`studio/page.tsx`) is a three-card dashboard — Projects and Tranches preview cards, then a single full-width **Tasks** card that is the one work surface: every Ready / active / blocked tranche task plus the backlog, in one status-filterable list (`studio/_components/TasksPanel.tsx`). The standalone `/studio/backlog` table also stays, separately.

Rows are minimal and column-aligned — `#issue` links to GitHub in a fixed-width leading cell (rendered even when a task has no Issue, so a two-digit and a four-digit number leave the rest of the row starting at the same x), then a status badge and the plain (non-clickable) title, with the tranche slug linking to its board (backlog rows carry no tranche). On wide viewports the title absorbs the leftover width and wraps within its own cell, so the slug holds the right edge of the first line; on narrow ones the row wraps and the slug drops to its own line, left-aligned under the issue number rather than stranded against the far edge. Rows stay flex, not a `<table>`. Narrow viewports also rule between tasks, since a multi-line row otherwise runs into the next one; wide ones drop the rule, where each task is a single line and it would only add noise. The Tasks card's chip row carries the same FILTER BY heading treatment as the backlog table, so both filter surfaces are announced as one labelled control.

The Tasks list aggregates via `studio/_lib/load-dashboard-tasks.ts`, which reads the tranche board's own `deriveTranche` + `checkDispatchReadiness` (via `loadTrancheSnapshot`/`loadDispatchReadiness`) and consumes the `status-display.ts` label vocabulary rather than re-deriving status.

### Board href derivation

A tranche's board href is derived in one place — `studio/_lib/tranche-href.ts`'s `boardHref()` — as its first **registered** project's route. All three surfaces that reference a board go through it: the home Tranches card, `tranches/TranchesTabs.tsx` (via the `trancheHref()` summary wrapper), and the Tasks card's per-task slug (via `load-dashboard-tasks.ts`, which resolves per `task.projects`, not per summary — which is why the shared rule takes a project list rather than a `TrancheSummary`). A tranche's `projects` is the union of the `project:*` labels **and** each Issue body's `**Project:**` field (derived in `@atta/aeg-forge-state`).

`boardHref()` takes the set of registered project names (from `.vinaya/projects.md`) and links only to a project in it, picking the first *registered* one — because only a registered project has a board (`readProject(name)` `notFound()`s otherwise). This avoids a dead-link class: a **retired** project name can still ride on an archived tranche's Issues, and linking to it 404s. So a tranche has no board to point at when **either** it declares no project at all (both label and field absent) **or** every declared project is unregistered. A missing `project:*` label alone is **not** board-less — the Issue-body `**Project:**` field still resolves a board. The mechanism is "not in `projects.md`" — a retired name, a typo, or a not-yet-registered project all render board-less rather than being surfaced as malformed; `projects.md` is the authority for what's registered.

That board-less state is real, not an error, and every such reference renders non-clickable but **self-explaining**: `NO_BOARD_REASON` ("No board — no registered project for this tranche.") as a `title=` tooltip on all three surfaces, plus an inline muted note on the `TrancheCard`. Board-less rows never render silently dead.

### Backlog table

`studio/backlog/page.tsx` is a filterable `@atta/ui` Table (client `backlog/_components/BacklogTable.tsx`) with project + tier + flags inline toggle-chip filters — every option visible, no dropdown — one row per Issue, so a cross-project Issue carries both `project:*` badges in a single row (matched by the project filter under either) instead of being dropped to its first label. Tranche/state are deliberately not filters (the backlog is the open, no-`tranche:*` set by definition), and the chip rows carry a **FILTER BY** `h2` with a left-pinned `Filter` icon, which also labels the chip block (`role='group' aria-labelledby`) so the filter controls have a programmatic name and not merely a visual one.

The table is `table-fixed`, so its `w-[..%]` column widths are one 100% budget that has to be rebalanced as a set — Flags is the widest label column at 32% because its labels are the longest, funded out of Title (37→32%, it wraps freely anyway) and Tier (11→10%). Since `vinaya-web` resolves the **retro** library, whose `Badge` ships `whitespace-nowrap` + a fixed `h-5` + `overflow-hidden`, the label cells relax those three on their children (`BacklogTable.tsx`'s `LABEL_CELL`) so a long label wraps INSIDE its column instead of overhanging the neighbour — the relaxation is on the cell, not on the shared `LabelBadge`, because the constraint belongs to this table's fixed layout rather than to the badge.

Forge honesty is uniform: `fetchOpenIssuesWithoutTrancheLabel` returns `{ issues, forge }` carrying a `ForgeStatus`, and both pages render `ForgeBanners`/`ForgeUnavailableBanner` on failure instead of a truth-shaped empty list — the Projects card, sourced from the local registry, still renders when the forge is down.

## Portal vs. Studio — production gating

Portal and Studio are two products sharing this one deployment: `src/lib/env.ts`'s `isVercelDeploy()` gates on `VERCEL_ENV` **presence**, not equality to `'production'` — `VERCEL_ENV` is also `'preview'` on every preview deploy, and an equality check would leave preview ungated — so a local `bun run build && bun run start` (neither var set) still shows the real dashboard while both production and preview redirect. In either case `/studio` renders nothing of its own; it `redirect()`s to `/the-studio` (a Portal page under `(site)/the-studio/page.tsx`), and `/studio/projects`/`/studio/tranches`/`/studio/backlog` still 404 on any Vercel deploy. `/the-studio` is therefore the only thing a production visitor ever sees of Studio: a display hero, then one section per Studio surface (`_components/StudioSection.tsx`, eyebrow/heading/body/shot) each carrying a real committed screenshot of local Studio (`_components/StudioShot.tsx`, a framed `next/image` — the frame is what lets a single-theme capture still read correctly under either viewer colour scheme), each shot captured in both colour schemes with a section-level switch between the pair and a click-to-expand dialog, and a closing section linking to `/docs/cli`, `/docs`, and `/roadmap` (deployed Studio stays a roadmap item, never claimed as shipped). The screenshots live under `apps/vinaya/web/public/`, this app's first use of Next's `public/` directory.

## `/docs`

A 4-card hub (Harness · State Machine · CLI · Reference) — plain navigation, no forge/model dependency of its own; its children split across two nested route groups, `docs/(with-sidebar)/` (the doctrine catch-all + `reference/`, wrapped in the `DocSidebarHost` shell) and `docs/(standalone)/` (`harness/`, `state-machine/`, `cli/`, none wrapped in that shell), with static route directories taking precedence over the `[...slug]` catch-all so the four never collide with a doctrine slug. Its children read `aeg-root/**.md` off disk rather than from the forge, which matters for production (see Tracing markers, below).

### `/docs/reference`

The generated reference view of the harness (`src/lib/docs/load-aeg-docs.ts`). Its surfacing rule is **model-backed**: the loader derives the same `DiagramModel` `/docs/harness` draws and publishes a doc **iff a node points at it** — `modelBackedDocPaths` (in `@atta/aeg-core/docs`) maps gate/check → `enforcement.md`, role → `roles/<id>.md`, contract → `contracts/<id>.md`, and the `surfaced` frontmatter flag is the only override, in both directions. `aeg-root/glossary.md` is the one doc that uses that override in earnest: no model node points at a glossary, so the loader special-cases the slug `glossary` into its own one-doc **Glossary** nav section rather than folding it into Roles or Contracts. The loader passes that allowlist to `isSurfacedDoc`; C6 (`docs-coherence` via `verify-docs`) checks against the same set, so raw markdown that backs no reachable node (`state-machine.md`, `process.md`, `coordination.md`, `skills/**`, …) never becomes public.

The nav is the **harness tree**, not the file tree (sidebar titled **The Harness**): sections **Roles / Contracts / Actions / The Rings / Glossary** (no "Overview"), at a granularity that follows content size. File-sized nodes keep their own page — `/docs/roles/<id>`, `/docs/contracts/<id>` — which publish the model frame plus **the doc's `## The short version` section only**, never the `## Reference` body beneath it: the short version is binding normative text, the reference is linked on GitHub rather than inlined. A contract page also renders its seam as words (producer → consumer, from the model's own `produces`/`consumes` edges). `publishedDoctrineBody` (`@atta/aeg-core/docs`) is the single extraction the page and the C7 gate share, so what renders and what is checked can never drift; it degrades to the body above `## Reference` if a doc ever lacks a short version, so the reference cannot leak. C7 (`published-prose.ts`, via `verify-docs --pr`) gates that section's structure and readability.

Row-sized nodes become `#`-anchored sections: `/docs/rings/ring-<0|1|2>` renders that ring's gates/checks as model-derived sections, and `/docs/actions` renders `ACTIONS` the same way; `/docs/rings` is the landing = `enforcement.md`'s three-ring intro prose. The one node→route source is `@atta/aeg-core`'s `nodeDocRoute`/`nodeDocHref` (`src/docs/node-route.ts`) — consumed by the nav, `docs/(standalone)/harness/_lib/read-more.ts`, and the `/docs/reference` map alike, so a card's deep-link, a "Read more" anchor, and a heading `id` are the identical slug.

The route is responsive: below `lg` the fixed rail is hidden and the nav opens as a **left drawer** (`Sheet side='left'`) from a menu trigger in a `lg:hidden` bar; at `lg`+ it is the unchanged fixed rail. Both surfaces render the same `DocSidebarNav` body out of `DocSidebar.tsx` (which carries the `role='navigation'` / `aria-label='The Harness'` landmark on the scroll container itself, rather than a wrapping `<nav>` that would break its flex/overflow) — unlike `/docs/cli`, whose sidebar hides below `lg` with no drawer because it is a same-page scroll-spy TOC rather than cross-route nav. `/docs/enforcement` 307-redirects to `/docs/rings` (old surfaced URL kept alive).

### `/docs/cli`

Vinaya's own CLI command reference — renders `@atta/vinaya-sources`' `COMMANDS` registry (so `web` depends on it directly without reaching into `cli` internals) rather than reading `aeg-root/**.md`. On `lg:` and up it is a two-pane command reference (the `cli.github.com/manual` shape): a sticky command sidebar (`docs/(standalone)/cli/_components/CliSidebar.tsx`) beside the content pane, reusing the `/docs/reference` `SidebarProvider`/`SidebarMenu` primitives — but active state is scroll-position-driven (an on-page TOC via `IntersectionObserver`), not pathname-driven, since every command is a section on this one page and clicking an item anchor-scrolls to it. The sidebar's hrefs and the content sections share one slug via `docs/(standalone)/cli/_components/command-slug.ts` (a plain, non-`'use client'` module so the server page can stamp the section ids the client sidebar links to). Below `lg` the sidebar is hidden and the page is a centered stacked column. The content pane's own shape (measure, top spacing, background, independent scroll) lives in `docs/(standalone)/cli/layout.tsx`, deliberately matching `/docs/reference`'s and `/start`'s `layout.tsx` shape by duplication rather than import — those trees were mid-edit on sibling work at the time a shared extraction would have touched. Both render code through `@atta/ui`'s `Code`/`CodeBlock`. The page renders `COMMANDS` in registry order.

### `/docs/state-machine`

`/docs/harness`'s sibling reference page: the AEG state machine as four tables — forge fact inputs (`FORGE_FACT_INPUTS`), labels and the one orthogonal fact each carries (`LABELS`), derived statuses (`DERIVED_STATUSES`, each marked derivable-or-not against `DERIVABLE_STATUSES` and cross-referenced to the rules that conclude it), and the ordered rule chain (`DERIVATION_RULES`). Every row maps over a model array; nothing is hand-authored. Where `/docs/harness` derives a `DiagramModel` from doctrine files, this page's `_lib/load-state-machine.ts` is a passthrough over static exports — its one real job is the SERVER BOUNDARY: it carries `import 'server-only'` because `@atta/aeg-core`'s barrel reaches `@atta/aeg-forge-state`'s `gh.ts` and so `node:child_process`, which Turbopack will not bundle for the browser; `page.tsx` and `_components/StateMachineTables.tsx` are both server components, so the model is held rather than serialized and a `'use client'` on either would be the bug. The loader also strips `DerivationRule.matches` on the way out — an unserializable predicate that is never rendered — so no caller can push a function across a client boundary. Client-side label needs go through the pure `@atta/aeg-forge-state/labels` subpath, never the barrel.

The page opens with a derived overview diagram (`_components/StateMachineDiagram.tsx`, server-rendered, stacked under the intro below `lg`): inputs → the ordered rule chain → the statuses it concludes, every count read as an array length and every status chip as an array element via `deriveDiagramGroups` in the loader — no hand-authored numbers. **What the tests actually cover:** `_lib/load-state-machine.test.ts` pins that `loadStateMachineModel` is a faithful passthrough of the model arrays and that `deriveDiagramGroups`' counts/names are array lengths and elements. It does **not** cover what the components render — this app has no React-render infrastructure, so a hand-authored `<TableRow>` in `StateMachineTables.tsx` would pass. The derivation lives in `_lib` precisely so the part that CAN be tested is; the components' no-literals rule is held by review and by their own doc comments.

## `/roadmap`

Five hand-authored roadmap items (Loop Engineering, Studio on the web, Linear & Jira support, Configurable forge, Configurable roles) living as a data array in `(site)/roadmap/page.tsx`, each a `Card` carrying its own bespoke concept mark from `(site)/roadmap/_components/RoadmapMarks.tsx` (a diagram of the feature rather than a stock glyph, `aria-hidden`). The items are deliberately **not** derived from forge state: the page imports no `@atta/aeg-core`, spawns no `gh` subprocess, and holds no forge dependency of any kind — which is why it stays live in production where `studio/*` `notFound()`s.

## `/start`

The adopter's path. `start/layout.tsx` matches `/docs`' `layout.tsx` shape (`StartSidebarHost`: a fixed rail at `lg`+, a `Sheet side='left'` drawer below, both rendering `StartSidebarNav` from one nav data module, `_components/start-nav.ts`) over this section's own fixed nav rather than `/docs`' model-derived one — no forge/model dependency, so this shell needs no async data fetch of its own. In `start-nav.ts`, Overview rides the section's own `overview` field rather than `items`, because a drift test pins Ship with Vinaya's `items` to exactly the seven stage ids and `StagePage`'s prev/next footer maps over `items` as the stage sequence — folding Overview into `items` would break both. `/start` itself `permanentRedirect`s to `/start/quick`; the conceptual material lives at `/start/overview`.

`/start/quick` is four fixed steps as a hand-authored data array, each a numbered `Card`: install (`_components/PackageManagerTabs.tsx`, a **local** `'use client'` tab block over `npm`/`pnpm`/`yarn`/`bun`, each rendering that manager's install-and-init one-liner via Radix `forceMount` + a `data-[state=inactive]:hidden` panel class so every command is server-rendered, not only the one a client mounts), `init`, `init product`, then "Start working". The tab block is built on primitives (`Tabs`/`TabsList`/`TabsTrigger`/`TabsContent`, `Code`/`CodeBlock`) the retro library this app resolves already re-exports — not an addition to `@atta/ui`.

"Ship with Vinaya" is seven pages — `/start/plan`/`brief`/`develop`/`review`/`security`/`archive`/`wrap-up`, one per non-Principal role in `aeg-root/roles/*.md` — sharing one component, `_components/StagePage.tsx`: a one-line in/out summary, that stage's full IN / transformation / OUT diagram (`_components/StageGlyph.tsx`'s `StageDiagram`), the same four questions every time (what kind of tool, what you say to it, what comes out, what to look at in Studio), then a "Read more" link into that role's `/docs/roles/<id>` page. The diagrams are a **port of an approved external design**: eight noun marks (Intent, Task issue, Tranche, Brief, Pull request, Verdict, Provenance record, Retrospective) live as `<defs>` in `MarkDefs` — mounted exactly ONCE per page, since the `#v-*` ids are document-global — and every diagram composes them via `<use>`, so a stage's output mark IS the next stage's input mark. The geometry (every `d` attribute, viewBox, transform) is copied verbatim from the design markup, never redrawn, while the chrome around it is this repo's own (retro `Card` containers, semantic tokens). The stage model — id, role, receives, produces, and the `aeg-root/contracts/*.md` file each is read from — lives in `_lib/stages.ts`, checked against the doctrine by a drift test (`_lib/stages.test.ts`) rather than hand-copied; Security carries no contract, since it runs alongside Review on the same pull request rather than sitting in the sequential chain.

`/start/overview` renders `_components/LoopComposition.tsx`: the design's noun-vocabulary card grid, then the full loop SVG (Plan fans out into per-task rows, Review and Security bracketed on ONE pull request, the MERGED gate, Archive, then Wrap up with human sign-off feeding the tranche's outcome back into the next Plan). The rule that keeps this section from drifting into a second copy of `/docs` is one-directional — a stage page links into `/docs`, never restates a rule it owns — which is why `/start/develop` alone carries two retained, verified `vinaya check --all` transcripts (`_components/GateRefusalDemo.tsx`): seeing a refusal is what makes determinism concrete, and `develop` is where a reader first runs the command that produces one. Like `/roadmap`, every page in this section carries no forge dependency and no `@atta/aeg-core` import — the drift test is the one place under `/start` that reads `aeg-root/contracts/*.md`, and it runs only at test time, never from a page.

## Nav / chrome

Nav is two-tier: root `layout.tsx` only wires `NextWebShell` (theme/shell, no TopBar of its own); the `(site)` route group (Home, The Harness, State Machine, Start, CLI, Docs, Studio, Roadmap) carries the site TopBar; `src/app/studio/layout.tsx` carries its own TopBar (logo "Vinaya Studio", links Home/Projects/Tranches/Backlog/Docs) with no left sidebar.

## Studio layout — shell owns padding, not nested layouts

The `/studio/projects` sub-bar (`ProjectsSubBar`) is sticky within `StudioShell`'s scroll container so it stays pinned under the topbar as the page scrolls; `projects/layout.tsx` adds no overflow/height of its own. **`StudioShell` owns the page padding too** — it is the single source of the `px-8 py-8` gutter, the `max-w-6xl` column, and the one scroll container, and a nested layout re-applying any of them is a bug, not a local override. `projects/layout.tsx` keeps a `pt-8` that is **the sub-bar's counterweight, not padding** — deleting it butts the first heading against the bar. `ProjectsSubBar`'s own negative top margin cancels the shell's top padding so the bar pins under the topbar — the counterweight and the cancellation must move together.

## Tranche board detail page — status derivation

The tranche board (`studio/projects/[name]/tranches/[slug]/page.tsx`) carries no breadcrumb — the topbar and sub-bar are the only nav — and its body below the header is two tabs, **Tasks** (the topology table, plus the backlog and coherence sections) and **Token Ledger**. Its header badge is one of three states — **Archived**, **Ready to archive**, **Active** — derived by `studio/_lib/tranche-status.ts`'s `deriveTrancheStatus(counts, archived)`, the same function `TrancheCard`'s `TaskProgress` consumes for its done-chip-vs-progress-bar branch, so the card and the board can never disagree on completion. `awaiting-archive` (every task resolved, at least one of them merged, `forgeAvailable`, Milestone still open) is deliberately distinct from `archived` (the Milestone closed) — it is the normal window before the Tranche Archivist runs, not an error, so its tone and copy invite the archive step rather than read as terminal or as a warning. `forgeAvailable: false` always falls back to the plain **Active** reading — the derivation never claims completeness from counts it cannot trust.

**Resolved is not the same as merged**, and that distinction is the whole of `src/lib/forge/task-buckets.ts`: `bucketTaskStatuses` is the one status → count bucketing both the cards and the board's own header read, and it carries every `DerivedStatus` under its own name instead of letting the terminal-without-merge pair fall through a `default`. A `dropped` task (Issue closed `NOT_PLANNED` — legitimately abandoned) leaves no outstanding work but never shipped, so completion is `done + dropped === total` while `done` itself stays honest, and the progress ratio measures done over what can still ship (`total - dropped`). An `incoherent` task (closed, no merged PR) is the opposite case — a defect the `Closes #N` law exists to surface — so it counts toward neither, and holds the tranche at **Active** until it is resolved.

Tab state is the only client-side piece: `_components/TrancheTabs.tsx` is a thin `'use client'` shell around `@atta/ui` `Tabs` that takes both panels as `ReactNode` props, so the page itself stays a server component and its `dynamic = 'force-dynamic'` live-forge reads are unaffected. The ledger tab always renders — its forge-unavailable banner and its no-rows empty state live inside the tab rather than replacing it. A project page's "no tranches" state (`projects/[name]/ProjectTranchesTabs.tsx`) renders as a `Card` + lucide `Inbox` block under the tab strip, on the **same** surface and spacing as a populated `TrancheCard`, **but only when the hint is non-null**: a null hint means that tab's forge fetch failed and the `ForgeBanners` above already carry the real explanation, so the grid renders nothing rather than a second, vaguer "nothing here" panel — the Studio explains emptiness once, accurately. Both tabs derive the hint from their own `ForgeStatus` (`forge.active`/`forge.archived`) rather than a hardcoded string, so a failed fetch never contradicts the banner above it.

## Tracing markers — the one production-only 500 class

`/docs/reference` and `/docs/harness` read `aeg-root/**.md` off disk rather than from the forge, which carries its own production requirement: neither loader is handed a root — `findRepoRoot()` (`src/lib/github-links.ts`) walks up from `process.cwd()` for `vinaya.config.json`, and `read-root.ts` walks up for `.vinaya/projects.md` — so **the marker files, not just the doctrine glob, must appear in `next.config.ts`'s `outputFileTracingIncludes`**. Vercel's serverless bundle ships only what tracing detects; a missing marker makes the walk throw before a single doctrine file is opened, 500ing exactly the routes that call it while every other route stays green. Locally the markers are always present, so nothing reproduces there.

Changing either marker constant means changing the tracing list in the same commit, for every marker the commit touches — mechanized rather than trusted: `src/lib/tracing-markers.test.ts` discovers every upward walk under `src/` (`github-links.ts`, `repo-state/read-root.ts`, `docs/load-aeg-docs.ts`), parses each one's marker out of source (the modules are `server-only` and cannot be imported), resolves the declared tracing entries as real paths, and fails if a marker is undeclared, declared at the wrong depth, names something that does not exist at the repo root, or belongs to a walk the guard does not yet know about.

## TopBar / ProductSwitch

Both TopBars (`(site)/layout.tsx`, `studio/layout.tsx`) render the CMS logo (`getProductCms('vinaya')`'s `branding.logoSolidDark`/`logoSolidLight`) plus `src/app/_components/ProductSwitch.tsx`, a Portal↔Studio switch gated `!isVercelDeploy() && hasForgeConnection()` (`src/lib/forge-connection.ts`) — forge-reachability alone is never sufficient authorization; the deploy-target gate above it is what keeps the switch out of production. The control splits across two files so the gate runs server-side: `ProductSwitch.tsx` is an async server component holding the gate, so an unauthorized request never ships the control at all; `ProductSwitchControl.tsx` is the `'use client'` toggle, navigating via `onCheckedChange` → `router.push` rather than an `href`. It carries a small visible STUDIO label stacked tight above the switch — the bare switch alone gave a first-time visitor no hint it was a destination toggle; the switch's own `aria-label` still states the current surface for assistive tech.
