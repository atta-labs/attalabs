# Vinaya Web

Next.js web app for Vinaya — landing page plus the methodology surfaces (The Harness, State Machine, Docs, Start, CLI, Studio). The landing (`/`) applies the v3 design (`vinaya-landing-v3-implementation-brief`): hand-rolled `<canvas>` hero scenes (`src/app/(site)/_components/canvas/NormalEraCanvas.tsx`/`LightSpeedEraCanvas.tsx`/`ProtectedCanvas.tsx`, each an isolated props-free client component — the original SVG+CSS-keyframe renderer was reworked to canvas per `vinaya-landing-v3-canvas-rework-brief` after the SVG scenes read as disconnected floating debris) and the v3 hero copy, all rendered through semantic theme tokens (canvas colors resolved from CSS custom properties, never hardcoded) — never the fixture's own cream palette. Has its own Sanity CMS identity (reusing Vitakka's project `o56nzgrr`): layout fetches its own config/branding via `getProductCms('vinaya')`, the generic key-addressed pattern every consumer uses. See [vinaya-spec.md](../specs/vinaya-spec.md).

The Hero and `#eras` sections' rotating bullet questions ("Ever clicked a link in your own docs and hit a dead end?" etc.) are not hardcoded copy — `src/lib/aeg/doctrine-questions.ts` reads `aeg-root/` doctrine content and calls `deriveDiagramModel()` from `@atta/aeg-core` to collect every node's `summary` as a real doctrine question, deduped. `RandomQuestionText.tsx` picks a random subset per page load and reveals them sequentially; its reserved-height box under `#eras` uses `minHeight` (not `height`) specifically because the line-count estimate is a heuristic (character-count based) and a hard cap let misestimates overflow into the "Meet Vinaya" button below — `minHeight` makes the box self-correct instead. `ProtectedCanvasPortrait.tsx` is a second, portrait-orientation variant of `ProtectedCanvas.tsx` (robots-only firing down into the ring, no human cluster) — `ProtectedSection.tsx` currently renders the portrait variant only, sized to match the era canvases' footprint.

The `/studio` subtree (`src/app/studio/**`, `src/app/api/coherence/route.ts`) is Vinaya Studio's dashboard, ported from the old AEG Studio (#493; that app was deleted outright by `deprecation-v1` task 1). It reads governance state via its own `repo-state`/`forge` derivation layers (`src/lib/repo-state/`, `src/lib/forge/`) — no governance logic is re-implemented here — the corresponding web/cli one-way import boundary is enforced by `src/lib/import-boundary.test.ts` (`vinaya-studio-v1` task 4, #389). `src/lib/repo-state/` was `src/lib/aeg-fs/` until #553: the name came over with the port, and Vinaya names nothing after AEG. The local `/studio` home (`studio/page.tsx`) is a three-card dashboard (`vinaya-pages-v1` task 11, #571) — Projects and Tranches preview cards, then a single full-width **Tasks** card that is the one work surface: every Ready / active / blocked tranche task plus the backlog, in one status-filterable list (`studio/_components/TasksPanel.tsx`). Backlog was folded into the Tasks card rather than shown as its own card — a Principal-directed consolidation from the original four-card design during the design pass; the standalone `/studio/backlog` table stays. Rows are minimal and column-aligned — `#issue` links to GitHub in a fixed-width leading cell (rendered even when a task has no Issue, so a two-digit and a four-digit number leave the rest of the row starting at the same x), then a status badge and the plain (non-clickable) title, with the tranche slug linking to its board (backlog rows carry no tranche). On wide viewports the title absorbs the leftover width and wraps within its own cell, so the slug holds the right edge of the first line; on narrow ones the row wraps and the slug drops to its own line, left-aligned under the issue number rather than stranded against the far edge. Rows stay flex, not a `<table>`. Narrow viewports also rule between tasks, since a multi-line row otherwise runs into the next one; wide ones drop the rule, where each task is a single line and it would only add noise. The Tasks card's chip row carries the same FILTER BY heading treatment as the backlog table, so both filter surfaces are announced as one labelled control. A tranche's board href is derived in one place — `studio/_lib/tranche-href.ts`'s `boardHref()` — as its first **registered** project's route. All three surfaces that reference a board go through it: the home Tranches card and `tranches/TranchesTabs.tsx` (via the `trancheHref()` summary wrapper) and the Tasks card's per-task slug (via `load-dashboard-tasks.ts`, which resolves per `task.projects`, not per summary — which is why the shared rule takes a project list rather than an `TrancheSummary`). A tranche's `projects` is the union of the `project:*` labels **and** each Issue body's `**Project:**` field (derived in `@atta/aeg-forge-state`). `boardHref()` takes the set of registered project names (from `.vinaya/projects.md`) and links only to a project in it, picking the first *registered* one — because only a registered project has a board (`readProject(name)` `notFound()`s otherwise). This closes a live dead-link: a **retired** project name still rides on its archived tranches' Issues (`deprecation-v1` declares `Project: aeg`, whose `projects.md` row was deleted when the old AEG Studio was ported to Vinaya), and the prior first-project rule linked it to `/studio/projects/aeg/…`, which 404s. So a tranche has no board to point at when **either** it declares no project at all (both label and field absent — `admin-ui-library-picker-v1`) **or** every declared project is unregistered (`aeg-coherence-v1`, which declares only the retired `aeg`). A missing `project:*` label alone is **not** board-less — the Issue-body `**Project:**` field still resolves a board (`state-machine-v1` carries no label yet links to `aeg-core`). The mechanism is "not in `projects.md`", of which "retired" is only the common case: a typo (`vda`) or a project registered later would also render board-less here rather than being surfaced as malformed — `projects.md` is the authority for what's registered, and refusing to link an unregistered name is that file's own malformed-project rule, mechanized at the surface (the row still shows `projects · <name>` beside the reason, so it never lies). That genuinely board-less state is real, not an error, and every such reference renders non-clickable but **self-explaining**: `NO_BOARD_REASON` ("No board — no registered project for this tranche.", honest for both cases) as a `title=` tooltip on all three, plus an inline muted note on the `TrancheCard`. Board-less rows never render silently dead (the Studio does not lie by omission, including by omitting the reason). The Tasks list aggregates via `studio/_lib/load-dashboard-tasks.ts`, which reads the tranche board's own `deriveTranche` + `checkDispatchReadiness` (via `loadTrancheSnapshot`/`loadDispatchReadiness`) and consumes the `status-display.ts` label vocabulary rather than re-deriving status. `studio/backlog/page.tsx` was rebuilt in that task as a filterable `@atta/ui` Table (client `backlog/_components/BacklogTable.tsx`, project + tier + flags inline toggle-chip filters — every option visible, no dropdown) — one row per Issue, so a cross-project Issue carries both `project:*` badges in a single row (matched by the project filter under either) instead of being dropped to its first label; tranche/state are deliberately not filters (the backlog is the open, no-`tranche:*` set by definition), and the chip rows carry a **FILTER BY** `h2` with a left-pinned `Filter` icon, which also labels the chip block (`role='group' aria-labelledby`) so the filter controls have a programmatic name and not merely a visual one. The table is `table-fixed`, so its `w-[..%]` column widths are one 100% budget that has to be rebalanced as a set — Flags is the widest label column at 32% (`vinaya-pages-v2` task 11, #624) because its labels are the longest, its +6 funded out of Title (37→32%, it wraps freely anyway) and Tier (11→10%). Since `vinaya-web` resolves the **retro** library, whose `Badge` ships `whitespace-nowrap` + a fixed `h-5` + `overflow-hidden`, the label cells relax those three on their children (`BacklogTable.tsx`'s `LABEL_CELL`) so a long label wraps INSIDE its column instead of overhanging the neighbour — the relaxation is on the cell, not on the shared `LabelBadge`, because the constraint belongs to this table's fixed layout rather than to the badge. Forge honesty is uniform: `fetchOpenIssuesWithoutTrancheLabel` returns `{ issues, forge }` carrying a `ForgeStatus`, and both pages render `ForgeBanners`/`ForgeUnavailableBanner` on failure instead of a truth-shaped empty list — the Projects card, sourced from the local registry, still renders when the forge is down. Portal and Studio are two products sharing this one deployment: `src/lib/env.ts`'s `isVercelDeploy()` gates on `VERCEL_ENV` **presence**, not equality to `'production'` — `VERCEL_ENV` is also `'preview'` on every preview deploy, and an equality check left preview ungated until code/security review caught it — so a local `bun run build && bun run start` (neither var set) still shows the real dashboard while both production and preview redirect. In either case `/studio` renders nothing of its own, it `redirect()`s to `/the-studio` (a Portal page under `(site)/the-studio/page.tsx` carrying the same honest local-only copy `StudioLocalOnlyLanding` used to render in-shell before this task deleted it), and `/studio/projects`/`/studio/tranches`/`/studio/backlog` still 404 on any Vercel deploy; `/the-studio` is therefore the only thing a production visitor ever sees of Studio, which is why `vinaya-pages-v2` task 5 (#603) rebuilt it from a placeholder card into the public landing page: a display hero, then one section per Studio surface (`_components/StudioSection.tsx`, eyebrow/heading/body/shot) each carrying a real committed screenshot of local Studio (`_components/StudioShot.tsx`, a framed `next/image` — the frame is what lets a single-theme capture still read correctly under either viewer colour scheme), and a closing section linking to `/cli`, `/docs`, and `/roadmap` (deployed Studio stays a roadmap item, never claimed as shipped). The screenshots live under `apps/vinaya/web/public/`, this app's first use of Next's `public/` directory; `/docs` (moved out of `studio/` into the `(site)` route group, `vinaya-pages-v1` task 8, #568) is unaffected since it reads `aeg-root/**.md` at build time, not the forge — `/studio/docs` and every `/studio/docs/<slug>` now permanently redirect there. Both TopBars (`(site)/layout.tsx`, `studio/layout.tsx`) render the CMS logo (`getProductCms('vinaya')`'s `branding.logoSolidDark`/`logoSolidLight`) plus `src/app/_components/ProductSwitch.tsx`, a Portal↔Studio switch gated `!isVercelDeploy() && hasForgeConnection()` (`src/lib/forge-connection.ts`) — for why forge-reachability alone is never sufficient authorization. The control splits across two files so the gate runs server-side: `ProductSwitch.tsx` is an async server component holding the gate, so an unauthorized request never ships the control at all; `ProductSwitchControl.tsx` is the `'use client'` toggle, navigating via `onCheckedChange` → `router.push` rather than an `href`. It carries a small visible STUDIO label stacked tight above the switch (`misc-hardening-v1` task 18, #702) — the bare switch alone gave a first-time visitor no hint it was a destination toggle; the switch's own `aria-label` still states the current surface for assistive tech and is unchanged.

`/docs` is the **generated reference view of the harness** (`src/lib/docs/load-aeg-docs.ts`) — moved out of `studio/` into the `(site)` route group by `vinaya-pages-v1` task 8; `/studio/docs` and every `/studio/docs/<slug>` now permanently redirect here. Its surfacing rule is **model-backed** (`vinaya-pages-v1` task 12, #590): the loader derives the same `DiagramModel` `/the-harness` draws and publishes a doc **iff a node points at it** — `modelBackedDocPaths` (in `@atta/aeg-core/docs`) maps gate/check → `enforcement.md`, role → `roles/<id>.md`, contract → `contracts/<id>.md` (16 files today), and the `surfaced` frontmatter flag is the only override — it always wins over the model, in both directions. `aeg-root/glossary.md` (task 11, #690) is the first doc to use that override in earnest: no model node points at a glossary, so the loader special-cases the slug `glossary` into its own one-doc **Glossary** nav section rather than folding it into Roles or Contracts. The loader passes that allowlist to `isSurfacedDoc`; C6 (`docs-coherence` via `verify-docs`) checks against the same set, so the raw-markdown ~60% that backs no reachable node (`state-machine.md`, `process.md`, `coordination.md`, `skills/**`, Cetana's `diagrams/**`, …) stops being public without a word being rewritten. The nav is the **harness tree**, not the file tree (sidebar titled **The Harness**): sections **Roles / Contracts / Actions / The Rings / Glossary** (no "Overview"), at a granularity that follows content size. File-sized nodes keep their own page — `/docs/roles/<id>`, `/docs/contracts/<id>`, which publish the model frame plus **the doc's `## The short version` section only**, never the `## Reference` body beneath it: the short version is binding normative text, the reference is linked on GitHub rather than inlined, and a contract page also renders its seam as words (producer → consumer, from the model's own `produces`/`consumes` edges — `carrier:` is deliberately not rendered, and role `performs:`/`refuses_when:` are not either, the first because its ids do not resolve against the action registry). `publishedDoctrineBody` (`@atta/aeg-core/docs`) is the single extraction the page and the C7 gate share, so what renders and what is checked can never drift; it degrades to the body above `## Reference` if a doc ever lacks a short version, so the reference cannot leak. C7 (`published-prose.ts`, via `verify-docs --pr` and full mode) gates that section's structure and its reader-readability. Row-sized nodes become `#`-anchored sections: `/docs/rings/ring-<0|1|2>` renders that ring's gates/checks as model-derived sections (label/badge/summary/detail, and for ring-0 the guarded action), and `/docs/actions` renders `ACTIONS` the same way; `/docs/rings` is the landing = `enforcement.md`'s three-ring intro prose (the one place its raw text renders). The one node→route source is `@atta/aeg-core`'s `nodeDocRoute`/`nodeDocHref` (`src/docs/node-route.ts`) — consumed by the nav, `the-harness/_lib/read-more.ts`, and the `/docs` map alike, so a card's deep-link, a "Read more" anchor, and a heading `id` are the identical slug (reused from the node id aeg-core stamps, never re-derived). The `/docs` index (the map) renders each part with its model `detail`/badges/what-it-guards and deep-links to the exact node. The route is responsive (`vinaya-pages-v2` task 16, #629): below `lg` the fixed rail is hidden and the nav opens as a **left drawer** (`Sheet side='left'`) from a menu trigger in a `lg:hidden` bar; at `lg`+ it is the unchanged fixed rail. Both surfaces render the same `DocSidebarNav` body out of `DocSidebar.tsx` (which carries the `role='navigation'` / `aria-label='The Harness'` landmark, on the scroll container itself rather than a wrapping `<nav>` that would break its flex/overflow), and the branch is pure Tailwind gating **in this app's code** — the shared `SidebarProvider` still does its own internal `useIsMobile()` `matchMedia` check — unlike `/cli`, which hides its sidebar below `lg` with no drawer because that sidebar is a same-page scroll-spy TOC rather than cross-route nav. `/docs/enforcement` 307-redirects to `/docs/rings` (old surfaced URL kept alive). It is distinct from `/cli`, Vinaya's own CLI command reference (`vinaya-pages-v1` task 9, #569; moved from `/install` — which now permanently redirects here — by `misc-hardening-v1` task 7, #681), which renders `@atta/vinaya-sources`' `COMMANDS` registry (moved out of `apps/vinaya/cli` in task 9's re-dispatch, so `web` depends on it directly without reaching into `cli` internals) rather than reading `aeg-root/**.md`. On `lg:` and up `/cli` is a two-pane command reference (`vinaya-pages-v2` task 1, #599, the `cli.github.com/manual` shape): a sticky command sidebar (`cli/_components/CliSidebar.tsx`) beside the content pane, reusing the `/docs` `SidebarProvider`/`SidebarMenu` primitives rather than a custom one — but active state is scroll-position-driven (an on-page TOC via `IntersectionObserver`), not pathname-driven, since every command is a section on this one page, and clicking an item anchor-scrolls to it. The sidebar's hrefs and the content sections share one slug via `cli/_components/command-slug.ts` (a plain, non-`'use client'` module so the server page can stamp the section ids the client sidebar links to). Below `lg` the sidebar is hidden and the page is the same centered stacked column as before. The content pane's own shape — measure, top spacing, background, independent scroll — now lives in `cli/layout.tsx` (`misc-hardening-v1` task 18, #702), matching `/docs`' and `/start`'s `layout.tsx` shape exactly rather than being inlined in `page.tsx`; it is a deliberate duplicate of that shape, not an import, since `/docs` and `/start` were mid-edit on sibling tasks at the time and a shared extraction would have rewritten the files those tasks were touching. Both render code through `@atta/ui`'s `Code`/`CodeBlock` (task 9 added them to the cross-library contract; task 8 adopted them here, deleting the class strings task 9 had copied from this file). `init` no longer sorts first on the page — task 7 deleted that stand-in-for-install hack now that `/start` (a sibling task, #682) is the dedicated install guide, so the page renders `COMMANDS` in registry order. `/state-machine` (`state-machine-v1` task 3, #615) is `/the-harness`'s sibling reference page and sits beside it in the nav: the AEG state machine as four tables — forge fact inputs (`FORGE_FACT_INPUTS`), labels and the one orthogonal fact each carries (`LABELS`), derived statuses (`DERIVED_STATUSES`, each marked derivable-or-not against `DERIVABLE_STATUSES` and cross-referenced to the rules that conclude it), and the ordered rule chain (`DERIVATION_RULES`). Every row maps over a model array; nothing is hand-authored, which is why `aeg-root/tranche-model.md` §3 no longer carries its own status table. Where `/the-harness` derives a `DiagramModel` from doctrine files, this page's `_lib/load-state-machine.ts` is a passthrough over static exports — its one real job is the SERVER BOUNDARY. It carries `import 'server-only'` because `@atta/aeg-core`'s barrel reaches `@atta/aeg-forge-state`'s `gh.ts` and so `node:child_process`, which Turbopack will not bundle for the browser; `page.tsx` and `_components/StateMachineTables.tsx` are both server components, so the model is held rather than serialized and a `'use client'` on either would be the bug. The loader also strips `DerivationRule.matches` on the way out — an unserializable predicate that is never rendered (`when` is the prose the model carries for it), so no caller can push a function across a client boundary. Client-side label needs go through the pure `@atta/aeg-forge-state/labels` subpath, never the barrel. The page opens with a **derived overview diagram** beside the intro (`_components/StateMachineDiagram.tsx`, server-rendered like the rest, stacked under the intro below `lg`): inputs (forge facts + labels) → the ordered rule chain → the statuses it concludes, every count read as an array length and every status chip as an array element via `deriveDiagramGroups` in the loader — no hand-authored numbers — followed by a signpost line naming the four table sections in reading order. **What the tests actually cover:** `_lib/load-state-machine.test.ts` pins the two `_lib` functions — that `loadStateMachineModel` is a faithful passthrough of the model arrays (same elements, same order, same length) and that `deriveDiagramGroups`' counts/names are array lengths and elements. It does **not** cover what the components render: this app has no React-render infrastructure (every suite is a pure `_lib` function), so a hand-authored `<TableRow>` in `StateMachineTables.tsx` would pass. The derivation lives in `_lib` precisely so the part that CAN be tested is; the components' no-literals rule is held by review and by their own doc comments. `/roadmap` (`vinaya-pages-v2` task 17, #655) is the simplest page in the `(site)` group: five hand-authored roadmap items (Loop Engineering, Studio on the web, Linear & Jira support, Configurable forge, Configurable roles) living as a data array in `(site)/roadmap/page.tsx`, each a `Card` carrying its own bespoke concept mark from `(site)/roadmap/_components/RoadmapMarks.tsx` (a diagram of the feature rather than a stock glyph, `aria-hidden` — the `CardTitle` carries the meaning). Both now render only `mx-auto max-w-4xl`; `projects/layout.tsx` keeps a `pt-8` that is **the sub-bar's counterweight, not padding** — deleting it butts the first heading against the bar. The tranche board (`studio/projects/[name]/tranches/[slug]/page.tsx`) carries no breadcrumb — the topbar and sub-bar are the only nav — and its body below the header is two tabs, **Tasks** (the topology table, plus the backlog and coherence sections) and **Token Ledger** (`vinaya-pages-v2` task 10, #623). Its header badge is one of three states — **Archived**, **Ready to archive**, **Active** — derived by `studio/_lib/tranche-status.ts`'s `deriveTrancheStatus(counts, archived)`, the same function `TrancheCard`'s `TaskProgress` consumes for its `done`-chip-vs-progress-bar branch (`misc-hardening-v1` task 2, #676): before this task each surface computed its own `done === total` (or, on the detail page, no completion check at all — just `archived ? Archived : Active`), so a tranche with every task merged but its Milestone still open read as **Active** on its own board while its card already read complete. `awaiting-archive` (every task merged, `forgeAvailable`, Milestone still open) is deliberately distinct from `archived` (the Milestone closed) — it is the normal window before the Tranche Archivist runs, not an error, so its tone and copy invite the archive step rather than read as terminal or as a warning. `forgeAvailable: false` always falls back to the plain **Active** reading — the derivation never claims completeness from counts it cannot trust. Tab state is the only client-side piece: `_components/TrancheTabs.tsx` is a thin `'use client'` shell around `@atta/ui` `Tabs` that takes both panels as `ReactNode` props, so the page itself stays a server component and its `dynamic = 'force-dynamic'` live-forge reads are unaffected. The ledger tab always renders — its forge-unavailable banner and its no-rows empty state live inside the tab rather than replacing it. A project page's "no tranches" state (`projects/[name]/ProjectTranchesTabs.tsx`) renders as a `Card` + lucide `Inbox` block under the tab strip rather than a small muted line — on the **same** surface and spacing as a populated `TrancheCard` (library-default `Card` padding, no `mt-*` of its own, since neither `TabsContent` nor the populated grid adds top spacing), so the tab body's rhythm does not change with its contents (`vinaya-pages-v2` task 14, #627) — but **only when the hint is non-null**: a null hint means that tab's forge fetch failed and the `ForgeBanners` above already carry the real explanation, so the grid renders nothing rather than a second, vaguer "nothing here" panel (the Studio explains emptiness once, accurately). **Both** tabs derive the hint from their own `ForgeStatus` (`forge.active`/`forge.archived`); Archived hardcoded its string until this task, so a failed fetch rendered a confident "No archived tranches yet." directly above the banner contradicting it.
